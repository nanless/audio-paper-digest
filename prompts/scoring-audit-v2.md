# 按论文类型复核评分的提示词

## 用途

先完成正文审校、表格核对和方法补充，再复核评分。只返回结构化评分，不改正文，也不处理插图。

## 提示词内容

~~~~
请复核下方分析的论文类型、八个维度的分数和理由。按不同类型适用的证据评价，不因论文类型加分、保底或重复扣分。

已有完整分析（代码已移除旧评分理由，其他正文保持完整）：

{existingAnalysis}

带编号的评分证据（只能依据这些内容核对或纠正事实）：

{sourceEvidence}

代码校验反馈：

{validationFeedback}

### 评分依据

先从方法研究、系统技术报告、模型报告、数据集与基准、综述、理论研究、应用研究中选择一个主要类型。类型决定采用哪些证据，不改变权重。

八个维度分别是创新性、技术严谨性、实验充分性、清晰度、影响力、开源、可复现性、工程/实践价值，满分依次为 2、1.5、1.5、1、1.5、1.5、0.5、1.5。八项满分合计 11，总分由代码求和并封顶 10。

判断证据能否支持论文实际声明，不机械要求所有论文都有传统消融。方法研究还要检查误差分析；系统及模型报告只在出现组件级因果声明时才要求对应消融；数据集与基准还要检查泄漏控制；综述还要检查分类体系；应用研究还要检查用户研究。其余类型沿用与审校阶段相同的证据要求。

系统级能力、软硬件协同、规模化方法和有证据的工程组合可以获得创新分，只有产品宣传不能。本速递面向语音、音乐和音频研究者；音频只是控制信号、附带模态或次要实验，而核心贡献属于视频、计算机视觉或自然语言处理等其他领域时，影响力通常不得超过 0.5。

每个理由引用一个或多个证据编号，形式如 `[A_METHOD]`、`[A_RESULTS]` 或 `[SCORING_SOURCE_3/20]`。原文证据优先于已有分析的转述，全文不同位置的证据都要考虑，不能只依据摘要或开头。占位提示和已经移除的旧评分理由都不是证据，重新依据当前证据写理由，不恢复旧理由。

不能反转或美化已记录的事实。例如原文或分析指出竞品版本、配置不透明，不能写成已经进行了公平比较。推测不能当成确认事实；“无法验证”也不等于“技术错误”。信息不足时降低 `confidence`，只在直接相关的维度扣分。

### 扣分归属

先确定每项缺陷归哪个维度，再写理由。同一个缺陷只能用于一个维度，不在其他理由中重复扣分：缺少代码、模型、数据或其他核心材料归开源；缺少模型参数、超参数、训练配置、硬件或复现步骤归可复现性；缺少支持结论的对比、消融、统计、压力测试或公平性控制归实验充分性；组织、文字、符号、公式解释或图表表达问题归清晰度；公开方法中的推导错误、不合理假设、算法或系统逻辑漏洞归技术严谨性。

闭源、参数未披露和无法复现本身不能用于技术严谨性或清晰度的扣分。创新性不能因闭源或配置缺失扣分；技术严谨性、实验充分性和清晰度不能把闭源、源码、超参数、训练配置和硬件配置缺失作为扣分事实。影响力和工程/实践价值不能重复扣开源或复现问题，开源不能扣复现步骤，可复现性不能再次扣闭源。代码会检查这些归属，违规输出会被拒绝。

开源按相应核心材料评分。模型论文看代码与模型，数据集论文看数据，工具论文看代码；理论研究看正文和附录是否公开核心证明、推导、假设和边界，不能仅因 `has_code`、`has_model`、`has_dataset` 均为否就给 0。

开源分只允许六个值：核心材料完整开放且文档完整为 1.5；开放但文档不完整为 1.2；部分开放为 1.0；明确承诺未来开放但尚未发布为 0.5；只有可访问的在线演示，没有核心材料为 0.2；完全关闭且无承诺为 0。演示不能给 0.5。

可复现性只看架构、训练、超参数、硬件、评测和步骤的披露是否充分。全部充分为 0.5；大部分充分、少量缺失为 0.3；关键配置大量缺失为 0.1；核心方法和配置几乎没有为 0。演示或开源仓库不能自动提高这一分数。

### 证据情况与分数上限

在 `evidenceProfile` 中记录是否声称多个组件有因果贡献，以及样本规模、部署测量、可复用工程资料和公开泛化评测是否已报告。`ablationStatus` 使用 `direct` 表示直接消融、`partial` 表示部分消融、`none` 表示缺失、`not_applicable` 表示不适用。`targetEvaluation` 使用 `public` 表示公开评测、`internal` 表示内部评测、`mixed` 表示两者都有、`not_applicable` 表示不适用。

`evidenceBoundary` 至少直接引用一个 `[证据编号]`，与 `evidenceIds` 一致。不能从“系统看起来完整”等叙述推断。方法、系统、模型、数据集或应用等实证论文的目标评测不能填 `not_applicable`。

`engineeringEvidence` 只能使用以下值：`measured_deployment` 表示真实延迟、吞吐或资源测量；`reusable_pipeline` 表示原文提供可复用且可核对的完整工程流程；`public_artifact_or_benchmark` 表示公开工具、数据或基准构成明确工程产物；`claim_only` 表示只有工程叙述或间接指标；`not_applicable` 表示不适用。只有 `measured_deployment` 才允许 `deploymentMeasured=true`。

代码会根据上述记录限制分数：多个组件的因果贡献没有直接消融时，实验充分性最高 1.2；只有部分消融时最高 1.3；只有内部评测且没有样本规模时最高 1.2；只有工程主张、没有测量或可复用产物时，工程/实践价值最高 1.0。理论、综述或未声称组件因果贡献的论文应如实使用不适用值，不机械套用方法论文的上限。

校验反馈指出具体错误时，针对该错误修正，不重复上次无效理由。非理论论文的明确资源状态会由代码按上述开源分值处理；理论研究依据公开证明材料判断。开源状态不能影响其他维度。

### 输出格式

只输出一个合法 JSON 对象，不加代码块围栏、前言、解释或结尾。键名和结构与示例一致，任何层级都不能增加键。八个维度各出现一次；`score` 是有限的非负 JSON 数字，最多一位小数且不超过对应满分，不写成字符串、`null` 或布尔值。开源分仅使用前述六个值。

每个 `reason` 至少 20 个字，写清具体证据。精确分数、样本量、模型规模、比例、名次和技术参数使用阿拉伯数字，中文与英文之间留空格。使用完整、自然的句子，不堆重复词、重复连接词或用分号结束段落。示例中的“具体理由”只是字段说明，不要复制到结果中。
