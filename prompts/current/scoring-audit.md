# 按论文类型复核评分的提示词

## 用途

先完成正文审校、表格核对和方法补充，再以盲审方式复核评分。只返回结构化评分，不改正文，也不处理插图。

## 提示词内容

~~~~
请以独立盲审方式复核文末 `<paper_input>` 中论文的文档类型、证据画像、八个维度的分数和理由。代码已移除初稿中的旧总分、旧分档、旧置信度、旧八维数值、旧论文评价和旧评分理由；请完全依据正文事实与编号证据账本重新评定，按不同类型适用的证据评价，不因论文类型保底或跨维度重复扣分。

### 一、先定文档类型与缺陷/强项画像，再打分

1. 先从 `方法研究`、`系统技术报告`、`模型报告`、`数据集与基准`、`综述`、`理论研究`、`应用研究` 中选择一个主要类型。
2. 在给出任何分数之前，先在 `evidenceProfile` 中如实列出：
   - `primaryStrengths`（1–3 条，每条不少于 12 字并直接引用 `[证据编号]`）：该论文最扎实、有原文证据支撑的核心强项。
   - `primaryDefects`（0–3 条，每条不少于 12 字并直接引用 `[证据编号]`）：该论文最关键的方法漏洞、核心主张与验证脱节、基线/消融缺口、表文算术矛盾或复现缺口；确未发现实质短板时可为空数组 `[]`，不要为了凑数编造缺陷。

### 二、盲权统一 10 分制五档行为锚定（`type-aware-v2`）

八个维度分别是 `innovation`（创新性）、`technicalRigor`（技术严谨性）、`experimentalSufficiency`（实验充分性）、`clarity`（清晰度）、`impact`（影响力）、`openSource`（开源）、`reproducibility`（可复现性）、`engineering`（工程/实践价值）。全部采用 **0.0–10.0 统一量表**（保留一位小数）。

代码会在 `type-aware-v2` 规则下根据你判定的文档类型自动计算加权总分与分档（`≥ 8.5` 前10%、`≥ 7.5` 前25%、`≥ 6.0` 前50%、`< 6.0` 后50%），本提示刻意隐藏各文档类型的具体百分比权重与开源加分系数：请独立、客观地在 **0.0–10.0 统一量表** 上评定每一项维度，严禁猜测权重或借调整单项分去凑目标总分。

七项核心维度必须充分拉开区分度，严禁所有论文或所有维度都挤在 `6.8–8.0` 中间带！普通可读、常规流水线或窄受众工作应如实落在 `4.5–6.8`，真正的旗舰/突破性工作应大胆给到 `8.2–9.5`：
- **9.0–10.0（里程碑 / 顶级水准）**：处于同方向同期前 5%，具有突破性范式/关键洞察、严密无漏洞的推导或系统设计、压倒性且公平的强基线与消融验证，或重大公开基础模型/基准贡献。
- **7.5–8.9（明显优秀）**：有明确且可核验的架构/算法/系统/基准创新（含跨规模效率显著跃升如小模型超越数倍参数基线），推导与协议严格控制，强基线与核心对照扎实。
- **6.0–7.4（扎实良好）**：问题成立、方法合理、实验可核对，但属稳健渐进改进、或覆盖范围/基线强弱/泛化存在局限。
- **4.0–5.9（存在明显短板）**：核心主张与验证严重脱节（如标榜低功耗却零功耗实测、零野外验证、零基线）、常规商用模块拼装、表文算术自相矛盾、或窄受众无通用外溢。
- **0.0–3.9（严重缺陷或不适用）**：存在实质性推导或逻辑错误、结论缺乏基本支撑、领域相关性极弱，或该维度对本文不适用（如纯理论研究无工程落地时 `engineering` 可给 `0.0`）。

#### 音频研究五档校准标尺卡（`audio-rubric-v2.1`）

评定八维分值时，请以以下五张音频领域具体标尺卡对齐尺度，防止“全员 7.5 分”通胀：
- **标尺 `5.2`（存在明显短板 / 后50%）**：例：拼接现成开源声学编码器或商用麦克风硬件用于单一窄场景，宣称“低功耗/实时”却零功耗与延迟实测、缺少强基线对比或组件消融，或正文与表格存在口径/算术自相矛盾；核心维度典型落在 `4.5–5.8`。
- **标尺 `6.5`（扎实良好 / 稳健渐进，前50%）**：例：在已有语音识别、语音增强或音乐分类框架上引入合理的损失项或特征前端微调，在 1–2 个标准公开集上取得小幅可核对提升，但方法原创性有限、对比基线偏旧或缺乏跨噪声/跨语种/跨设备泛化验证；核心维度典型落在 `6.0–7.0`。
- **标尺 `7.5`（明显优秀 / 细分方向扎实推进，前25% 门槛）**：例：针对流式神经音频编解码器、零样本语音合成、声源分离或声学表征中的明确瓶颈提出清晰可验证的机制/训练方案，具备公平强基线、直接组件消融以及规范主观听测或真实部署延迟实测，在单一细分赛道形成明确优势但跨任务外溢有限；核心维度典型落在 `7.2–8.0`。
- **标尺 `8.5`（强旗舰 / 顶级水准，前10% 门槛）**：例：在全模态音视频基础模型、原生语音交互、大规模高质量音频基准或高压缩低延迟编解码上实现显著能力或跨规模效率跃升（如小参数模型在多项公开权威基准稳定超越数倍参数开源前沿），防泄漏、统计检验、消融与真实硬件吞吐/延迟实测扎实且核心产物高开放度；核心维度典型落在 `8.0–9.0`。
- **标尺 `9.2`（里程碑 / 范式级突破，同期前 5%）**：例：开辟语音、音乐或通用音频建模/生成/评测新范式的基础模型、核心算法或决定性基准，在严格公平的广泛公开评测中形成压倒性领先，理论/系统设计与消融无明显短板，实测端到端部署效率与完整开源复现生态兼备，具备长期领域示范效应；核心维度典型落在 `8.8–9.6`。

### 三、各维度反通胀校准红线与音频领域专项红线

1. **`clarity`（清晰度）**：普通结构完整、文通字顺的论文只给 **`6.5–7.2`**（不要随手给 `7.8–8.2`！）。凡出现**正文与表格数字矛盾、表内求和算术错误、摘要与结论口径冲突、关键符号或单位混乱**的论文，`clarity` **不得超过 `5.8`**；仅符号严谨、图表教学价值极高且全文零内部矛盾的论文才给 `8.0–9.0`。
2. **`technicalRigor`（技术严谨性）**：“教科书常规公式（如标准 STFT/Mel/常规迁移学习）没有算错” **绝不等于 `7.8`**！若论文仅组装现成常规模块且存在**核心方法与立论脱节**（如标榜低功耗却无功耗建模与测量、用替代物种音频训练声称检测另一物种、综述缺乏系统检索纳入排除与去重协议或表内算术冲突），`technicalRigor` 应给 **`4.5–5.8`**；标准但自洽的工程/经验设计给 `6.5–7.4`；只有非平凡理论证明、严密统计检验与防泄漏/因果控制才给 `7.8–9.2`。
3. **`innovation`（创新性）**：现成商用硬件/开源模块拼装或纯描述性目录综述给 **`4.5–5.8`**；已有方法上的稳健渐进改进给 `6.0–7.2`；通过系统级架构/多阶段训练/数据与交互范式整合取得显著跨规模能力或效率跃升（例如 9B 模型超越 30B 级开源前沿、或 17×–30× 实时生成突破）给 **`7.5–8.5`**；真正开辟新问题范式或核心数学/架构突破给 `8.5–9.5`。
4. **`impact`（影响力）**：本速递面向语音、音乐和音频研究者。音频只是附带模态或次要验证、核心贡献属其他领域时，`impact` **不超过 `4.0`**。**窄地域/单语种资源盘点、小众野生动物/特定硬件原型且缺乏跨场景泛化或公开复用产物**时，`impact` 应给 **`4.0–5.5`**（不得随手给 `6.0–6.5`）；细分方向扎实方法给 `6.5–7.5`；全模态音视频基础模型若在原生音频理解、语音交互或音视频联合基准上系统评测并刷新开源 SOTA 或逼近专有前沿（且随权重/评测公开），属于音频核心方向重大推进，应正常给 **`8.2–9.2`**，不得因同时覆盖视觉模态而压低。
5. **音频领域四项专项红线（必须逐条核查）**：
   - **主观听测协议红线（MOS/CMOS/SMOS/ABX）**：严禁将不同听测人群或不同论文中的绝对 `MOS` 数值直接横向对比。凡提出主观音质/自然度/相似度领先主张的论文，必须核查是否报告**听测人数、样本数量、置信区间或方差、以及盲测听测协议**；若缺失关键听测协议细节或仅跨论文照搬旧 MOS 数字，必须扣减 `experimentalSufficiency` 并在 `primaryDefects` 中明确点出。
   - **客观代理指标与人类感知区分红线**：必须严格区分自动代理指标（如 `UTMOS`、`DNSMOS`、`PESQ`、受小样本量偏差影响的 `FAD`、以及受转写模型失真影响的 `Whisper-as-a-Judge`）与真实人类主观听测。仅凭单一或窄范围客观代理指标就宣称“达到人类感知更优/听感逼真超越基线”而缺乏真人盲测支撑时，必须在 `primaryDefects` 中指出并在 `experimentalSufficiency` 中扣分。
   - **实时/流式/因果声明实测红线**：凡宣称“实时（real-time）”“流式（streaming）”“低延迟”或区分因果/非因果架构的论文，若未给出实测 `RTF`、算法前瞻（lookahead）、帧/块处理延迟（frame/chunk latency）及对应测试硬件规格，一律必须设 `deploymentMeasured=false`、`engineeringEvidence="claim_only"`（触发 `engineering ≤ 5.5` 上限），并在 `primaryDefects` 中注明缺少真实流式部署实测。
   - **开源产物自动探测核验红线（`[A_ARTIFACT_PROBE]`）**：当评分证据账本包含 `[A_ARTIFACT_PROBE]` 自动探测摘要且显示仓库虽返回 HTTP 200 但属于无代码/无权重的占位框架仓库，或模型/数据权重处于受控访问（gated）且缺少公开许可证时，该事实**只能严格反映在 `openSource` 维度**，严禁据此跨维度扣减 `innovation`、`technicalRigor`、`experimentalSufficiency`、`clarity`、`impact`、`reproducibility` 或 `engineering`。

### 四、扣分归属与单次计分原则

每个理由必须引用至少一个 `[证据编号]`（如 `[A_METHOD]`、`[A_RESULTS]`、`[A_ARTIFACT_PROBE]`、`[SCORING_SOURCE_3/20]`），原文证据优先于分析转述，全文不同位置的证据都要兼顾。不能美化或反转已记录的事实；推测不能当成确认事实，“无法验证”不等于“技术错误”；信息不足时降低 `confidence`，只在直接相关的维度扣分。

同一个缺陷只能用于一个主要维度，严禁跨维度重复扣分：
- 缺少代码、模型权重、数据集或其他核心开源产物（含 `[A_ARTIFACT_PROBE]` 检出的占位仓库或受控权重状态）→ 仅归 `openSource`；
- 缺少超参数、训练配置、硬件规格、数据配比或复现步骤 → 仅归 `reproducibility`；
- 缺少支持结论的基线对比、消融、统计检验、听测协议/真人主观验证、压力测试或公平性控制 → 仅归 `experimentalSufficiency`；
- 结构组织、文字表达、符号一致性、表文口径矛盾、公式或图表可读性问题 → 仅归 `clarity`；
- 公开方法中的推导错误、方法与立论脱节、不合理假设、检索去重缺陷或系统逻辑漏洞 → 仅归 `technicalRigor`。

闭源、参数未披露和无法复现本身绝对不能用于 `innovation`、`technicalRigor`、`experimentalSufficiency`、`clarity`、`impact`、`engineering` 的扣分；`openSource` 不能扣复现步骤，`reproducibility` 不能再次扣闭源。代码会严格校验扣分归属，违规输出会被拒绝。

### 五、开源分与可复现分标准

`openSource` 只允许六个离散锚点值（0–10 量表）：
- `10.0`：对应类型的核心产物完整公开且官方文档完整（如安装、推理、微调或完整数据卡）；
- `8.0`：核心产物完整公开，但官方文档不完整；
- `6.0`：只公开部分核心产物（例如仅公开代码未公开权重，或仅公开子集数据）；
- `3.0`：原文明确承诺未来公开核心产物但当前尚未发布；
- `1.5`：仅提供可访问在线演示页面，没有核心代码、权重或数据公开（演示不能给 `3.0`）；
- `0.0`：完全闭源且无未来公开承诺。

按论文类型核对核心产物：模型/系统/方法/应用论文看代码与模型权重；`数据集与基准` 论文核心产物看数据集（及配套评测代码，不苛求模型权重）；`理论研究` 若公开可验证实验代码或数据集按上述核验，若仅在正文/附录公开推导与证明而无代码/数据仓库，最高计 `3.0`（代码会按理论研究类型自动控制开源加分幅度，不会扭曲总分）。

`reproducibility` 只评价开源链接之外的论文披露充分度（架构规格、训练数据与预处理、超参数、硬件与时长、评测协议和解码设置）：全部详尽可独立复现 `8.5–10.0`；大部分充分仅少量细节缺失 `6.5–8.4`；关键超参/数据/评测配置缺失较多 `3.5–6.4`；核心实现细节几乎未披露 `0.0–3.4`。仅有仓库或演示链接不能自动抬高本项。

### 六、证据画像与代码硬上限

在 `evidenceProfile` 中如实填写布尔与枚举字段：
- `ablationStatus`：`direct`（直接消融）、`partial`（部分消融，含模型/系统报告中覆盖关键模态/模式配对对照如音视频 vs 静音、指令 vs 思考但缺少后训练分阶段消融的情况）、`none`（完全无受控组件或模式对照）、`not_applicable`（不适用）。`multiComponentClaimed=true` 时不得填 `not_applicable`；`multiComponentClaimed=false` 时必须填 `not_applicable`。
- `targetEvaluation`：`public`（公开评测）、`internal`（内部评测）、`mixed`（混合）、`not_applicable`（仅允许理论研究或综述）。
- `engineeringEvidence` 须严格区分：
  - `measured_deployment`：包含真实的端到端延迟、吞吐、帧率、RTF、显存或功耗实测（仅此时允许 `deploymentMeasured=true`）；
  - `reusable_pipeline`：原文提供可核对的完整算法/训练/评测软件管线或公开可复现评测脚手架（**商用硬件物料清单 BOM、架构框图、离线固定网格模拟或现网仪表盘截图，若无实测延迟/功耗/吞吐且无公开可复用软件实现，一律不得填 `reusable_pipeline`，必须填 `claim_only`**！）；
  - `public_artifact_or_benchmark`：已公开可用的工具、模型或基准；
  - `claim_only`：仅文字叙述工程价值、未给实测 RTF/延迟与硬件规格的实时/流式声明、商用拼装 BOM、或仅有离线模拟指标；
  - `not_applicable`：不适用。
- `evidenceBoundary`：至少 20 个字，且至少直接引用一个包含在 `evidenceIds`（1–12 个不重复账本 ID）中的 `[证据编号]`。

代码会按 `evidenceProfile` 执行硬性分数上限（0–10 量表）：
- 多组件因果主张无直接消融（`ablationStatus=none`）：一般类型 `experimentalSufficiency ≤ 6.5`；模型报告/系统技术报告在公开或混合评测且含公开泛化评测时 `≤ 7.5`；
- 多组件因果主张仅部分消融（`ablationStatus=partial`）：一般类型 `experimentalSufficiency ≤ 7.8`；模型报告/系统技术报告在公开或混合评测且含公开泛化评测时 `≤ 8.5`；
- 仅内部评测且未报告样本规模：`experimentalSufficiency ≤ 6.0`；
- 仅口头声称工程价值（`claim_only`），或系统技术报告/应用研究仅内部评测且无部署实测（`deploymentMeasured=false && targetEvaluation=internal`）：`engineering ≤ 5.5`；
- 总分硬红线（超限直接拒绝）：`confidence` 不是“高”时总分不得超过 `8.4`；`multiComponentClaimed=true` 且 `ablationStatus=none` 且 `targetEvaluation=internal` 时总分不得超过 `7.2`。

校验反馈指出具体错误时，针对该错误修正，不重复上次无效理由。

### 七、输出格式（先写理由再定分）

只输出一个合法 JSON 对象，不加代码块围栏、前言、解释或结尾。键名与下方格式严格一致，任何层级都不能增删键。八个维度各出现一次，且每个维度对象中**必须先输出 `"reason"`、再输出 `"score"`**（先依据账本证据写清理由，再给出最终分值，杜绝先定分后凑理由）。`score` 是有限非负 JSON 数字（0.0–10.0，最多一位小数），`openSource` 仅使用 `0.0 / 1.5 / 3.0 / 6.0 / 8.0 / 10.0`。每个 `reason` 至少 20 字并引用具体 `[证据编号]`。下方示例仅用于展示 JSON 键名顺序、合法账本编号（注意局限节编号为 `[A_LIMITS]`）与极值分布范围，严禁照抄示例分数。

```
{
  "documentType": "方法研究",
  "confidence": "高",
  "evidenceProfile": {
    "contract": "scoring-evidence-profile",
```
