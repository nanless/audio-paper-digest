# API 论文解读写作要求

## 用途

事实修复和评分完成后，本阶段为博客生成完整的论文解读。机器摘要、标签、分数和评分理由仍保存在已有分析记录里，不在这里改写。

## 提示词内容

~~~
中文讲解与术语用法

【以下仅为写作规则和术语对照，不得复制到文章；只使用本篇原文涉及的条目】
- 讲清论文解决的具体问题、各部分分工、输入处理过程及作用和代价；按实际内容自然展开，避免固定栏目、反复总结和宣传语。
- 术语首次出现时解释实际作用，之后保持称呼一致。critic 按原文任务命名：价值估计用“价值评估模型”，学生分布分数估计用“辅助分数模型”；分类判别任务中的 discriminator 可称“判别器”。不得套用论文未涉及的角色。
- 术语对照：score＝对数密度对输入的梯度（适用于原文采用此定义时）；FID＝生成图像与参考样本的特征分布差异指标（参考集以原文为准）；patch FID＝在图像块上计算的 FID。Inception、Fréchet、KL、梯度和模型专名保持准确名称。
- 普通概念用自然中文，写出具体对象、处理过程和统计方式；必要专业术语可保留，首次说明含义。
- 正文只讲论文内容和有证据的结论。结构、来源校验、字数与修复权限仅供执行，不写进正文。事实、公式、数字、单位、指标方向、方法归属及逐字引文保持准确。

请为刚进入语音、音乐或音频领域的研究生写一篇中文论文解读。读者读完要能理解方法，能复述关键步骤，也知道实验结论在什么条件下才成立。用词要准确，段落要自然，不要夸大论文的价值。

论文标题：{title}
arXiv ID：{arxivId}

首次写作只依据下方论文原文和本次收到的官方原图。其他生成分析里的解释、评价和推断都不要沿用。修复时可以参考提供的草稿，但那只是待改的文字，里面的事实仍要回到原文核对。

带 ID 的论文原文证据：

{sourceEvidence}

代码校验反馈：

{validationFeedback}

上一版完整 JSON 草稿（首次生成时为“无”）：

{previousDraft}

本次代码检查的数量和长度要求：

{mechanicalContract}

上一版不是“无”时，就以它为底稿。先修反馈指出的局部问题，再看改动有没有波及已经通过的部分。标题别无故换，数字别重排，全文也别重写。提交时仍要输出完整 JSON，不能只给修改片段。

文章如何展开

开场先交代任务的输入、目标、必须保留的信息和输出。任务和已有研究路线讲完，再介绍方法的整体流程、组件与计算、训练或构造过程，然后解释实验条件和结果，最后讨论复现与结论。只讲论文实际研究的任务。教学例子要明确标成例子，不能添加没有来源的数值或效果。

每一节解决一个具体问题，标题就写读者要理解的那个问题、操作或机制。节数和正文汉字数按本次代码要求来，不必写满上限。这里数的是汉字，不是 JSON 字符数、英文长度或 token 数。篇幅留给计算过程、比较条件和复现细节，不要靠重复摘要、泛泛背景、反问或免责声明凑。再次讨论结果时，要带来新的对照、机制解释或适用条件。

句子长短随内容走，段落之间自然衔接。比喻确实有帮助时才用，而且要说清它对应哪个实际信号或组件，比喻本身不算证明。正文里不要出现本系统的论文评分、标签、机器摘要、评分理由、提示词、证据 ID 或内部检查状态，也不要讲写作流程。“本节同时出现两个术语”“表前需要”“为了满足表格列数要求”这类自述都不要写。JSON 示例里的说明只是字段示意，不能照抄进正文。

相关工作要按原文来比，比的时候输入、目标、监督和运行阶段都得相同，不能把类别上的差异写成同条件下的胜负。结尾回答三个问题：什么时候值得尝试，复现第一步做什么，还需要补哪项验证；关键超参数和信息条件要保留。代码开源、权重可下载、系统可运行是三件事，要分开说。本篇容易产生的误解用自然段解释，不要再重复摘要或通用问答。

术语、方法与公式

术语第一次出现时，先用日常语言解释，再给英文名或缩写；后文固定用同一种简称。介绍组合机制时，紧接着说清每个术语各指什么、怎么分工、为什么搭配、组合后多了什么作用。先沿着一个样本讲输入怎么经过各组件得到输出，再展开公式。代词要有明确的对象，解释结论之前先把它依赖的概念讲清楚。

方法部分要说明原文给的理由和已经验证过的对照。参数怎么冻结或更新、梯度经过哪里、监督来自哪里、什么时候重置，这些只能按证据写；原文没报告，就指出缺的是哪一项，不要从模型名称猜实现，也不要补写“拿掉后必然怎样”。论文没有训练时，先说清本研究没训练哪些模型，再解释实际的调用、搜索、标注、仿真或计算。无训练不等于确定性求解，参数冻结也推不出系统输出确定。

介绍公式时，先说明符号和输入，再解释计算目标以及原文明确的实现。原始目标、近似、停止梯度和优化步骤要分开；原文没说明的梯度路径不要猜。`READER_ARTIFACTS` 提供了完整原始 TeX 时，在方法部分挑至多 5 条关键公式；只有 1 条就选 1 条。每条公式用独占一段的 `[[FORMULA_<ordinal>]]` 表示，对应关系记在 `formulaBindings` 里。原式由代码显示，不要自己写展示公式。

实验结果与结论范围

实验部分按要回答的问题来组织：交代测量对象、比较方法、条件是否一致、指标方向和关键数字，再解释结果支持什么判断、有什么限制。证据够的话，数据和评测规则、主结果、消融或失败条件、训练与部署成本分别说明，并在核心结果之外展开至少两类本篇特有的细节。原文报告了定量主结果时，`result` 或 `ablation` 小节必须给出含必要基线和实际可运行策略的数字表，数据表或配置表不能顶替。比较时，原文实际可运行的策略都要保留。搜索选出的最优值、预先知道正确答案时得到的结果（oracle）、事后最优值要另行标明，不能当成实际部署时能够获得的提升。

数据、划分、采样、指标、聚合方式、统计方法和硬件预算都按原文交代。核对表格数字时，数据集、模型或基线、实验阶段、指标、单位和聚合对象要一起看；数值相同并不等于就是同一个指标。百分点和相对百分比是两回事。不同指标的差值不要塞进模型列，自动指标也不等于人工评价。原文表头、图注或算术互相冲突，就明确标出冲突，不要编一套划分或统计方式去解释矛盾。

每张表的前后都要有相邻的独立段落。表前说明比较问题、公平条件和指标方向，表后解释主要收益、具体代价或反例；字数按本次代码要求，段落数不固定，也不用逐行复述。至少在相应结果附近写一个未胜出项、负结果或尚未评测的范围。表格数量和宽度要符合要求，不能为了凑列数造无来源的列、混放不同条件，或删掉不利的基线。

写清论文直接报告了什么、证据只支持怎样的解释、哪些还只是推测。“报告”“显示”“支持”“可能”“待验证”这些词可以换着用，但不要每段都套同一个句式。缺证据不等于技术有错，相关也不等于因果。没有测量误判率、延迟或成本，就不能承诺它们会改善。训练资源、推理开销、输出帧率和实际延迟分开讨论；总体趋势推不到每一组结果或每一个步骤。

原图的选择与解释

只选本次真的收到像素、而且有教学价值的论文图，最多 4 张，也可以一张都不选。在同一小节里先写独立的读图说明，再放独占一段的图片占位符，之后用独立段落解释可见内容。`focusPoints` 给 2–4 个针对这张图的观察动作，段落长度按本次代码要求。不要自己输出图片 Markdown 或网址。没有像素时，只能说明来源后引用图注或正文，坐标、颜色、曲线和模块位置都不能猜。

先看图例，确认对象、条件和时间范围，分清分布曲线和单样本标记；颜色一样不代表对象一样。再看纵轴是原始指标、相对改变量还是改善量，结合指标方向判断好坏。曲线往下不能直接写成性能变差，末步结果也不能推广到全程。图里辨不清的数值或步数不要硬写；用原文补充说明时交代来源。

表格的来源与数字

`tableBindings` 按最终正文的表格顺序逐项对应。原表数字只走已有 `selection` 或完整原表声明 `completeTable`；不要把 DOM 数字抄入手写表后伪用 `source_quotes`。`selection` 仍只允许 `eligible:true`；`completeTable` 不选子集，只展示所指定原表的完整矩阵，是否可安全展示仍由原始 DOM、数字单位与正文检查决定。没有真实原表时，不得发明序号；全文连续原句中的数字可按已有 `source_quotes` 整理。不能计算差值、换算数字、补单位、猜表头或把来源校验失败说成作者没有报告。

表格数字和单位保留原文的写法、千分位和精度：44,000 不要改成 44000，100% 不要改成 100，19.44 不要四舍五入成 19。叙述数量用阿拉伯数字，数字和拉丁单位之间留一个空格。原文转换后出现字符粘连或 TeX 重复时，不要猜新数值，改用能核验来源的同实验表或清楚的连续原句。

四种表格记录方式

每张表只能使用以下一种结构，不混用正文形式或字段：
   - 完整原表声明（`reader-complete-table-declaration-v1`）：正文只在模型自己选择的合法小节中独占一段写 `[[TABLE_<tableIndex>]]`，记录恰好为 `{"tableIndex":1,"completeTable":{"sourceTableOrdinal":2}}`（序号按真实证据替换）。不写 Markdown、不填行列或数字、不附带 `selection`、`sourceType`、`cellBindings`、`sourceQuotes`。程序保留该原表全部行列、双层表头及合并单元格投影，生成既有 `artifact_table` 来源记录后照常严格核验。必须保留表格前后的比较问题、结果及限制；不能把标记放入 `tableMarker` 等未知字段。
   - `selection`：正文独占一段写 `[[TABLE_<tableIndex>]]`，不手写该表的 Markdown。记录只含 `tableIndex` 和 `selection:{sourceTableOrdinal,sourceRows,sourceColumns}`。行列从 0 开始编号，只能选择证据实际给出的行列；`sourceRows` 第一项是明确的表头行，之后是数据行，不得重复或越界。代码会据此生成原表、坐标对应关系和 SHA。占位符编号是正文表序，不是原表编号；不要附带手写值、`sourceType`、`cellBindings` 或 `sourceQuotes`。
   - `artifact_table` 是保留的兼容模式。在 `sections[].body` 里写完整 Markdown 表，不用 `TABLE` 占位符。记录恰好包含 `tableIndex,sourceType,sourceTableOrdinal,cellBindings,sourceQuotes`；`sourceType` 为 `artifact_table`，`sourceQuotes` 是空数组。每个 `cellBindings` 项恰好包含 `renderedRow,renderedColumn,sourceRow,sourceColumn` 四个坐标，逐格记录完整对应关系。
   - `source_quotes` 用来直接整理原文句子。在 `sections[].body` 里写完整 Markdown 表，不用 `TABLE` 占位符。记录恰好包含 `tableIndex,sourceType,sourceTableOrdinal,cellBindings,sourceQuotes`；`sourceType` 为 `source_quotes`，`sourceTableOrdinal` 为 `null`，`cellBindings=[]` 必须为空。`sourceQuotes` 是逐字连续原句组成的字符串数组。`value`、`quoteIndex`、`renderedText` 这类字段不能发明；引用只用来核验来源，不生成表格。
   `source_quotes` 里的原句必须覆盖每个数字单元格的全部数字和单位。原文数值带单位时，单位留在同一单元格，不要拆成独立列再跨列补全；原文是裸数值就不要自己添单位，指标单位按原文写在表头或相邻说明里。格式示例：正文 `| 条件 | 指标 | 基线 | 本方法 | 比较对象 |\n| --- | --- | --- | --- | --- |\n| [原文条件] | [指标名] | [原值及单位] | [原值及单位] | [原文对象] |`；来源记录 `{"tableIndex":1,"sourceType":"source_quotes","sourceTableOrdinal":null,"cellBindings":[],"sourceQuotes":["[覆盖这些数字与单位的原文连续句]"]}`。方括号中的文字只是格式示例，不能照抄。正文不再放 `TABLE` 占位符。

记录与正文的对应关系

每张正文表都要有 `tableBindings` 记录，每条展示公式都要有 `formulaBindings` 记录，SHA 和 DOM 单元格对应关系不要自己填。原文确实没有相应证据时，数组可以为空；自行整理的表仍要用原句说明来源。图和公式的正确编号、概念解释占位符及对应关系都要保留。修正一处事实时，不要重排无关章节或重新编号。

只输出一个合法 JSON 对象，不要 Markdown 代码块、前言或结尾。字段必须精确如下。示例标题和看图步骤只说明写法；只有论文确实研究相应任务、本次原图确实包含相应路径时才照用，其他论文按自己的内容填：

  "readerTitle": "语音与文本如何共同支持音频检索",
  "oneSentenceThesis": "用一句话写清问题、方法选择、最强证据和主要代价",
  "conceptBridges": [
    {
      "terms": ["术语 A", "术语 B"],

      "explanation": "[直接解释术语 A 与术语 B 的分工、搭配理由和组合机制，不照抄此占位说明]"
    }
  ],
  "figurePlacements": [
    {
      "figureOrdinal": 1,
      "targetKind": "method_overview",
      "marker": "[[FIGURE_1]]",
      "focusPoints": [
        "先沿输入到输出的箭头看主路径",
        "再比较语义分支与声学分支在哪里汇合"
      ]
    }
  ],
  "tableBindings": [
    {
      "tableIndex": 1,
      "selection": {
        "sourceTableOrdinal": 1,
        "sourceRows": [0, 1, 2],
        "sourceColumns": [0, 1, 2, 3, 4]
      }
    },
    {
      "tableIndex": 2,
      "sourceType": "source_quotes",
      "sourceTableOrdinal": null,
      "cellBindings": [],
      "sourceQuotes": ["全文中逐字连续、覆盖表内关键数字与单位的原句"]
    }
  ],
  "formulaBindings": [
    {
      "formulaOrdinal": 1,
      "targetKind": "component",
      "marker": "[[FORMULA_1]]"
    }
  ],
  "sections": [
    {
      "kind": "background",
      "heading": "音频检索的输入、候选与评价条件",
      "body": "完整、连续、面向初学者的段落"
    }
  ]
}

`sections` 必须包含 12–18 个小节，起草时建议安排 14–16 节。输出 JSON 前实际数一次数组项数；少于 12 节或超过 18 节都不能输出。`kind` 可以重复，但重复项也计入小节总数，总数不得超过 18。同类组件、结果读数或消融条件过多时，把它们合并为同一小节中的自然段；不得为压缩节数删掉证据、数字、单位、比较条件、来源记录或结果限制。不要把表格读数和结果解释机械拆成两个小节。`kind` 只能按需要从以下集合中选择，整体按列表顺序展开：

background / related_work / problem / method_overview / component / training / experiment_setup / result / ablation / limitation / reproduction / synthesis

必须覆盖 `background`、`related_work`、`method_overview`、`training`、`experiment_setup`、`result`、`limitation`、`reproduction` 和 `synthesis`。`training` 不代表一定有神经网络训练。没有训练时，在该节明确说明，并讲清 PCA/SVD、优化器、规则、检索、仿真或已有模型推理的实际计算过程。理论、综述和数据集论文可以解释各自的构造、证明、检索或标注流程。

`conceptBridges` 数量按本次代码要求，每项 `terms` 2–4 个不同的真实论文术语。`marker` 按数组顺序写成 `[[CONCEPT_BRIDGE_1]]`、`[[CONCEPT_BRIDGE_2]]` 等，在对应 `sectionKind` 的正文里独占一段。`explanation` 里全部术语都要出现，说明各自分工、为什么搭配、组合起来多了什么意义，不能只写“二者结合效果更好”。代码会在占位符处显示这段解释。

`figurePlacements` 可以为空，最多 4 项。只能选请求末尾“模型本次真正收到像素”的论文图；只有 `READER_ARTIFACTS` 图注、没收到像素的图不能选。不要为凑数量加入重复曲线、界面截图或装饰图。每个 `figureOrdinal` 只能出现一次。`marker` 写成 `[[FIGURE_<figureOrdinal>]]`，在目标小节正文中独占一段。`targetKind` 等于实际包含占位符的小节 `kind`；不要照抄示例里的 `method_overview`，结果曲线通常放在 `result` 或 `ablation`。占位符前一段是完整的读图说明，后一段解释实际可见的内容。`focusPoints` 给 2–4 个针对可见元素的观察动作。代码会在占位符处显示看图步骤和官方原图。

`tableBindings.tableIndex` 从 1 开始，对应最终正文的表序。原表可用性及四种结构遵守上方要求。选择模式的 `sourceRows[0]` 必须来自 `TABLE_<ordinal>_HEADER_ROWS` 明确列出的表头行；`SHAPE` 给出矩阵尺寸，`role: unknown` 表示科学用途还没判断。作者或机构表不能当结果表，只选实际呈现的行列，因预算省略的内容不要猜。手写坐标记录里，`renderedRow=0` 是表头，`renderedRow=1` 是第一条数据行，分隔行不计数；`sourceRow/sourceColumn` 是原矩阵从 0 开始的坐标。`rowspan/colspan` 覆盖的位置仍使用被覆盖的矩阵坐标，代码会找到真实 DOM 单元格。每个显示单元格必须恰好对应一次。

`formulaBindings` 只能选 `READER_ARTIFACTS` 的 `FORMULA_ORDINALS_AVAILABLE` 里明确列出、完整恢复且带原始 TeX 的公式。清单是 `[]` 时，正文不能出现 `FORMULA` 占位符，并须输出 `"formulaBindings": []`。`marker` 必须是 `[[FORMULA_<formulaOrdinal>]]`，在 `targetKind` 小节独占一段且只出现一次。代码会显示原始 `\[TeX\]` 并记录 DOM SHA。
