# Manual 全文分析成稿规范

此模板只供 Codex/人工编辑在不调用项目 LLM API 时撰写 `manual_analysis_records`。它不由模型接口执行，但其 SHA-256 必须进入 Manual spec，使规则变化能够使旧 spec 失效。

```text
你正在基于受控的论文完整全文撰写一篇可直接发布的中文技术解读。Manual 不是摘要扩写，也不是把若干字段凑到长度门槛；最终成稿必须达到标准 API 深度分析的读者可见质量。

零、执行隔离与研究者选题
- 一篇论文只能由一个独立 paper subagent 撰写；所有论文理解、正文撰写、评分、可读性复核和最终单页审查 subagent 固定使用 `gpt-5.6-terra`、reasoning effort `high`，不得用 Sol 代写逐篇正文。主 Agent/Sol 只负责队列、代码、确定性门禁、组装和发布。该 subagent 的上下文只能包含本篇 metadata、全文、图片和本篇记录，禁止同时处理第二篇论文。每篇另由不同的 Terra-high 评分/review subagent 做终审；新 record 在 `paperSubagent` 中记录 `model` 与 `reasoningEffort`。
- 新正文必须按 `fresh-authoring-v1` 从受控论文证据冷启动。author 只可读取本篇 metadata、全文 source snapshot、ArtifactIndex、原论文图表/公式、空白 record schema、固定写作 prompt 和编辑契约；禁止读取历史 analysis、旧 `readerArticle`、任何 `article.md` / `post.md`、博客 Markdown/HTML、已填写 quality、previous draft 或历史 review prose。旧正文不得进入生成、修订或质量回归，也不得改名伪装成 metadata/evidence。
- review 要求修正时，revision subagent 只能读取同一份原始证据和结构化 findings（issue ID、证据引用、修改要求），从空白生成完整替换稿；禁止让 reviewer 提供可直接粘贴的替换段落，禁止在上一稿上移动、润色、扩写或补段。交稿须记录允许输入的 realpath、kind 与 SHA，并声明 `prohibitedProseInputs=[]`；缺失或多出输入即失败。
- 开写前先站在音频研究者视角回答：这篇论文真正值得学的 3–6 件事是什么？读者要复现或判断贡献，必须知道哪些输入表示、音频路径、组件数据流、训练冻结策略、数据规模、评价协议、强基线、关键数字、消融/负结果和部署边界？
- 每篇提交 `researchBrief`：中心问题、7–12 项 `mustExplain`、2–8 项 `compress`、1–8 项 `omit`、3–6 条 takeaways、证据画像和显式推导。每个 mustExplain 同时绑定全文原句和最终正文局部；低价值内容只能在 compress 对应短句中出现一次；omit 声明的模板或背景句不得进入成稿。
- `mustExplain` 至少覆盖 task_boundary、audio_path、architecture、training、evaluation、reproduction、limitations；实证论文另覆盖 ablation_or_negative。系统/模型报告必须明确区分“继承组件、本文新增组件、训练系统、尚未验证的主张”。
- 先建立全文 inventory：贡献、模型模块、训练阶段、数据规模、全部结果表、消融、算法和图片逐项登记为详讲/压缩/略过。不能因为第一张表或第一张架构图已经够写，就停止阅读后续表格和附录。

零点五、先写编辑蓝图，再写正文
- 新 record 必须在 `researchBrief.editorialPlan` 中先提交 v2 蓝图：`readerTitle`（中文观点式标题）、`oneSentenceThesis`、`governingTension`、4–7 个递进 `readerQuestions`、2–4 个互不重复的 `evidencePillars`、4–8 个论文特有 `sectionPlan`。中心矛盾要写清两端分别需要什么、为何相互拉扯、论文把共享与分工放在哪里；禁止用“现有方法不足，本文提出框架”代替。
- v2 蓝图是发布契约，不是备忘录：除 canonical 固定章节外，必须提交 `editorial.readerArticle` 作为最终博客的“深度解读”正文，长度 2400–24000 字，只使用与 `sectionPlan` 同序、同名的 `###` 论文特有小节。每个 `readerQuestions` 的 `answerQuote`、每个 `sectionPlan` 的 `anchorQuote`、每个 `evidencePillars` 的 `readerQuote` 都须原样落入这篇文章；标题、引语或证据柱未真正进入成稿会阻断组装。
- 开头先给一句可证伪的核心判断，再用小表或等价紧凑对照解释技术冲突。系统/模型论文先给完整输入→表示→组件→输出数据流，再拆核心模块；每个模块都回答输入、输出、职责以及为何不由相邻模块承担。可用 ASCII 流程图帮助建立心智模型，但不能用图替代解释。
- `readerQuestions` 必须形成递进：为什么需要它→如何工作→为何这样训练/求解→能做什么→哪组实验最能证明→哪里不成立。正文小节标题应直接表达读者问题或判断，不得机械照搬论文目录、Table 编号或固定字段名。
- `evidencePillars` 按主张而不是表号组织实验：目标任务、公开泛化、消融/负结果、效率/部署中选择 2–4 柱。每柱只保留最强或最有代表性的比较，同时写“该证据支持什么”和“不能推出什么”。
- 图表必须是论证节点：总览图负责心智模型，机制图解释关键分工，结果图或失败图支撑证据/边界；同一问题下的重复图必须删除。训练阶段、能力地图或多任务输入输出适合用紧凑表格时，应优先用表格降低段落负担。
- 若选图，`readerArticle` 必须原样包含该 HTTPS 图片 Markdown、`imageInsertions.lead` 与 `imageInsertions.explanation`，并放在相应论证节点；canonical 的图片插入计划不能替代发布正文中的图文邻接。

一、论证主线
- 主要内容默认达到参考稿式标准：详细清楚、图文并茂、逻辑清晰、文字翔实、数据和表格清晰。这里的“翔实”指关键机制、训练和证据完整，不是增加背景史、逐表抄录或重复数字。
- 核心摘要用 5–8 个完整句子回答：研究问题、既有缺口、方法主线、关键证据、实际意义、主要边界。句子之间必须有因果或转折推进，不能逐字段复述。
- `editorial.review` 是发布页和汇总页中置于核心摘要之前的“毒舌点评”，不是情绪化标题党。必须恰好两段、总长 180–700 字、每段至少 70 字：第一段明确评价论文真正做对且证据最强的一点，第二段明确写最该泼冷水的一点——缺少的对照、未被覆盖的条件、不能外推的结论或实现代价。两段分别至少复用 `readerArticle` 里一个论文特有的机制、实验或边界短语，供 assembler 审计其确实来自深度解读；要尖锐但准确，禁止人身化、嘲讽作者、只夸不批、只批不夸，以及“亮点一是/短板是”式模板句。
- canonical 的六个核心章节仍用于事实、评分和图片门禁，但它们不是最终博客的固定版式。最终博客保留题目、链接、标签、评分、核心摘要、开源资源与文末证据；中间一律以 `readerArticle` 连续组织“问题→机制→训练/取舍→能力证据→反证/边界→结论”，不得再以“方法概述和架构”“核心创新点”“实验结果”“细节详述”“局限与问题”等栏目标题切碎文章。同一核心数字事实最多在摘要和深度解读各出现 1 次，禁止换一种说法重复。
- 同一个机制例子、推导或边界说明最多完整讲 1 次。摘要可以一句点名，其他章节用指代推进，不得把同一个帧率示例、同一开源链接或“长上下文不等于实时”之类限制在 3 个以上章节反复改写。
- 方法概述至少包含 5 个独立段落，依次讲清输入与表示、模块职责、数据流/并行分支、训练目标与阶段、推理输出及设计取舍。理论/数据集论文应使用与文档类型等价的对象、构造、证明或标注流程。
- `editorial.method` 与 `editorial.innovations` 是面向读者的最终完整章节，不是追加在短字段后的扩写。必须在一条连续叙事中吸收 `method/method2/method3/innovations` 的事实职责，但不要再次复述这些短字段；短字段仅用于证据审计和阶段 provenance。
- 核心创新写 3–5 项。每项都必须同时包含既有方法的具体限制、本文改变的机制、支持该机制的证据，以及不能外推到何处。禁止只列组件名。
- 实验结果必须绑定数据集、比较对象、指标方向、精确数字、消融或负结果和实验条件。全文有实验表时至少转写一张可读 Markdown 表；优先形成“主结果/效率”与“消融/失败案例”两层证据，而不是把论文压成三列结论卡。每张表至少有方法、数据集或设置识别列，指标名写明 `↑/↓`，单元格保留可核对数字；禁止用“结果、观察、含义、说明、结论”等叙述列冒充指标，也禁止把异构指标拼成总分。
- 系统/模型报告不能只摘最顺手的一张内部表。至少回答：目标域任务是否真的改善、公开基准是否支持核心机制、同主干是否有收益与退化、组件是否有直接消融、效率/实时主张是否有测量。若某项不存在，必须明确 `notEvaluated`，并同步限制评分。
- 表格必须嵌入论证：表前先提出该表要回答的具体比较问题并交代保留口径；表后只解释最关键的差异、原因或代价及不能外推的边界。不得孤立摆放数据卡，不得按行逐字复述表格。
- 实验按核心主张或能力族分小节，不按论文 Table 1/2/3 顺序翻译。每节遵循“问题→代表性对照与数字→支持的结论→反证/未胜出项→证据边界”；跨任务强结论至少写出 1 个未占优、未验证或不可直接比较的限定。禁止把局部第一概括成全面 SOTA。
- 每篇另写至少 3 条结构化 `resultClaims`，逐条给出 `datasetOrSetting`、`splitOrCondition`、`method`、`baseline`、`metric`、`value`、`unit`、`direction` 和全文连续 `sourceQuote`。每条还必须提供 `sourceBindings` 与 `readerBindings`：两者都必须且只能包含上述 8 个语义字段；值是人工选取的连续证据片段，至少 2 个非空白字符。`sourceBindings` 的每段必须存在于该条 `sourceQuote`，`readerBindings` 的 8 段必须共同落在实验结果的同一个自然段、句子或完整 Markdown 表中，不能靠数字在全章节别处偶然出现冒充本条证据。同一短片段最多供 3 个字段复用，禁止 8 字段机械复制整句。`direction` 只允许越高越好/越低越好（含 `↑`/`↓` 与等价英文）、描述性、绝对值关联强度或带理由的未报告。正文未报告的字段只能写成 `{ "notReported": true, "reason": "至少 8 个非空白字符的原因" }`，并为两套 binding 选取缺失、定性或负面证据；不能使用裸 `notReported`，也不能与推断数字混写。实证论文至少 1 条 claim 必须包含可核对数字；理论或纯定性论文若不足 3 条，必须用 `resultClaimsException` 绑定全文说明。
- 每条 `resultClaims` 还必须提供 `readerNarrative`：40–360 字的完整自然句，原样落在同一实验段或表格说明中，交代设置、方法、强基线、指标方向、数值、比较关系和边界。禁止把 `FireRedAudio，英语 RP，基线，ACC，70.3%` 这类 schema 字段串直接留给读者；若异构指标难以放入自然句，应先做同质比较表，再在表后写一句解释。
- 当前系统/方法记录至少 4 条 resultClaims，并增加 `evidenceScope`、`sourceGroup`、`baselineType`。claims 至少来自 2 个独立表/实验组，同组不得超过一半；至少一条使用同主干或强外部基线，不能只拿 4B/9B sibling 互比。若论文有公开泛化或直接消融，必须分别覆盖 public_generalization 与 ablation_negative。
- 细节详述逐项覆盖数据/划分、目标或损失、优化与训练日程、关键超参数、硬件、推理/解码和稳定化技巧。论文未披露的项目明确写“未说明”，不得按常见实现补造。
- 局限分为“论文证据直接支持的边界”和“进一步审视”。前者只写作者或实验直接支持的限制；后者写审稿视角的缺失对照、统计、外推、复现或部署风险。
- 结尾必须回扣开篇中心矛盾，概括论文选择带来的能力与代价；不得再次罗列分数或把摘要换词复述一遍。事实、作者声明与编辑推断要分层，机制归因或泛化判断没有直接实验时必须写成“合理解释/推断”。

二、评分
- 八个维度各自给出论文特有证据和扣分边界。每条理由必须能脱离维度名称独立成立。
- 禁止“创新维度认可……”“方法维度有……”“综合维度体现……”等模板句。
- 清晰度只评价组织、符号、公式、图表与表达；可复现性只评价数据、配置、超参数、硬件与步骤；不得错位。
- 开源只计算本文直接交付的代码、模型、数据或 Demo，第三方依赖和未来口头承诺按固定锚点处理。
- `scoringReasons` 必须人工显式给出，禁止由摘要、创新或局限字段回填。评分 subagent 必须与正文 subagent 不同，并逐维绑定 evidence IDs。
- 10 个兼容阶段都必须在 `stageReviews` 中独立记录 decision、attempts、evidenceIds、连续 sourceQuotes、issues 和 conclusion；decision 只能是 manual_verified、repaired、not_needed。禁止由组装器自动选择通用全文 chunk，也禁止把全局 audit.attempts 复制给全部阶段。repaired 必须保存至少 1 个实际问题和至少 2 次尝试。
- 无直接消融的多组件系统，实验充分性不得超过 1.2/1.5；只有部分消融不得超过 1.3/1.5。目标域评测为内部数据且不报告样本规模时，实验充分性不得超过 1.2/1.5。没有真实延迟、吞吐或资源测量时，工程价值不得超过 1.0/1.5。置信度不是“高”时总分不得超过 9.0；缺消融且主要依赖内部评测时总分不得超过 8.5。

三、图片与技术表达
- 逐项审阅全文 manifest 中通过安全过滤的论文图。优先架构、流程、核心实验和关键失败案例；最多 4 张。资助方 logo、站点 chrome、作者头像、许可图标和无语义碎片必须拒绝。
- `figureReview` 必须覆盖 manifest 的每个图片 URL，不只是入选图。逐图写 figure number、caption identity、select/reject、理由；选图至少列 2 个从像素直接可见的事实。当前发布器只会嵌入完整原图并提供可点击原分辨率链接，不会真正物化 crop/panels 派生资产；因此新记录的 select 项只能声明 `renderPlan.mode=full` 且必须在手机缩略图或点开原图后可靠核读。若理解关键事实必须依赖尚不存在的裁图/分 panel 资产，必须 reject，禁止只写一个不会执行的裁图计划冒充移动端可读。不同 URL 复用同一 caption 时必须人工确认图号。
- 只要选择图片，就必须在同篇 record 中显式给出与 `selectedImageUrls` 等长、同顺序的 `imageInsertions`；禁止省略选择后由代码自动生成邻文。每项包含 `url`、`section`、`anchorQuote`、`conclusionQuote`、`lead`、`explanation`。
- `anchorQuote` 必须唯一命中目标章节的一段正文；`lead` 承接该段具体命题并提出阅读任务（核对分支、比较曲线、追踪输入输出等），且复用至少一个论文特有术语。`conclusionQuote` 必须唯一命中同节中不早于锚点的后续论证或结论段；`explanation` 先写图中可见结构/曲线/色块/样例，再回扣该结论的条件或边界，并复用至少一个论文特有术语。
- 禁止“逐项对照”“不代表额外阶段”“不替代未报告配置”“只支持对应设置、不能外推”等跨论文模板。图片必须插入最相关正文段落之后，保留完整图注 alt；不得只把 URL 堆到章节末尾，也不得形成与前后段无逻辑关系的孤岛。
- 图前、图后和表前说明必须随论文内容自然改写；禁止把“关键比较问题是：”“下图用于核对”“证据边界在于”“下一段将解释”当作固定句首，禁止用“1. 是……”批量展开创新点。段落不得以分号结束，也不得出现“具有有”“尚尚”或“但……，但……”这类拼装痕迹。
- 若全文 manifest 有合格论文图，Manual 必须逐图明确选择或拒绝；不能省略 `selectedImageUrls` 让代码代选，也不能用空数组绕过审查。
- 源文中对理解方法或实验必要的公式，应使用 `$...$` 或 `$$...$$`；不需要公式的论文不得为了形式完整而编造。

四、事实与编辑质量
- 所有数字、方向、数据集、基线、资源状态、作者机构和限制均须由绑定全文或明确仓库证据支持。
- 核心正文中的每个精确数量、模型规模、时长、帧数、频率、设备型号和科学计数法，都必须能在本篇全文、显式外部证据或 `derivedFacts` 中定位；不得从同批相邻论文带入罕见数字或实体。显式推导必须保存公式和参与推导的原文句。
- 所有实验数字、样本量、模型规模、时长、频率、百分比、比例、名次、超参数和置信区间统一使用阿拉伯数字；中文数词只用于序数、固定词组和不精确修辞数量。禁止先在表中写 `128`，再在正文写“一百二十八”复述。
- 每条结果句必须就近绑定数据集或设置、比较方法、基线、指标、数值、单位、方向和必要条件；不能让读者回到上一段或表格猜单位。术语首次出现写中文释义与官方英文/缩写，后文固定一种简称，并在中文与 ASCII 技术词之间保留空格。
- 不得出现人工审计、证据块、prompt、manual_complete、评分锚点等流程元话语。
- 不得在不同章节复制同一长句；相同事实再次出现时必须承担新的论证作用，并保留比较对象和条件。
```
