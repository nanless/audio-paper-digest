# 单篇论文分析提示词

## 用途

主模型依据文本完成结构化分析。配置了副模型时，后续由副模型根据实际图像补充说明；未配置时，图片只保留候选信息，不自动插入正文。

## 调用方式

代码通过 `loadPrompt()` 读取第一个代码块，把占位符替换成论文标题、作者、类别、arXiv ID、本次可用的原文和标签选项。`{hasFullText}` 说明本次输入是全文证据还是摘要；`{tagPromptText}` 提供当前可用的标签及其定义。

## 提示词内容

~~~
请依据下方文本分析这篇论文，核对研究问题、方法、证据和结论，并按后面的格式用中文输出。{hasFullText}

论文标题：{title}
作者：{authors}
类别：{categories}
arXiv ID：{arxivId}
链接：https://arxiv.org/abs/{arxivId}

{textForAnalysis}

以下 13 个一级标题必须按顺序各出现一次，不增删、重复，也不把同名标题嵌入正文。输出直接从 `## 评分` 开始，不加问候、前言或任务说明。无法从输入确认的信息，写“未说明”“未提供”或“论文中未提及”，不根据常识、作者或机构声望、邮箱、外部网页和历史记忆猜测。

正文使用完整句子和自然段落，句子长短可以变化。核心摘要解释问题、方法、主要结果及限制，方法解释组件与数据流，创新说明与已有方法的差异。实验展开比较，细节说明复现条件，局限集中讨论尚不能成立的结论。同一核心数字最多在摘要和实验各出现一次，不在其他章节换说法重复。

精确实验数值、样本量、模型规模、时长、频率、百分比、比例、名次、超参数和置信区间使用阿拉伯数字。中文数词只用于序数、固定词组或非精确描述。术语首次出现时给出中文解释和官方英文名或缩写，后文采用固定简称，中文与英文之间留空格。不要重复套用“关键比较问题是”“下图用于核对”“证据边界在于”“下一段将解释”等通用句首，不把字段串拼成正文，不使用双重编号或以分号结束的段落。

写作风格，正文各章节都要遵守。面向第一次接触这个方向的读者，用平实的中文写清事实、条件和依据，不预设他们熟悉术语或研究惯例。

不要这样写：

* 八股连接词。“首先、其次、最后、总之”反复出现，“不是 A，而是 B”“这就是……的本质”。有真实的先后顺序就直接写出来，没有顺序关系就不要连接词。
* 元叙事标签。给每节加“人话版”“一句话总结”“看什么”“记住”这类固定的口头标签。直接写事实或写清两段之间的关系。
* 工作流话术。“本轮、排期、交付、后续迭代、闭环验收”。只写读者需要理解或核对的内容，编辑过程不进入正文。
* 产品与咨询黑话。“拉通链路、推动落地、赛道红利、能力底座、核心抓手、组合拳、性能天花板、方案兜底”。改写成具体的模块、指标、限制，或失败之后要做的处理。
* 过度拟人和伪口语。“算法把频谱吃进去”“把掩码喂给”“网络接管”“系统翻车”“掉链子”。改写成“网络输入语谱图”“用掩码估计协方差”“条件数增大后求逆误差上升”。
* 夸张口语与竞技化标签。“踩坑、命门、崩塌、通吃、露馅、打榜”。直接写失效条件、响应变化或公开评测目标。专业含义明确的“秩亏”“零陷”不属于这一类。
* 营销式断言。“工业默认、唯一正确、彻底消除、任何场景都适用、直接碾压”。写明数据集、条件、假设和比较对象；证据不够就降低结论强度。
* 命令读者。“记死、不许质疑、照抄”。改成说明建议、适用条件和出错后果。
* 不必要的中英混杂。“调 trade-off”“跑 baseline”“pipeline 已 ready”。首次出现写“中文名（英文全称，缩写）”，后文用中文或缩写。

可以保留的用法。真实步骤里的“先、再、最后”，单个“总之”用来收束一段也可以；已经给出中文名和英文全称之后的专业缩写；代码、命令、API 名称和没有稳定中译名的正式术语；由公式或标准给出数值的“上限”，表示可复现对照的“基线”；表示信号或数据依次经过哪些模块的“链路”。“不是 A，而是 B”、类比和提问句可以偶尔用，但如果删掉不损失信息，或者在相邻段落里重复出现，就改写。

写结论时的要求。定量结论要写清条件，写成“在……条件下，……约为……”，不写“显著提升”。因果关系要写清依据，写成“因为……，所以……”，不写“得益于……”。用类比时说明它只解释哪一部分、边界在哪里，不让类比代替机制说明。

## 评分
单独写总分，格式为 `X.X/10`。

## 机器摘要
以下 17 个键必须各出现一次，不能增加其他键。每行使用 `key: value` 纯文本格式，不加列表符号，不在键或值中使用加粗等 Markdown 标记。

```
document_type: 方法研究 / 系统技术报告 / 模型报告 / 数据集与基准 / 综述 / 理论研究 / 应用研究
rank_bucket: 前10% / 前25% / 前50% / 后50%
innovation: X.X
technical_rigor: X.X
experimental_sufficiency: X.X
clarity: X.X
impact: X.X
open_source: X.X
reproducibility: X.X
engineering_score: X.X
confidence: 高 / 中 / 低
primary_task_tag: #标签
primary_method_tag: #标签
sota_claim: 是 / 否 / 未说明
has_code: 是 / 否 / 未说明
has_model: 是 / 否 / 未说明
has_dataset: 是 / 否 / 未说明
```

`document_type` 按论文主要贡献选择示例中的一个类型。类型用于判断应采用哪些证据，不直接加分或扣分。`rank_bucket` 只能使用示例中的四档，`confidence` 只能写“高”“中”或“低”。`sota_claim` 表示论文是否明确声称达到当前最佳结果；它与 `has_code`、`has_model`、`has_dataset` 都只能写“是”“否”或“未说明”。

八个分项分别是创新性、技术严谨性、实验充分性、清晰度、影响力、开源、可复现性和工程/实践价值，满分依次为 2、1.5、1.5、1、1.5、1.5、0.5 和 1.5。分项必须是非负数字，四舍五入保留一位小数，不超过对应满分。评分理由使用相同分值。八项满分合计 11，代码会求和并封顶 10，保留一位小数。

开源分只允许 `0.0 / 0.2 / 0.5 / 1.0 / 1.2 / 1.5`。主任务和主方法标签分别从下方标签选项中的 `facet=task` 和 `facet=method` 选择，使用状态为 `active` 的首选名称，不能用方法名、arXiv 类别或一段描述代替任务标签。

### 评分依据

先判断论文在同期同方向工作中的位置。前10%对应突破性工作，前25%对应明显优秀，前50%对应合格到良好，后50%对应问题较多。排序档位与总分保持一致：总分至少 9.0 为前10%，至少 7.5 为前25%，至少 5.5 为前50%，低于 5.5 为后50%。代码会根据评分理由重算总分和档位，不在理由中重复计算。

评分应有区分度，不故意压低。9.0 分以上用于具有里程碑潜力的工作；8.0–8.5 分用于在重要问题上作出扎实贡献、有明确影响力的工作；大多数扎实但非突破性的论文应落在 6.0–7.5。工程组合是否有创新，要看组合产生了什么新认识、新能力或可验证的提升，不能只因使用已有技术就扣分。

先明确论文声称解决什么，再判断实验、证明、系统测试或数据分析是否足以支持这些结论。不同类型采用不同证据：方法研究看代表性基线、消融、跨数据集泛化和统计分析；系统技术报告和模型报告看端到端质量、延迟、吞吐、成本、规模、压力测试、公平对比和失败案例，论文声称某个组件带来提升时，才要求该组件的消融证据；数据集与基准看覆盖范围、标注质量、泄漏控制、评测协议和基线；综述看检索方法、覆盖范围、分类体系和综合分析；理论研究看证明、假设、边界条件和反例；应用研究看真实场景、外部验证、用户研究和部署约束。

同一个缺陷只用于一个主要维度的扣分。缺少代码、模型、数据或核心产物归开源；缺少超参数、训练配置、硬件和复现步骤归可复现性；缺少支持结论的对比、消融或其他验证归实验充分性；写作、符号、图表和组织问题归清晰度；推导错误、不合理假设或算法逻辑漏洞归技术严谨性。不能因一处信息缺失在多个维度重复扣分。“无法验证”不等于“已经证明错误”；信息不足时降低 `confidence`，只在直接相关的维度扣分。

本分析面向语音、音乐和音频研究者。核心贡献不属于这些领域时，即使技术优秀，影响力通常不超过 0.5。不能仅因方法可能用于音频就给高影响力分。只有音频是核心实验对象、评测任务或应用场景时，才正常评价其领域影响。小众、垂直、特殊人群、病理语音和动物声音等题材的创新性、技术严谨性正常评分；受众较窄的工作的影响力通常不超过 0.5，实验充分性中与数据集通用性直接相关的部分可酌情扣分。

系统级能力、软硬件协同、规模化方法和工程组合产生的新能力可以计入创新；只有功能宣传而没有可检查证据的内容不能获得高创新分或高实验分。论文类型不提供固定加分、保底或豁免。闭源系统如实扣开源和可复现性，纯理论工作没有工程应用时，工程/实践价值可以为 0。适用的证据要求也要体现在摘要、方法和实验中，原文缺少的证据明确说明，不补造。

各维度采用以下标准：创新性评价问题、方法和关键认识的新颖程度，以及与已有最佳方法的区别（2 分对应突破，1.5 分对应明显创新，1 分对应小改进，0.5 分对应微小改进）；技术严谨性评价公开的推导、证明和算法或系统逻辑，检查假设和边界（闭源或未公开配置本身不能作为技术错误）；实验充分性评价适用证据能否支持结论（不机械要求所有论文提供同一种消融）；清晰度评价组织、符号、公式解释、图表和文字（实现细节不足导致无法复现时，归可复现性）；影响力评价对音频领域的推动、后续研究价值和实际用途（重要基准上的最佳结果、大规模数据或工具、长期问题的解决可以支持高分，但不能根据作者或机构声望加分；适用范围很窄的小改进或非音频核心工作只得低分）；开源评价相应核心材料（模型论文看代码和权重，数据集论文看数据，工具论文看代码，理论研究看正文和附录是否公开核心证明、推导、假设及边界；核心材料开放且文档完整为 1.5，开放但文档不完整为 1.2，只开放部分核心材料为 1.0，承诺未来开放但尚未发布为 0.5，只有在线演示、没有核心材料为 0.2，完全关闭且无承诺为 0）；可复现性评价开源之外的说明是否足够，包括训练、超参数、硬件、实验配置和步骤（全部充分为 0.5，大部分充分、少量缺失为 0.3，关键配置大量缺失为 0.1，核心方法和配置几乎没有为 0）；工程/实践价值评价系统流程、可复用实现和实际测量（完整的生产系统、标准化流程或基准建设有充分细节和组件可供使用时为 1.5，系统设计或训练部署流程有明确参考价值时为 1.0，零散实现技巧、优化经验或工程取舍为 0.5，没有工程应用价值为 0。系统报告、模型报告和基准工作应认真评价这一维度，不因属于理论或方法论文而预设高分）。

参考总分区间：9.0–10.0 表示突破性贡献或里程碑候选；8.0–8.5 表示重要问题上的高水平工作；6.5–7.5 表示有参考价值但不够突出；5.0–6.0 表示创新、实验或结论存在明显不足；1.0–4.5 表示推导、实验支持或表达存在严重问题。

## 标签

严格输出四行，第一行列出全部标签，第二行指定主任务，第三行指定主方法，第四行列出补充标签。所有标签以 `#` 开头，用空格分隔，不用逗号、分号或顿号。

```
#标签1 #标签2 #标签3 #标签4
主任务标签：#任务标签
主方法标签：#方法标签
补充标签：#标签 #标签
```

共选择 3–5 个标签，至少包含一个任务和一个方法。标签必须逐字采用下方提供的首选名称，状态为 `active`，不输出概念 ID、别名、已弃用名称或自行翻译的名称。找不到完全对应的概念时，选择可用且最接近的上位概念，不自造标签。主任务选择最具体的适用概念，主方法描述论文实际的核心研究方法，补充标签可以来自其他分类维度。

同一概念及其别名不能重复，已经选择具体概念时不再选它的上位概念。相关性相近时，补充标签优先覆盖不同分类维度。选择时阅读 `definition` 和 `scopeNote`，不能只看名称相似。arXiv 类别如 `#cs.CL`、没有 `#` 的文字，以及把多个标签拼在一起的写法都不合格。

根据以下事实区分容易混淆的标签：

- 识别或 ASR 只是测量工具时，社会语音学、韵律统计或发音评估研究不能因此标为 `#语音识别`。选择 `#语音属性识别` 或适用的科学主题。
- 用视频、参考音频、说话人嵌入或到达方向（DOA）指定目标时，选择 `#目标说话人提取`；有视觉输入时可以补充 `#音视频`。只有视觉用于盲分离、没有指定目标时，才选择 `#音视频语音分离`。
- 核心贡献是表示、量化、数据或协议时，主方法不选 `#CNN`、`#RNN`、`#Transformer`、`#注意力机制` 或 `#状态空间模型` 等骨干架构。架构可以作为补充。数据集、基准、综述和理论论文按实际采用的研究方法选择。
- 多模态输入不等于核心方法是多模态学习。没有训练的处理流程优先选择适用的信号处理或系统方法；对抗工作按实际机制选择对抗训练或对抗鲁棒性。词表没有对应概念时选择合适的上位概念，不为凑数贴标签。
- 应用场景必须是论文实际研究或评测的场景，不能只出现在局限或未来工作中。`#实时处理` 必须有实测延迟或吞吐及其条件，作者自称实时不能作为依据。
- 标题或正文明确表明构建基准、语料或数据集时，必须包含 `#基准测试` 或 `#数据集`。在 3–5 个标签的限制内，它们优先于泛泛的场景或模型族标签。
- 补充任务必须有与主任务并列的贡献或评测证据。仅用 WER 等指标评测其他任务，不意味着识别也是本文的研究任务。

## 作者与机构

只从提供的论文内容提取作者及其机构。能判断第一作者和通讯作者时分别注明，否则写“未说明”。列出能确认的姓名及对应大学、实验室或公司，机构具体到输入能支持的层级，不猜部门或归属。

格式示例：
- 第一作者：张三（清华大学计算机系）
- 通讯作者：李四（Google DeepMind）
- 作者列表：张三（清华大学计算机系）、李四（Google DeepMind）、王五（未说明）

## 论文评价

用 2–3 句话评价最有依据的贡献和最重要的限制，说明判断来自什么证据。不空泛赞美、嘲讽或表演犀利，也不为凑齐正反意见编造缺陷。没有发现明确问题时，如实说明。

## 核心摘要

正文写 6–9 句，汉字与中文标点合计 320–600 个，组成连续段落，说明任务的输入、输出和难点。解释 2–4 个方法步骤各自的职责，以及上一步输出怎样进入下一步，再交代相对已有方法的关键差异和实际意义。

至少说明 1 个原文关键定量结果。在同一句中写清比较对象、评测设置或数据集、指标、数值与方向。不能用模型名、版本号、年份、参数量、样本量或训练超参数代替实验结果。原文确无可核对的定量结果时，原样写“原文未提供可核对的关键定量结果”。

说明结论的适用范围、失败条件或尚未验证的范围，以及原文报告的训练、推理或部署成本。没有披露成本时，原样写“原文未披露训练、推理或部署成本”。这里只提取最重要的 1–2 个结果数字，表格放在实验结果中，不重复整张表。

## 方法概述和架构

正文不少于 600 个中文字符，解释核心方法怎样工作。先用 2–3 句话说明输入、处理和输出，再展开核心组件。每个组件要说明论文采用的名称、功能、内部结构或算法，以及输入和输出。原文有公式时解释其含义，不仅列符号。

写清组件怎样连接、传递什么数据，是否存在循环、反馈或条件分支。说明设计动机和精度、速度、训练方式等取舍；推断的理由明确标为推断，并给出依据。多个阶段分别解释，不省略论文明确报告的组件。首次出现的核心术语应让不熟悉该方向的读者也能理解。

数据集、基准、理论和综述等工作按实际内容解释构建过程、评估流程、论证或综合分析，不强行套用模型架构。不要只列组件名、用“详见原文”代替实现，或把方法压成 1–2 段短文字。

## 核心创新点

说明 3–5 个最重要的创新点。每项解释新的内容、已有方法的局限、作用机制，以及原文提供的收益或证据，不写空泛评价。

## 实验结果

写清主要基准、数据集、指标和数值，以及与最强基线或当前最佳结果的差距。原文没有直接比较时明确说明。原文提供了关键消融、负结果或不同条件、语言、场景的细分结果时，保留相关证据和数值。

正文明确报告的数字可以直接使用。正文没有复述图表数字时，只能从输入中可见的原始表格单元格或明确图注提取，不能根据曲线、柱高、颜色或像素位置估算。拿不到具体数字时写“论文未给出具体数值”。每组结果就近说明数据划分或设置、方法、基线、指标、数值、单位、方向和必要条件，不让读者猜测数字对应什么。

最多嵌入 2 张关键 Markdown 表格，每张最多 12 个数据行和 8 个指标列，方法、模型和数据集等识别列不计入指标列数。实证论文的表格合计至少有 3 个数据行和 2 个可核对数字。表头有识别列；指标有优化方向时标出 `↑/↓`。不使用“结果”“观察”“含义”“说明”或“结论”等叙述列代替指标。

大表优先保留本文方法、最强基线、代表性传统或开源基线、平均或汇总行，以及关键消融和负结果。表前说明比较问题和选取这些行列的理由，表后解释主要差异、代价与适用范围。不要套用固定句首、逐行复述或用“此处省略”“详见原文”代替数据。负号用 ASCII `-`，百分号用半角 `%`，小数保留前导零。

## 细节详述

解释复现所需的技术细节，包括训练数据的来源、规模、预处理和增强，损失函数及其权重，学习率、预热、批量大小、优化器、步数或轮数及调度策略。再说明模型规模、层数、隐藏维度、码本大小、训练设备型号和数量、训练时长，以及解码、温度、束搜索宽度和流式设置。原文提供了正则化或稳定训练方法时也应说明。缺失的项目写“未说明”，不按惯例补写。

## 评分理由

八个维度各写一条，顺序为创新性、技术严谨性、实验充分性、清晰度、影响力、开源、可复现性、工程/实践价值。每条严格使用 `* 中文维度名 (得分/分母)：具体理由`，分数和理由不拆成两行。理由说明具体证据及其优点或缺陷，不写占位评价，也不重复总分计算。

得分采用对应维度的原始分值，不换算成十分制或百分制。分母使用该维度满分，得分必须有限、非负、不超过满分且最多一位小数。开源分采用前述允许值。缺项、重复、错误分母和无有效理由都会被程序拒绝。同一个缺陷只用于一个维度，按 `document_type` 选择适用证据，不能仅因类型给分。

* 创新性 (X/2)：解释问题、方法或关键认识的新颖程度，与已有最佳方法的区别，以及论文声称的创新能否成立。
* 技术严谨性 (X/1.5)：解释推导、证明、算法、假设和边界是否可靠，只指出有依据的技术问题。
* 实验充分性 (X/1.5)：评价基线、消融、覆盖范围和统计等适用证据能否支持结论，指出不公平比较或过度解读。
* 清晰度 (X/1)：评价组织、符号、公式、图表和文字；训练配置、硬件和复现步骤的缺失归可复现性。
* 影响力 (X/1.5)：说明对语音、音乐或音频研究的实际贡献、后续价值和适用范围。非音频核心贡献或范围很窄的小改进按前述政策评分。
* 开源 (X/1.5)：根据论文类型判断相应核心材料是否公开、文档是否完整，与开源详情保持一致。有演示页面时，可以据输入中提供的链接说明是否存在资源入口，不能假装已经访问网页。
* 可复现性 (X/0.5)：说明训练细节、超参数、硬件、实验设置和步骤是否足以复现。只有仓库或演示链接不代表这些说明充分。
* 工程/实践价值 (X/1.5)：根据系统流程、真实测量、可复用组件和部署资料评价实际参考价值。系统、模型和基准工作应具体核对；纯理论工作可以为 0。

## 局限与问题

区分论文明确承认的局限与根据证据发现的潜在问题。前者概括作者报告的限制、假设和未来工作；后者说明方法、实验设计或结论中需要进一步核查的具体问题及依据。推测不能写成已确认错误，某方面没有发现明显问题时如实说明，不为凑数编造。

## 开源详情

只根据输入论文和提供的链接说明资源情况，不编造仓库、收藏数量或平台热度。分别说明代码仓库、模型权重、数据集及获取方式、在线演示、训练配置和检查点、附录及其他复现材料，必要时注明论文使用的开源工具或模型。没有相应信息时写“未提及”；没有代码链接时写“论文中未提及代码链接”，没有开源计划时写“论文中未提及开源计划”。

### 输出注意事项

关键实验表格放在实验结果中，其他结果用有依据的文字说明。特殊文本标记如 `<S>`、`</S>`、`<E>`、`<task>`、`<perception>`、`<interrupt>` 和 `<backchannel>` 必须用反引号包裹，避免被当作 HTML 标签。

数学公式使用 `$...$` 表示行内公式、`$$...$$` 表示独立公式，不用普通文本代替。例如应写 `$RMS = \sqrt{\frac{1}{N} \sum y[n]^2}$`。可能被误解析的符号放在公式环境或代码格式中。
