# batch 与 deep 的锁内来源检查

`batch`、`deep` 保留入口完整检查：正式批次与来源运行、完整论文集合必须对应，每篇论文的文本、PDF、来源元数据和清单都必须通过。初始任意一篇文件损坏，所有论文都不能开始模型请求。

取得每篇论文锁后，程序重新读取当前正式记录、最新运行清单、完整论文集合和批次信息，并要求与入口使用的来源运行完全一致。换运行、换集合、日期或批次不一致时停止，不能沿用入口旧计划，也不自动拼接新计划。本篇四份文件每次重新读取并核对；事实反馈的来源与正文绑定仍照常核验。

此前每个反馈论文的锁内检查还会读取另外所有论文的 PDF、文本和元数据。这一步改为只重新核本篇；没有缓存来源内容或文件校验结果。程序内部仅记录入口实际完整核验返回的计划身份，防止调用方传入另一份计划或随意的“已核验”标志。

正常结束前，在最后一次中央保存事务内重新核整批来源，再写 `complete` 和完成时间。包括零待办入口。处理过程中的保存保留论文结果，但批次一直为 `running`；结束检查失败不能留下新写入的批次完成状态。已成功保存的正文、Reader 和费用账不删除。

如果运行期间另一个论文的来源文件被改，本篇未消费该文件，可以继续使用自己重新核验过的来源；被改论文进入自己的锁时会拒绝，正常结束前的整批检查也会拒绝。这不是“每篇锁都重新核了全批”，也不保证绕过正常入口的调用者已完成整批审查。

优化只用于 `batch`、`deep`，没有改变显式强制重分析、Reader 刷新或其他入口。现有入口准备本身可能包含额外一次整批检查；这次移除的是每篇锁内重复核整批的热点，末尾增加一次完整检查。进入分析后的阶段来源核验仍保留，不宣称每篇总共只读四个文件。
