# 分析与 Reader 刷新的温和停止

在批量分析或 Reader 刷新期间发送 `SIGTERM` 或 `SIGINT`，程序停止领取新论文和发送新的模型请求。已经发出的请求仍按原超时等待，返回后正常解析、记账和保存；不会为了停止而丢弃已返回内容，也不会退回已登记的费用。

停止状态覆盖 `analysis-engine.analyzeBatch()` 的所有正常轮次，以及单篇、批量 Reader 刷新。`deep`、`batch`、`reanalyze` 和 `full-fetch` 的整篇分析使用统一引擎。抓取和筛选阶段不在这个停止作用域内；图片准备期间已经开始的网络操作也可能继续。不能将此行为说成“立即取消所有 HTTP 请求”。

公共模型请求在进入时检查停止状态，并在实际发送、登记新预算之前再次检查。等待并发额度或排队期间收到停止也不能再发请求；同一论文的后续修复、内部重试和账号切换都受此检查约束。全批轮次边界同样检查停止状态，不能因为本轮已结束而再启动失败集合。已返回的服务端错误保持原错误和用量，不会因停止改成另一种错误。

程序完成在途处理与最终保存后，以 `ANALYSIS_STOP_REQUESTED` 运行级错误结束。即使最后一篇已经成功，也不会返回正常成功让命令继续生成、审查或发布。错误附带实际保存结果与统计；已成功保存的论文仍是成功，不被加入虚假的失败清单。保存期间收到停止也会在保存完成后检查。真实磁盘、中央保存或服务配置错误优先保留，不能被停止错误覆盖。

信号监听器只在运行期间安装，嵌套操作共用状态，并行操作保留各自状态；退出时移除本模块自己的监听器。主动停止一个作用域不影响另一个作用域。进程收到停止信号后，即使当前作用域已经退出，同一进程后来开始的分析也不能再发送请求。正常继续运行应重新启动原入口，核验已有来源、检查点和账目后恢复。

第一次和重复的 `SIGTERM`、`SIGINT` 都是温和停止，不会自动升级为强制退出。若明确使用系统强制结束（例如 `SIGKILL`），可能来不及保存最后返回的内容，也不能保证最终状态已经写入；已经登记的请求额度和费用仍保留，不清零、不退款。恢复时必须按原账和原稿核验，不能把强停当成该次请求没有发生。

## 离线验证

测试使用本地生成的来源、合格正文和模拟传输，不请求外部模型、不写正式数据，覆盖：

- 嵌套状态继承、并行主动停止不串扰、监听器移除。
- 请求进入后、实际发送前收到停止，不登记预算也不发送，事件记为发送前拦截。
- 已返回内容先保存，内部下一次请求被挡，新论文和新的失败轮不启动。
- 真实子进程收到 `SIGTERM` 和 `SIGINT` 后保存返回内容与最终状态，后续作用域仍不能发请求。
- 最后一篇成功、最终异步保存中收到停止，都向公共调用方传播停止，后续阶段不执行。
- 单篇和批量 Reader 已保存成功结果后仍传播停止，不将已保存成功列为刷新失败。
- 显式付费轮的原始归档、已返回稿与原 `48000` 预留账逐字保留，停止后的 `16000` 请求不新增费用。
- 停止期间的真实运行级错误、最终保存 `ENOSPC`、中央保存错误不会被吞掉。
