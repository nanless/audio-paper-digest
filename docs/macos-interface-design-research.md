# Mac 论文研究应用：界面设计深度调研与逐屏规范

调研日期：2026-10-24。对象是本项目拟新增的 Mac 桌面应用：读取既有网站成果、图文精读、按需打开 PDF、个人 LLM 研究和 Zotero 存档。

本文交付研究结论与下一版设计要求。依据包括 Apple 官方规范、产品官方资料，以及实际查看的 8 组官方 Mac 截图。未安装或付费试用这些参考产品，也没有据官网宣传测试它们的性能、准确率或可靠性。官方页面保留的旧截图只作为构图参考，不冒充当前版本的完整实测。

下文分别标记“来源说明”“视觉观察”和“本项目建议”。尺寸、字号、间距、比例及取舍属于本项目拟定的设计起点；除明确说明外，不是 Apple 规定的固定数值。

## 1. 结论：最适合本项目的方向

建议采用**原生 Mac 的窗口与操作秩序，加上高质量学术阅读排版和按需展开的证据工作区**。

具体是：窗口与工具遵循 macOS，论文库适合快速扫描和筛选，单栏像经过认真排版的阅读器，双栏让原文足够大、解释足够清晰，模型和后台任务在需要时出现。真实论文里的图、表和公式成为视觉中心，应用外壳保持克制。

这个方向同时解决用户反复指出的三个问题：它属于 Mac 桌面应用；关闭 PDF 时完整单栏；打开 PDF 后的双栏也有独立、完整的构图，而非把原页面挤小。

“好看”的判断应覆盖持续阅读、查找、选择、编辑、等待、出错和恢复。功能检查通过只能证明交互可用；视觉完成还要用真实长标题、真实正文、科学图表、公式、表格及各种窗口状态逐屏评审。

### 2.3 这些参考共同说明什么

1. 让人愿意长期使用的阅读工具，通常有稳定的空间秩序。
2. 层次主要靠排版、对齐、内容分组与适当留白建立，不需要给每项内容套一个圆角框。
3. 真实内容本身可以丰富而有色彩，应用外壳应当给它让位。
4. 工具要容易找到，同时避免持续挤占正文。
5. 单栏、分栏、编辑和辅助窗口需要分别设计；共享视觉系统不意味着每屏套同一个网页模板。

这是对参考图与本项目需求的综合判断，不是产品优劣排名。

## 3. 前几版原型仍然存在的问题

| 问题 | 为什么影响观感与使用 | 后续要求 |
|---|---|---|
| 用红黄绿窗口点证明“像 Mac” | 外壳之内仍可能是网页仪表盘的组织方式 | 窗口、工具栏、菜单、设置、焦点和分栏都遵循桌面习惯 |
| 大量浅蓝底与蓝色标签 | 页面被同一种轻颜色铺满，科学内容与交互的区别不清楚 | 以中性色为基础，系统强调色主要表示交互和选择 |
| 正文整段使用次级灰色 | 让研究正文看起来像辅助说明，阅读对比度不足 | 主要文本色用于正文，次级颜色用于书目与时间等信息 |
| 为了填图文区使用通用波形图 | 图形漂亮与否不能替代真实论文内容，所有论文看起来相同 | 设计验证必须使用真实图、表、公式及图注 |
| 单栏先居中再留大片空白 | 字号、行长和视觉重心没有一起确定 | 先确定阅读尺度，再分配剩余空间 |
| 双栏只压缩单栏 | 标题、元数据、图与按钮同时拥挤 | 双栏采用独立尺寸与折叠策略 |
| PDF 一直缩成完整纸页 | 页面看起来完整，但双栏论文可能无法舒适阅读 | 默认考虑适合宽度，允许纵向滚动与局部放大 |
| 论文库主要是大卡片 | 长标题容易断裂，列表比较效率低 | 默认列表，图片模式作为可选展示 |
| 设置变成主窗口里的整屏后台页面 | 组织方式更像网站；切换后丢失阅读上下文 | 改为独立 Mac 设置窗口 |
| 齿轮、任务图标和侧栏入口多处重复 | 造成工具噪声与空间浪费 | 对命令按频率和作用域重新分组 |
| 主标题栏加第二条工具栏过高 | 降低正文的实际可见高度 | 优先合并为系统统一标题栏/工具栏 |
| 边框、卡片、徽章和阴影使用过多 | 缺少轻重关系，类似通用后台模板 | 保留真正需要的表面与边界 |
| 页脚常驻画布尺寸、版本与预览提示 | 把制作信息混进产品信息 | 设计说明放在预览外；产品只显示有用的真实状态 |
| 只看几个正常页面 | 聚焦、错误、等待和非活动窗口仍可能粗糙 | 同时设计状态，不把“所有界面”缩成八张静态图 |

## 4. 三条视觉路线与选择

### A. 原生、清晰的研究阅读器——推荐

系统窗口与控件，安静的导航，清晰正文，按需显示原文和证据。主要借鉴 Mac 阅读器、Bear 的内容层次以及 Highlights 的研究对照。

适合：每日找论文、连续长文阅读、图表核对、个人笔记与可靠归档。风险是做得过于朴素，需用真实内容、字体细节与交互打磨来体现完成度。

### B. 强编辑感的长文阅读器

标题与正文更强调出版排版，界面工具退到较低层级。适合长导读与专题文章。风险是大标题、大留白和装饰性叙事压过科学内容，双栏时也容易失衡。

采用其中的段落节奏与图文处理，不把整个应用做成杂志封面。

### C. 高密度专业资料工作台

表格、多条件筛选、检查器和多窗口能力更强，参考文献管理工具。适合大库整理与集中研究。风险是默认露出过多面板，对日常阅读负担较大。

采用其列表、批量操作和证据管理，较复杂功能逐步展开。

最终组合以 A 为骨架，吸收 B 的阅读排版与 C 的资料整理能力。避免把三种界面的全部工具同时摆到首页。

## 5. Mac 窗口与尺寸

### 5.1 基准画布不是实际运行限制

1440 × 900 适合作为统一评审的桌面设计基准，但实际应用必须支持拖动、调整大小、全屏、多窗口与外接显示器。这符合 [Apple 窗口指导](https://developer.apple.com/design/human-interface-guidelines/windows)。

设计尺寸以逻辑点讨论。Retina 物理像素与逻辑尺寸不同；例如 2 倍像素倍率下，1440 × 900 逻辑点会对应 2880 × 1800 像素。这里不声称所有 Mac 的默认显示尺寸相同。

聊天里的原型可对整张桌面画布等比缩略，不能根据聊天栏宽度把应用改成手机版。实际应用也不能依靠整体缩小控件来适应小窗口。

### 5.2 建议验证的窗口组合

| 参考窗口 | 需要验证的重点 |
|---|---|
| 1280 × 800 | 单栏舒适；双栏时合理收起资料侧栏 |
| 1440 × 900 | 标准单栏、双栏、资料库和辅助窗口 |
| 1728 × 1117 | 扩大工作区而不过度拉长正文 |
| 1920 × 1080 | 外接显示器、分隔线调整和多窗口操作 |
| 较窄桌面窗口 | 设置合理下限，允许收起侧栏或把 PDF 移到独立窗口 |

这些是本项目建议的测试尺寸，并非具体 Mac 型号的默认规格表。最小窗口约束要在真实内容验证后决定。

### 5.3 基础空间分配

- 资料侧栏建议初始 210–230 pt，可隐藏、可调整。
- 优先让统一标题栏/工具栏占约 56–68 pt 的量级，具体跟随系统组件表现。
- 没有必须显示的信息时，不常驻占用高度的底栏。
- 全局搜索与任务状态按需展开，不在每篇文章顶部重复做完整搜索页面。
- 使用真实系统分隔线与拖动行为，保存用户调整的面板比例。

侧栏在窗口变窄时可以自动收起，用户仍可显示和固定。Apple 官方允许这种 Mac 行为，见[侧栏规范](https://developer.apple.com/design/human-interface-guidelines/sidebars)。

## 6. 视觉系统：如何让所有界面像同一个产品

### 6.1 颜色

推荐“石墨色文字 + 中性阅读底色 + 系统强调色 + 真实内容原色”。避免让整个应用都呈浅蓝或浅紫色。

| 角色 | 推荐做法 |
|---|---|
| 正文 | 主要文本色，足够深；不要整段套次级灰 |
| 元数据 | 次级文本色，仍须可读 |
| 选中状态 | 系统选中与强调色，活动/非活动窗口分别处理 |
| 侧栏 | 系统材质或中性表面，让它与正文有层次 |
| 图、表、科学图片 | 保留原始颜色和图例含义 |
| 模型推断、原文证据 | 用标签与图标说明类型，不只靠颜色 |
| 错误、等待、完成 | 颜色配合文字，不能把红绿当唯一信息 |
| Zotero 标识 | 作为服务身份局部出现，不改变应用通用按钮的语义 |

原生实现优先用系统语义颜色，而不是硬编码整套浅色值。系统强调色、深色外观与提高对比度设置应得到尊重。依据：[Apple Color](https://developer.apple.com/design/human-interface-guidelines/color)。

### 6.2 可用于样稿的颜色起点

以下只用于比较样稿，运行时优先映射为语义颜色。

| 用途 | 浅色样稿示例 | 说明 |
|---|---|---|
| 阅读背景 | `#FAFAF8` | 接近中性的柔和底色 |
| 正文 | `#25262B` | 主文对比明确 |
| 次级文本 | `#656973` | 书目、日期等辅助信息 |
| 强调色样例 | `#3468D4` | 仅供方案讨论，最终支持系统强调色 |

本次按 WCAG 相对亮度公式计算：正文/阅读底色约 14.45:1；次级文本/阅读底色约 5.26:1；强调色与白色约 5.15:1。这只验证指定纯色组合，不代表整套界面、玻璃材质或深色外观已经通过验收。

[WCAG 对比度说明](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)给出普通文字 4.5:1、大文字 3:1 等基准。项目可以据此检查文字，但仍需在实际系统和材质上验证。

### 6.3 字体与层次

Apple 给出的 macOS 常规界面字号参考为默认 13 pt、最小 10 pt；这并不意味着长篇中文导读应该用 13 pt，更不意味着把全部辅助信息都压到最小值。依据：[Typography](https://developer.apple.com/design/human-interface-guidelines/typography)。

| 角色 | 本项目建议起点 |
|---|---|
| 系统工具与侧栏 | 跟随原生标准样式，通常在 13–14 pt 的阅读量级 |
| 论文库主要标题 | 14–16 pt，根据列表密度与长标题调整 |
| 书目与辅助信息 | 12–13 pt，重要信息不靠极小字号压缩 |
| 单栏中文正文 | 17–18 pt 起，允许用户调整 |
| 双栏中文正文 | 16–17 pt 起，保持阅读性 |
| 文章主标题 | 26–32 pt，长科学标题允许换行 |
| 章节标题 | 19–22 pt |
| 图注、表注、来源 | 12–14 pt |
| 代码 | 等宽字体，约 13–15 pt 起 |

界面采用系统字体。中文正文优先系统中文字体；衬线阅读主题可以是用户选项，不预设所有人都要宋体。不要在导航、正文、徽章和弹窗中各用一套字体。

公式使用合适数学排版，代码使用等宽字体。数字比较、评分列和表格数据使用稳定对齐方式。原生逻辑点与 WebKit 的 CSS 单位要通过实机渲染校准，不能直接把原生 `17 pt` 机械写成网页 `17pt`。

### 6.4 间距、边界与图标

建议先采用 4、8、12、16、24、32 的间距层级，再按真实内容调整。标题与章节留白有规律，面板内边距和表格对齐线保持一致。

系统控件优先使用原生 regular/small 样式。桌面控件不统一套手机式大触控按钮；具体高度跟随平台与任务，而不是给所有按钮设同一个大圆角和大留白。

边界只用来说明容器、选中、分隔与浮层。PDF 纸张保持纸张感，正文不要连续嵌套卡片。阴影主要表达浮层，避免列表每项都靠悬浮阴影制造“高级感”。

图标优先 SF Symbols，保持字重与文字协调。侧栏图标、工具栏图标和状态图标语义一致；不要仅因喜欢某个形状就让不同操作共用它。

## 7. 材质与深色模式

### 7.1 Liquid Glass 的使用边界

Apple 明确将 Liquid Glass 定位于导航和控件层，并提醒不要把它用在正文内容层，也不要过度自定义。依据：[Materials](https://developer.apple.com/design/human-interface-guidelines/materials)。

本项目应让系统决定窗口和适用工具的材质。文章、科学表格和 PDF 应有稳定、可读的内容背景。玻璃效果不能盖在公式和实验图上。

减少透明度、提高对比度、窗口失焦时，界面也必须清楚。最低支持系统若不具备新材质，使用该系统的标准表现，不手工仿一层玻璃来追逐外观。

### 7.2 PDF 与图片的深色处理

深色应用不等于反转整张论文。图表的颜色、热力图、光谱与图例有科学含义，不应随 UI 主题随意变色。

建议第一阶段提供深色外壳、可调的阅读背景和原色 PDF；更复杂的 PDF 自动深色处理单独验证。Highlights 的[官方说明](https://highlightsapp.net/changelog/2026/01/28/macOS-Version-2026.1/)也将文本/背景变化与保留图像及标注区别处理，可以作为功能参考。

## 8. 论文库：默认以列表为核心

### 8.1 为什么不默认大卡片

本项目资料主要是长标题、来源、日期、任务、方法、评分与状态。需要连续比较和快速筛选，文字列表更符合任务；Apple 也建议优先用列表或表格展示文字数据。依据：[Lists and tables](https://developer.apple.com/design/human-interface-guidelines/lists-and-tables)。

大图网格可以作为可选模式，适合确实有可用封面或代表图的专题浏览。不能为了让网格好看，给每篇论文都造一张通用示意图。

### 8.2 建议的论文行

舒适密度下，行高可先尝试 72–88 pt；紧凑模式再减小。主要标题允许一到两行，原题或作者作为次级信息。完整题目在打开详情时必须可见。

建议默认列：论文标题、任务、网站日期、网站评分、阅读/存档状态。方法与其他字段通过列选择显示。日期、数值和状态对齐，列标题可排序。

只展示当前任务真正需要的标签，不在每一行展示完整分类树。评分明确来自网站，不包装成个人兴趣或模型可信度。

### 8.3 浏览和打开

选中行后可以查看简要信息，Return 或双击进入导读，保留原列表的位置与筛选。支持右键菜单、键盘选择和多选。

默认进入精读后不强制保留“资料侧栏 + 论文列表 + 导读 + PDF”四栏。论文列表可以收起，用户也可通过窗口菜单把某篇放到新窗口。

## 9. 单栏阅读：正文成为主角

### 9.1 结构

```text
系统标题栏与统一工具栏
┌────────────┬──────────────────────────────────────┐
│ 资料侧栏   │ 文章标题、书目、网站评分             │
│ 可收起     │                                      │
│            │ 正文：章节、科学图、公式、表格       │
│            │                                      │
│            │ 引用与必要的研究操作                 │
└────────────┴──────────────────────────────────────┘
```

不开 PDF 就不保留空白 PDF 栏，不默认给文章旁边再塞一块聊天区。留白用于控制阅读行长，不是机械地把一个小模块放到大画布中间。

### 9.2 阅读尺度

中文正文可先以 17–18 pt、约 1.75–1.9 倍行高测试，阅读列约 680–800 pt。具体需按字体、混排和公式调整，不把某个行宽当所有文章的硬上限。

更宽的窗口增加边侧空间或允许宽图表展开，不无限拉长每行文字。主标题完整，原题与作者信息清晰；不为了海报感把正文标题改成营销句。

章节标题、图前图后距离、图注和表注统一。真实文章可能很长，允许正常滚动，不能为了“一屏看完”缩小正文。

### 9.3 图文处理

- 图片按原比例展示，点击可在适合的放大视图中查看。
- 宽图表可暂时占用更大的内容宽度，正文仍保留阅读行长。
- 图注与来源同图绑定，不只放一张没有解释的装饰图。
- 表格列对齐，单位与统计条件完整；内容过宽时使用局部滚动或展开。
- 公式清晰、可放大，不能把长式子缩到难以辨认。
- 代码、脚注与引用沿用同一排版体系。

美观样稿必须至少包含一张真实方法图、一张结果表和一个公式。通用波形图不能证明真实科研内容的呈现已经做好。

## 10. 双栏 PDF：原文优先保证可读

### 10.1 独立布局

```text
系统标题栏与统一工具栏
┌──────────┬─────────────────────┬──────────────────────┐
│ 资料侧栏 │ 导读 / 个人解析     │ PDF 工具与原文       │
│ 可收起   │                     │                      │
│          │ 问题、解释、证据    │ 按宽度阅读与滚动     │
│          │                     │                      │
└──────────┴─────────────────────┴──────────────────────┘
```

初始比例建议从左 46%、右 54% 验证，用户可调整。右侧需要容纳原文页面，不必为了形式对称坚持 50/50。

在 1440 pt 宽的窗口中，如果侧栏 220 pt，剩余区域约 1220 pt；46/54 大致对应左 561 pt、右 659 pt，尚需扣除各自内边距与分隔线。这个估算用于提前发现挤压，不替代原生布局测量。

### 10.2 不把 PDF 缩成“邮票”

双栏论文在“整页适合窗口”时，正文可能缩得过小。建议默认测试适合宽度，允许页面纵向滚动；提供整页、实际大小、选区放大等明确控制。

原文为双栏时，可研究对某一栏或选区的放大阅读，不把 PDF 改写成未经核验的文本重排。放大后的导航与返回必须自然。

PDF Expert 的[官方阅读器介绍](https://pdfexpert.com/features/pdf-reader-mac)提供了阅读模式、并排与标注能力的参考；具体默认缩放是本项目需要用真实论文验证的选择。

### 10.3 左栏的重新组织

- 主标题略收敛，仍可完整换行。
- 书目只保留关键字段，其他信息放入详情。
- 图、表和公式保留清晰尺度，必要时单独放大。
- 切换网站导读、个人解析和笔记不丢选区与编辑内容。
- 只有解析模式出现提问区，导读和笔记不长期背着聊天输入框。

### 10.4 较小 Mac 窗口

窗口变窄时，先收起资料侧栏，并减去次要工具。不要先缩小全部字体，也不要默认切成手机式上下两页。

可测试约 1000–1100 pt 宽的桌面窗口下，保留约 360–420 pt 的解释区域和约 520 pt 的 PDF 工作区域。若无法同时满足可读下限，可提供“将 PDF 移到独立窗口”，或限制继续缩小。最终下限由实测确定。

### 10.5 开关与滚动

打开 PDF、关闭 PDF、调整分隔线时，保存当前章节、输入、笔记和 PDF 页码。导读与 PDF 不按滚动百分比机械同步；引用跳转只使用真实证据定位。

## 11. 原文解析：研究结果仍然像研究文档

当前选区以简短来源块显示，包括论文版本与页码。问题可以小范围区分，回答正文沿用导读的阅读样式；不要把所有科研解释包装成巨大的聊天气泡。

回答分别展示解释、原文证据、推断和限制。公式、表格和图片同样可读。点击证据返回实际原文；只有页码时只做页级定位。

输入区建议两到五行可调整，固定在当前研究面板的可见范围内。回答独立滚动，用户向上阅读时不要被流式内容不断拉回底部。

模型、输入范围与必要用量信息清楚，但不在每条回答上堆满技术徽章。没有原生 PDF 或视觉能力时，使用清晰的能力说明。

正文编辑和解析发送的键盘行为区分明确。可以考虑 Command–Return 解析，Return 保持换行；避免普通回车意外产生付费请求。

[Zotero 阅读器](https://www.zotero.org/support/pdf_reader)中，摘录进入笔记后仍带有回到 PDF 的关联；[LiquidText](https://www.liquidtext.net/features)同样强调往返来源。这些交互关系比给答案加一个“可信”颜色更有价值。

## 12. 我的笔记：采用 Mac 编辑体验

笔记应像一个可以长期维护的文档：标题、正文、摘录、来源和研究问题有层次，编辑区保持正常行距与光标行为。

避免把网页默认的大 textarea 直接当成最终笔记产品。实现时验证原生文本编辑、撤销重做、拼写、链接、输入法、文本选择、拖入摘录与粘贴行为。

格式工具按需显示，科学证据与个人想法有清楚归属。自动保存状态必须来自真实保存结果；不能键入后就无条件显示“已保存”。

笔记在单栏和 PDF 对照模式都可用，打开原文不会把编辑区压成窄条。全局搜索不应抢走编辑器常用快捷键，例如 Command–K 在文本编辑环境里常与链接操作相关，需认真处理命令作用域。

[Bear 的字体设置说明](https://bear.app/faq/typography-options/)支持分别调节字号、行高、行宽与段落间距，可借鉴其把阅读尺度作为一组参数的思路；本项目默认值仍需针对中文科研内容确定。

## 13. 后台任务：简洁、诚实的工作状态

轻量状态可通过工具栏活动入口展开，完整任务列表用于集中处理。没有任务时不为了填满页面显示虚构的进度图和费用卡片。

任务行显示对象、当前阶段、状态及可用操作。下载可以显示实际字节；模型等待阶段使用不确定进度，不用没有根据的百分比制造“顺畅感”。

暂停、取消、重试与查看结果位置稳定。网络失败、密钥错误、文件保存失败和等待 Zotero 各自有准确说明，操作按钮直接对应恢复动作。

费用与请求状态相关联；取消不等于没有消费，未知用量不等于零。失败不能被绿色完成样式掩盖。

Apple 的[进度规范](https://developer.apple.com/design/human-interface-guidelines/progress-indicators)强调准确和一致的反馈。具体任务结构还需遵守本项目已有的恢复与费用规则。

## 14. 设置：独立的 Mac 设置窗口

这是对前面原型的重要修正。Apple 建议通过应用菜单与 Command–Comma 打开设置窗口，并避免用设置按钮占据主工具栏。依据：[Settings](https://developer.apple.com/design/human-interface-guidelines/settings)。

建议按模型 API、阅读、Zotero、同步与存储等少量分组组织。窗口保持独立、尺寸适合内容，记住上次位置。不能每次设置模型都把主阅读区切走。

模型配置采用清楚的表单层次：服务、端点、模型、凭据状态、能力检查与使用范围。密钥由系统安全存储管理，界面不回显。错误就近显示，不让一个小配置问题触发全屏警告。

阅读中的临时字号、当前 PDF 缩放和列表筛选应在当前任务里调整，不必每次打开全局设置。

建议用真实系统表单与设置场景验证外观，而不是把大型网页设置中心缩进一个小窗口。SwiftUI 提供原生 [Settings scene](https://developer.apple.com/documentation/swiftui/settings)。

## 15. Zotero：短时归档任务与持续连接管理分开

首次连接属于连接设置；归档一篇论文属于与当前文档相关的短任务。正常情况下，点击存档进入简明 sheet，完成后回到原阅读位置。

归档预览显示论文身份、目标分类和当前可保存资料。默认摘要足够清楚，完整书目字段通过展开查看；不把每个元数据字段都做成首页上的一行表单。

原文 PDF、离线图文、个人解析与笔记有明确选项。缺文件、版本不一致或元数据缺口就地说明。不能让漂亮的勾选状态掩盖实际未获取的附件。

已经连接时，主按钮是实际存档动作；未连接时引导连接。部分完成、重复归档、用户修改了已有笔记和附件失败需要独立状态，成功后可以直接打开 Zotero 条目。

长时间上传不应让用户一直困在模态 sheet 中。转入可恢复后台任务，并给出可回看的结果。持续查看详情适合非模态区域。依据：[Sheets](https://developer.apple.com/design/human-interface-guidelines/sheets)。

## 16. 工具栏、侧栏和快捷键

### 16.1 工具按作用域分组

| 区域 | 建议内容 |
|---|---|
| 导航 | 返回、显示/隐藏资料侧栏、当前文档上下文 |
| 阅读 | 导读/个人解析/笔记，原文显示与必要阅读工具 |
| 文档动作 | 收藏/待读、Zotero 存档、分享或更多 |

避免主标题栏一排图标、下方又一整排图标，最后还在正文里放同样操作。各阶段只让真正高频的动作常驻。

所有工具栏操作也要能从菜单中找到。减少重复常驻不意味着删掉能力；右键菜单、标准菜单和上下文操作可以保留专业功能。依据：[Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars)。

### 16.2 快捷键草案

| 动作 | 建议 | 性质 |
|---|---|---|
| 应用设置 | Command–Comma | Mac 常见系统习惯 |
| 当前文档查找 | Command–F | 保持文档语境 |
| 全库查找 | 可采用 Command–Shift–F | 本应用拟定，需核对命令冲突 |
| 打开/关闭侧栏 | 放入 View 菜单并提供快捷键 | 具体组合实施时确定 |
| 导读/解析/笔记 | 可提供 Command–1/2/3 | 本应用拟定 |
| 解析发送 | 可采用 Command–Return | 本应用拟定，保留换行行为 |
| 关闭窗口 | Command–W | 保持系统窗口语义 |
| 取消临时操作 | Escape | 不丢失已经输入的内容 |

需要验证输入法、菜单作用域与编辑器命令。不要把网上流行的命令面板快捷键无条件注册成整个应用的全局拦截。

## 17. 所有界面也包括这些状态

| 位置 | 至少要设计和检查的状态 |
|---|---|
| 论文库 | 空库、正在同步、有结果、无搜索结果、选中、多选、长标题、缺字段 |
| 单栏导读 | 文本、方法图、宽表、长公式、脚注、外部链接、离线缺图 |
| PDF | 未下载、加载、正常、扫描页、密码保护、缺失版本、放大与定位失败 |
| 双栏 | 默认比例、极限比例、侧栏收起、用户固定侧栏、切换文档、关闭恢复 |
| 个人解析 | 未配置、空问题、选区、流式回答、超时、取消、截断、已有结果复用 |
| 笔记 | 空白、编辑、聚焦、已保存、保存失败、外部修改冲突、来源被更新 |
| 任务 | 等待、执行、暂停、需处理、部分完成、结束、恢复 |
| 设置 | 默认、编辑、能力未知、检测中、成功、配置失败、凭据不可用 |
| Zotero | 未连接、无写权限、选择分类、已有条目、上传中、部分完成、核验成功 |
| 窗口与外观 | 活动/非活动、浅色/深色、提高对比度、减少透明度、减少动态效果 |

这些状态共享组件和反馈语言。不要只在成功页面讲究排版，失败后就出现粗糙对话框、原始 JSON 或重复重试按钮。

## 18. 动效、触感和细节完成度

优先保留系统控件自带反馈。打开 PDF 的转场只帮助用户理解空间变化，不为了展示动效让正文等待。自定义动效可先尝试约 180–250 ms，再按真实感觉调整；这不是 Apple 的统一时长要求。

关闭原文后应回到同一阅读位置，拖动分隔线连续而稳定。hover、按下、键盘聚焦、禁用、选中和窗口失焦都要有对应表现。

不要让每张论文卡片都弹起、每个标签都呼吸、每次回答都逐字闪现。支持减少动态效果，操作不依赖动画才能理解。依据：[Motion](https://developer.apple.com/design/human-interface-guidelines/motion)。

## 19. 为这个视觉方向选择实现方式

仅面向 Mac 时，建议优先验证 SwiftUI/AppKit 的原生窗口、工具栏、侧栏、设置和编辑能力；PDF 先验证 PDFKit。这样可以降低系统行为、焦点、菜单、外观和辅助功能的一致性成本。

[PDFView](https://developer.apple.com/documentation/pdfkit/pdfview)提供显示、选择、导航、缩放与文本复制等能力。需要用真实论文检查中文、两栏、公式、选区坐标、大文件和标注，不因框架原生就假定全部问题已经解决。

网站图文内容可用原生 [WKWebView](https://developer.apple.com/documentation/webkit/wkwebview)承载。把 HTML 正文放进原生应用是合理技术组合；窗口、工具与个人数据操作仍需要明确边界。

原项目的 Node/Python 分析、请求或数据能力可通过受控本机接口复用，不让客户端任意启动生产入口。模型配置与 Zotero 连接也不需要被网页正文访问。

此前规划里的 Electron/PDF.js 应视为候选方案，而不是已经替用户确定的路线。Electron 同样能做 Mac 应用，但当前明确以 Mac 体验为目标，应先比较原生组合在 PDF、图文数学、打包和后台任务上的实际表现，再做选型。

## 20. 下一轮设计与验收顺序

### 第一批：真实阅读样稿

选择同一篇已发布论文，用真实正文、科学图、表格和公式制作单栏与双栏。先解决中文排版、PDF 缩放、窗口宽度、工具栏和侧栏；不再用几段说明文字与通用示意图宣告阅读界面完成。

同时制作长标题、长公式、宽表和两栏 PDF 的困难样例，检验设计能否承受内容。

### 第二批：资料库与编辑

制作默认列表、筛选、搜索、选中、多选、笔记编辑和带来源的解析。让用户能从论文库连续进入研究，再自然返回。

### 第三批：辅助窗口与故障

完成原生设置、Zotero 归档、任务详情、未连接、上传失败和输入保存失败等状态。检查焦点、取消、返回与窗口关系。

### 第四批：整套一致性验收

| 维度 | 必须检查的内容 |
|---|---|
| 构图 | 单栏、双栏、资料库、编辑与辅助窗口各自完整 |
| 内容 | 长标题、中文混排、图、表、公式、代码、脚注 |
| 字体 | 正文与辅助信息有层次，放大后不溢出 |
| 颜色 | 系统语义色、科学图原色、实际对比度 |
| 控件 | hover、按下、选中、键盘焦点、禁用 |
| 空间 | 多种 Mac 窗口大小，分栏最小宽度与侧栏收起 |
| 外观 | 浅色、深色、提高对比度、减少透明度 |
| 连续性 | 打开/关闭 PDF、返回资料库、切换论文和窗口后上下文保留 |
| 异常 | 模型失败、来源缺失、笔记冲突、Zotero 部分完成 |
| 系统 | 菜单、快捷键、文本编辑、拖放、窗口活动状态 |

功能自动化、截图比对和人工视觉评审各自提供证据，不能用其中一种替代其他两种。只有新变化或未解决的问题才扩大重测，不为证明已经相同的结果反复跑整套。

## 21. 需要替换的旧设计决定

1. 保留 1440 × 900 作为研究画布，实际应用改为合理自适应的 Mac 窗口。
2. 论文库默认从大卡片改为可配置列表；图像模式可选。
3. 合并重复工具层，降低常驻工具噪声。
4. 全局设置改为独立设置窗口，从菜单与 Command–Comma 进入。
5. 单栏与双栏分别制定排版，优先保证 PDF 真实文字可读。
6. 使用主要文本色呈现正文，减少浅色泛化与过小元数据。
7. 用真实论文内容验证图文质量，移除通用装饰图作为主要验收材料。
8. 补足编辑、焦点、失败、部分成功和非活动窗口等状态。
9. 将预览制作信息移出产品界面，不让最终应用展示调试与画布说明。
10. 用原生 Mac 实现原型验证框架选择，再扩展完整功能。
