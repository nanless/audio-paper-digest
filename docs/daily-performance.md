## 结论与责任范围

## 造成长尾的具体机制

1. **系统误报被当成正文错误。** 下载包、运行系统、开源代码的概念区分，以及软件功能结果与模型性能摘要的区别，曾在公共校验中混淆。系统错误必须停产后用真实原稿和反例统一修复；再付费写一遍不可靠。
2. **Node/Python 对同一原表显示理解不同。** 双写数学符号、DOM 单元格与原始 TeX 等问题在发布边界才暴露。原表错误不属于正文局部补丁可以改变的范围。
3. **第一个阻断掩盖后续独立问题。** 修一处再暴露下一处，反复制作清单、重跑资格、重新审稿。诊断应收齐可独立执行的检查，依赖失败的后续项标明 blocked_by；最终完整 parser 仍须通过。
4. **预览没有完全重放真实调度。** completed-core 私有上下文、pending 义务、诊断迁移、旧付费候选与新空候选的选择，均影响下一请求。预算保护正确阻断，却被误当成“应当可局部恢复”。准备结果必须来自同一真实生产函数。
5. **临时资源观测影响生成身份。** GitHub 探测 deadline 曾改变 Reader 输入。不能冻结错误状态；应在正常身份与评分重放边界中明确处理资源变化。
6. **保存门槛晚于方案预检。** 预览参数通过并不代表真实 pending/父稿组合可保存；这次 Teacher 的 tag-only 父组合在正式保存时才暴露。需要在付费和人工方案提交前检查真实保存门槛。
7. **重复验证放大工程往返。** 69 篇一次成功资格原耗时约 27–29 秒，内部 105 次 Python 启动；状态回写、批次 reconcile、保存及汇总反复调用。零请求也可以耗费数分钟。

## 已落地的优化与验证方式

### 状态回写只计算一次当前资格

提交 `a0414fcf`。`scripts/digest-status.js` 对同一行当前稿只调用一次完整资格，只有失败稿才查询旧可用正文。公共合并入口仍自行核验，不接受外部 success 标志。保留最新失败、pending 和旧成功稿的原规则。

真实 DuET/Detection/Teacher 三稿：资格调用 12→3、旧正文检查 6→0，4.497 秒→1.266 秒。前后状态结果 SHA 完全相同：`3dedac46428b50378b2e8c51cb872dd4b6695f01dc75c4e896d85ff81c06f83f`。状态、死锁 owner、pending/latest-failure 回归均通过。该 72% 是三样本状态计算耗时下降，不是整个日更提速比例。

### CI 在独立 runner 隔离分片

提交 `8fc4421e`。每个 Node 版本分别运行 4 个原 JS 测试文件分片、完整 Python、完整语法与数据检查；共 12 个独立验证 job。测试文件来自 `package.json.scripts.test` 的真实集合，使用 Node 原生分片，各自仍串行执行，避免共享目录测试同时写入。

双 Node 汇总要求整组全部通过，失败、取消或缺失不能报告通过。分片命令明确输出“局部验证，不是完整验收”。`npm run verify` 默认完整行为不变，CI 不用 quick；Hugo 集成、Python 两目录和数据验证保留。10 个定向测试包括实际 7 文件跨 4 分片恰好各运行一次的覆盖证明。远端整组耗时应以实际 run 为准，不能从理论除以 4 宣称收益。

### PDF 引文与列单位的纯提取消重

提交 `f4202097`，新增 `scripts/lib/reader-pdf-extraction-scope.js`，接入两项原 PDF 提取适配器。只在一次 Reader 检查的短作用域复用完全相同输入的 Python stdout，不缓存最终资格、来源许可或修复次数；四源前后读取、SHA、原表与逐格比较保持。

key 绑定完整输入、程序与固定依赖、launcher/guard、工作区环境、真实解释器和 PyMuPDF 元数据；每次仍实时检查 sandbox、角色和私有 FD。未知 runtime 不缓存；异常/坏 JSON 不缓存；32 MiB/128 项上限；作用域结束清空，返回独立副本。

真实 69 稿结果仍全部通过，四源读取 597 次不变，Python 启动从 105→55。早期同追踪样本 29.481→23.955 秒，但最终保护补齐后在并行重负载下测得 43.11 秒，不能将早期结果作为最终墙钟保证。需要安静窗口背靠背对照。确定收益首先是完全相同解释器请求减少 47.6%。

### 发布同次调用内复用真实绑定

提交 `e880b429`，修改 `scripts/publish-to-blog.py`。`_validate_generation_input_integrity` 内绑定已完整计算，后续 proof 只组装同一局部结果；保存清单的模式选择、proof、字段也使用同一局部绑定。独立写入前 integrity 和后续 review/push/git_push 边界均重新真实核验。

完整 integrity 从 2 遍→1 遍；保存清单推断模式从 5 遍→2 遍，显式 API 模式从 4 遍→2 遍。不新增跨调用缓存、公开 skip 选项或 record 自报已通过。三真实样本局部边界 5.331→2.934 秒；真实 69 稿完整边界从 144.561→90.596 秒，下降 37.3%，proof/bindings 逐字一致。原 276 份封存文件、正式数据和生成清单均不变；四源逐一字节破坏全部拒绝。它不是整个发布链或日更耗时降幅。

曾尝试逐次哈希约 43 MB 依赖的缓存：Node 启动 14→8，却让三稿 4.629→6.608 秒。该方案已从源码撤回，失败测量仍保留；不能只汇报进程数而隐去实际变慢。

### 运行入口明确显示各大阶段耗时

`run-daily-digest.sh` 对真正执行的阶段输出目标日期、UTC 开始/结束时间和累计秒数；失败同样报告耗时、保留原退出码并停止后续阶段。续跑不伪造被跳过阶段的计时。实际执行替身测试覆盖正常推送后豁免，以及推送退出 23 时不执行任何后续视觉操作。该改动只补充大阶段观测，不宣称已经区分其中所有本地/网络/人工时间。

## 站点和 CI 的独立瓶颈

原 Pages run 总 32 分 55 秒，Unit checks 462 秒，Build and verify 1415 秒，其中 Hugo 自报 1370.171 秒。生成 9935 个页面、2457 个分页和 1385 个 alias；最后 HTML 检查 13773 文件、903513 引用，约 23.6 秒，前置来源/标签检查约 17.4 秒；上传约 29 秒，deploy 约 22 秒。主耗时是构建和测试。

博客 367 测试，363 通过、4 既有 skip。其中一项全站发布选择集成测试约 323 秒，包含六次真实 Hugo 正负例构建。不能删掉负例伪造加速，应优化其共同模板计算。

原源仓 CI Node 20/22 为 16 分 44 秒和 18 分 01 秒；JS 872/945 秒、Python 115/119 秒、语法约 14 秒，安装少于 45 秒。源仓隔离分片已实施，实际新 run 仍需收齐。

博客模板的候选热点为同一分类快照反复扫描、反复对 386 项目录做规范化。只允许在一次 Hugo build 内按完整 SHA 复用不可变快照解析，首次仍执行全部双份目录冲突检查；跨 build 不能复用。需要真实 Hugo 负例和完整产物逐字对照后才接受。带 metricsHints 的隔离 profile 在 15 分钟内未结束，已停止并保留超时证据，不把它当成已定位的函数耗时，也不与无 instrumentation 的原 Pages 时间直接比较。
