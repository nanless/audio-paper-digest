# Manual 全文分析与 API 分析质量对照

## 审计范围

本审计比较两类产物：

- API 链路的 2026-08-17 参考页：VoiceChat-TTS（2608.13831）和 Omni-LiveAvatar（2608.13602）。两篇页面来自已发布的 API 深度分析，保留了方法分阶段说明、实验表格、指标条件、局限和论文插图。
- 离线 manual 链路的 2026-08-19、2026-08-20 分析。manual 不调用远程模型，但必须读取受控的全文快照，并通过与发布链相同的结构、评分、表格和阶段终态契约。

## 差距与根因

参考页的正文不是“摘要扩写”：方法段分别交代输入表示、模块数据流、训练/推理边界，实验段给出数据划分、基线、消融、指标方向和表格，细节段补足复现实验所需的硬件或配置，局限段区分作者承认的限制与尚未验证的外推。两篇参考页分别约 1.3 万和 1.0 万字符，并含 2–3 张与正文锚点对应的论文图。

旧 manual 产物的问题来自架构，而不是单纯字数：

1. `create-2026-08-20-manual-analysis-spec.js` 把每篇全文压成固定的“核心贡献形态/可执行流程”模板，创新点只有三条泛化句，实验段把“没有给出的数字”当成正文，因而没有论文特有的机制、表格和比较关系。
2. `manual-repair-analysis.js` 原先按关键词拼接全文段落，作者/机构、参考文献、图注和架构图无障碍文本可能被选为方法或实验依据；后处理只加“第 N 个证据块/结果证据 N”包装，审计过程泄漏到博客正文。
3. API 链路在 `analysis-engine.js`/`deep-analyzer.js` 中按阶段执行主分析、开源与 demo 扫描、审校、表格修复、方法修复、结构修复、评分审计和插图计划，每个阶段有独立输入证据、指纹和终态；旧 manual 只把同一正文 SHA 复制到多个阶段，不能证明每个阶段实际复核过不同事实。

## 已实施的对齐

- manual 现在从完整全文构造章节感知的句子单元：跳过作者/邮箱/参考文献和图示粘连，方法优先使用 Methods/Architecture/Training 的真实段落，实验优先使用 Results/Evaluation/Ablation 的数字、比较和表格段落。
- 方法、核心创新、实验结果、细节、评分理由和局限都由论文事实组织；不再输出证据块编号、阶段审计过程、提示词复述或“可执行流程”模板。
- 结果段保留可读 Markdown 表格，并把数字和数据集、基线、硬件、指标方向放在同一语境中；图片继续使用来源中的 HTTPS 图并由发布侧的图片门禁过滤。
- manual 阶段 provenance 使用各阶段独立的输入/审计哈希和专属 claim hint；`analysis-contract.js` 的 manual 深度契约检查摘要、方法、创新、实验、细节、评分、局限长度、表格、结果数字和编辑痕迹。
- 明确禁止以下正文表达：`第 1 个证据块`、`证据块`、`结果证据 1`、`方法事实 1`、`实验事实 1`、`实现细节 1`、`manual_complete`、提示词或人工审计过程。它们只能存在于 provenance/测试上下文，不能进入发布正文。

## 验证方式

每批 manual 结果必须依次通过：

1. 全文路径、来源 SHA、prompt SHA 和逐阶段 provenance 校验；
2. 正文结构、八维评分、表格上限、实验数字和编辑泄漏扫描；
3. `npm run validate:data`，确认 canonical、filtered、raw 和 decisions 一致；
4. 博客 generate → review → push 三阶段，以及发布后的逐页内容和图片 QA。

没有通过任一门禁的论文不会写成 `manual_complete`，也不会进入博客生成或 push。manual 是“无 API 的全文编辑/审校流程”，不是把摘要或固定模板冒充深度分析。
