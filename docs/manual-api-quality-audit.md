# Manual 全文分析与 API 分析质量对照

## 2026-08-25 对照结论

本次以 2026-08-14 的 12 篇 API 博客和 2026-08-25 初版的 46 篇 Manual 博客做完整对照。差距不只是图片数量，而是正文的技术叙事能力：8 月 14 日页面通常把研究问题、方法数据流、训练/推理条件、实验比较、复现信息和局限串成连续论证；8 月 25 日初版虽然大多事实可回查，却明显像字段拼装，读者需要自行把分散事实重新组合成论文逻辑。

第一轮 Manual v3 重写、去除短字段拼装并恢复安全论文图后，8 月 25 日独立页的平均页面字节为 15,069.3、平均 143.0 行，35/46 页含图，共 72 张（平均 1.57 张）；方法章节平均 6.98 个实质段落。这证明字数和图数已不是唯一问题：通用图前图后套话、表格证据过粗、精确数字中文化和章节间重复仍会让文章像字段拼装。因此这一轮只能作为问题取证，不得宣称已达到最终验收。Manual v4 的目标也不是把每页机械扩到 19.8KB，而是消除这些读者可见的低质量短板。

## 根因

1. `create-manual-analysis-spec.js` 的两个极端都造成过问题：早期把 `editorial.method/results/details` 当成替换值，会静默丢弃短字段事实；随后改成把路线短字段整体前置，又让同一数据流和贡献在长文前重复一遍。v4 明确把短字段留作审计输入，要求 `editorial` 自身成为完整、无重复的读者正文。
2. Manual 记录按字段独立撰写，缺少统一的篇章职责：摘要没有问题—机制—证据—边界推进；方法未稳定闭合输入、组件、训练/求解和输出；创新容易退化为名词列表；实验缺少基线、消融、指标方向和负面结果；局限把作者证据与审稿人推断混在一起。
3. 八维 `scoringReasons` 只要求存在和总长度，曾出现“某维度认可……”模板及清晰度、可复现性理由错位。分数虽然能算对，理由并没有回答对应维度。
4. 全文抓取已经保存 `imageInfos`，但 8 月 25 日人工 records 用空 `selectedImageUrls` 批量关闭图片。canonical 有候选却没有正文插图；博客 review 也就无法审查图注、邻文和图文关系。此前出现资助方 logo 误选后，修复走向了另一个极端。
5. Manual provenance 复用了 API 阶段名称和 prompt SHA，却没有明确说明这些只是人工覆盖检查，容易让状态读者误以为开源扫描、审校、评分和插图模型实际运行过。
6. `manual-review-blog.py` 只接收批次级八项布尔值，随后给所有文件写 `deterministic_only`。这不能证明 47 个页面分别检查过技术叙事、事实、实验、复现、局限、评分和图片。

## Manual v4 的质量等价契约

Manual v4 不复制 API 的模型调用过程，但必须在读者可见结果上达到同等职责覆盖：

- `prompts/manual-analysis-record.md` 是人工写作规范并进入 spec/canonical 复用指纹。摘要须形成连续论证；方法至少五段并覆盖输入、组件数据流、训练/求解、推理/输出；创新至少三项且每项交代既有缺口、本文机制、实验证据和边界；实验写明数据、基线、指标方向、关键数字、消融或对照和负面结果；细节覆盖数据、目标/优化、超参数、硬件、推理部署中的至少三类。
- 组装器把 `method/method2/method3/innovations` 保留为证据与阶段 provenance，不再把这些短字段机械前置到完整 `editorial`。面向读者的 `editorial.method` / `editorial.innovations` 必须自行吸收输入、数据流、训练、推理、证据与边界；没有 editorial 的兼容记录才使用显式路线图回退。它同时拒绝跨论文模板复用、篇内跨章节复制和流程元话语。
- 局限必须显式分成“论文证据直接支持的边界”和“进一步审视”；评分必须恰好八条、逐维绑定论文事实与扣分边界，禁止通用维度模板和跨维度理由。
- 图片候选统一复用 `deep-analyzer.js` 的排序与安全过滤。Manual v4 不再自动选图或生成通用邻文：有合格候选时必须显式给出 1–4 张 `selectedImageUrls`，并逐图绑定同序的锚点、后续结论、读图任务与可见证据。资助方 logo、页面 chrome、赞助素材和碎片子图说明被排除；下载仍经过 HTTPS、公网 DNS/IP、重定向、MIME、字节上限、魔数和缓存 SHA 门禁。通过的图片按稳定段落 ID 插入方法、实验或细节正文，插图计划与诊断进入 image manifest 指纹。
- Manual 的兼容阶段统一保存 `executionKind=manual_attestation`。逐阶段 prompt、输入、claim、审计和输出 SHA 仍可复核，但任何文档和状态都不得据此声称实际执行过 LLM API 阶段。
- 博客人工审查升级为 attestation v2：generation 中每个文件都必须绑定精确 SHA、独立 notes，并确认标题元数据、技术叙事、事实、实验比较、复现信息、局限、评分和图片。receipt 使用 `manual_semantic`，push 会重新核对逐文件集合与 SHA；批次级勾选不再足够。

## 不等价边界

Manual v4 仍不是 API 流程的实现替身：它不会调用主分析、开源扫描、gap-fill、方法/表格/结构修复、评分审计或副模型插图规划。`manual_attestation` 表示人工对这些职责做了可审计覆盖，不表示对应模型执行过。反过来，API 调用次数多也不自动代表文本质量高；两条路线最终都必须通过相同的公开正文结构、事实、表格、图片、发布和远端门禁。

## 批次验收

每批 Manual 结果必须依次通过：

1. 完整全文、指定版本、来源 SHA、人工写作 prompt、证据账本和逐阶段 `manual_attestation` 闭环；
2. `full-text-evidence-v4` 的论证、方法、创新、实验、复现、评分、双层局限、结构化结果声明、可读性 rubric、模板复用和编辑泄漏门禁；
3. 图片候选过滤、安全下载、正文插入、图注与邻文语义复核；
4. `npm run validate:data` 与完整 Node/Python/shell CI；
5. 博客 generate 后对全部独立页和汇总页签发逐文件 Manual 语义审查 v2，再由普通 push 验证 Git 基线、精确变更集和远端 OID；
6. 默认日更还要在发布后重新规划并目检失效的 TOP 10 长图和汇总封面；用户显式排除生图时必须停在博客发布验收，并如实报告视觉状态未完成，不得将旧资产冒充本轮成品。

任何一步失败都不能写成已完成。Manual 的定义是“无 LLM API 的全文人工编辑与语义审校”，不是摘要扩写、字段拉长、模板拼接，也不是用兼容状态冒充模型阶段。
