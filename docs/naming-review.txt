这份文档保留最初研究的基线、问题分类和迁移方案。统计来自 b388b883e17f0a59d799d17c69a1033907bdbb88，不代表当前缺陷数量。当前修正范围、验收状态和剩余问题见 docs/refactor-progress.txt；各批完整旧记录保存在该文件链接的固定 Git 版本中。下文的已完成和待处理说明也应结合当前进度阅读。

为什么要改 taxonomy

taxonomy 意为分类体系，是分类与信息组织领域已有的术语。W3C 的 SKOS 文档也使用这个词，不能仅凭它出现就认定代码由 AI 编写。仓库历史显示，共享标签词表在 d0b3ab2 引入，后续逐步接入正式分析、标签检查和发布；这些名称有业务背景，但并不适合出现在所有位置。

本项目实际需要表达两件事。一件是标签词表，其中保存标签名称、别名、分类维度、上下级关系和启用状态；另一件是标签规则，负责解析标签、检查主任务与主方法、判断数量和层级是否符合要求。把两者都叫 taxonomy，读者必须反复进入实现才能分清对象。普通说明应使用“标签词表”或“标签规则”，代码则分别用 tagCatalog 和 tagRules。

同样，buildPromptProjection 返回的是提供给模型的标签文本。名字只说“投影”，没有说明生成了什么，改成 buildTagPromptText 更直接。这里不需要换一种理论来解释程序，需要让名称指向实际输入、操作和返回值。

已经确认的问题类型

名称没有交代对象。taxonomy 有时表示词表，有时表示规则服务；canonical 在部分函数中只是当前保存的分析记录。词表可叫 tagCatalog，分析记录应按用途叫 storedAnalysis 或 analysisResult。表示标准网页地址的 canonical 则有明确含义，不应误改。

同一抽象词用于不同操作。projection 可以表示提示词文本、给读者展示的摘要与评分理由、遮住可修改字段后的全文，也可以表示去空白后供页面比较的内容。这些返回值并不相同，应分别说明“生成标签提示文本”“提取展示内容”“遮住分类字段”“提取页面比较内容”。不能将它们统一改成另一个宽泛名称。

比喻取代了业务对象。表格修复中的 donorSectionPath 实际是原表所在小节，donorGlobalTableIndex 是原表编号。代码和提示词可以使用 sourceSectionPath、sourceGlobalTableIndex，但这两个现有名称属于模型输出与修复计划接口，必须连同解析器和旧计划兼容一起迁移。

说明把技术动作写得过于抽象。“已封口 stage 的回放”“精确闭环”“决策投影”需要读者猜含义。应根据实际检查写成“重新核验已保存的阶段记录”“图片前后的说明与插图计划一致”“汇总页展示的摘要、资源情况和评分理由”。错误提示还要说明究竟哪一项不一致，不能只换成“检查失败”。

中文说明重复附带英文。分类维度后再写 facet、连续使用 runner/binder/sealer，并没有增加信息。普通说明应使用完整中文，只在确实需要定位代码或字段时引用一次原名。英文文档中的自然英文以及 API、SHA、JSON 等明确技术名称不属于这类问题。

名称夸大了检查结果。“封存”“已核验”“可用”各有不同条件。来源文件已保存不等于论文内容已独立审查，链接可达不等于许可明确或能够复现。改名和改文案时，应按照实际条件描述结果，不能借清理表达改变检查规则。

最初的基础函数迁移方案（已实施）

最初方案按以下对应迁移 Node 函数：loadTaxonomy 改为 loadTagCatalog；validateTaxonomy 改为 validateTagCatalog；createTaxonomyRuntime 改为 createTagRules；getDefaultTaxonomyRuntime 改为 getDefaultTagRules；buildPromptProjection 改为 buildTagPromptText。Python 对应迁移 load_taxonomy、validate_taxonomy、build_prompt_projection、prompt_projection_sha256，分别使用 load_tag_catalog、validate_tag_catalog、build_tag_prompt_text、tag_prompt_text_sha256。

词表模块的局部 taxonomy 使用 tagCatalog 或 tag_catalog；调用词表模块的 taxonomyApi 使用 tagCatalogApi，标签规则服务使用 tagRules 或 TAG_RULES。有一处 taxonomyApi 调用的却是历史分类分配模块，应单独改成 tagAssignmentsApi。每处名称都按实际职责判断。

实施时已同步迁移导出、导入、成员调用、依赖注入和原测试，没有添加一组长期并存的旧函数别名。跨端测试中嵌入的 Python 程序也需要同步。Python 参数还要检查关键字调用；对象简写要分清局部变量与字段。例如变量改名后，原输出仍需写成 taxonomy: tagCatalog，以保留当时已有的保存格式。

这批修改确实改变模块函数接口，也会改变函数名属性、未来错误栈和源码身份。不能声称接口或所有 SHA 都不变。标签文本、词表原字节、选择结果、持久字段和检查规则则应保持；旧凭证不因改名重新签发。

已经完成的迁移与后续工作

分类基础函数已按上述方案迁移。模块文件名、命令、导入和实现身份路径清单也已同步更新，原 paper-taxonomy.js 的职责现在由 tag-catalog.js 与 tag-rules.js 表达。实际提示文本生成使用 buildTagPromptText；新请求采用 paper-tag-prompt-text-v2，旧提示版本只用于按原记录重建核验文本。

解析缓存的新写入字段为 tagValidation，标签阶段和检查点的新写入键为 tagSelection，阶段格式为 paper-tag-stage-record-v2。taxonomyValidation 和 taxonomySeal 用于读取旧记录，读取器按原字段核验；同一记录混用新旧字段会被拒绝。更名不授权手工改运行文件，也不会自动给旧记录补发新凭证。这两项格式迁移已完成，不能再把它们列为尚未开始的工作。

仍需按用途检查局部变量、私有函数、注释和诊断，区分词表、检查结果、分析正文、阶段记录和页面展示内容。每组都应查真实返回值及完整调用链；错误文字被重试、修复或测试读取时，消费者须一起处理。提示词修改还须核对第一个围栏、占位符、输出格式和阶段指纹。

facet、projectionSha256、freshRewriteProvenance 以及表格修复计划中的 donorSectionPath 等保存字段和模型接口仍有消费者。迁移这些接口前须设计版本、旧格式读取及冲突拒绝规则，并同步写入方和读取方；不能因局部名称已经改为 sourceSectionPath 就认定模型格式也已迁移。词表、历史记录和页面中的旧协议名称须按各自用途判断，不能批量替换字符串。

历史文档继续保留当时的数字、字段和完成范围；当前操作说明应使用现行接口，并明确旧格式的读取方式。

如何判断修改是否可靠

先冻结具体名称、文件和修改范围，再交独立代理审查。改名之后按批准范围逆还原，核对完整语法树、字节和输出字段；其余文件与 Git 基线一致。复用现有分类、解析、恢复和发布测试，并运行默认与 Manual 的完整离线验证。只有实际实施和测试通过后，才在进度记录中记为完成。

命名原则是让读者能从名称看出对象和操作。使用常见词，但不牺牲准确性；根据业务选择具体名，不为显得专业加抽象词，也不为缩短名字使用陌生缩写。自然语言写清实际条件与结果，避免省略主语、机械排比和重复译注。

外部依据

W3C SKOS Core Guide：https://www.w3.org/TR/swbp-skos-core-guide/
这份标准说明 taxonomy 属于已有的信息组织术语。它能解释词的来源，但不能证明项目中每个使用位置都合适。

Google JavaScript Style Guide，Naming：https://google.github.io/styleguide/jsguide.html#naming
该规范强调名称应便于新读者理解，避免只有项目内部才懂的缩写。本项目依据实际对象选名，不机械照搬全部格式要求。

Python PEP 8：https://peps.python.org/pep-0008/
该规范将可读性作为目标，也明确提醒不要仅为风格破坏向后兼容。这里采用分批接口迁移，并保留旧数据读取边界。
