# 维护指南

## 受众与原则

本文供修改默认 API、共享发布、提示词、数据格式或文档的维护者使用。维护时先找到一条配置或规则在哪里生效，再确认哪些程序读取它；只改一份说明，不能证明 Node 与 Python 两端都已经使用新规则。

先定位配置或接口的实际实现，再同步使用这些配置或接口的程序、测试与说明。旧记录核验与独立人工审查见 [manual/README.md](../manual/README.md)。

## 一次修改怎样完成

1. 先读对应流程和当前实现，确认要改的是入口、共享模块还是旧记录兼容读取器。
2. 列出受影响的调用方、来源记录、阶段指纹和测试；先保留工作树里其他人的改动。
3. 用临时目录中的样例复现问题，修改后验证真实正例和相关负例。付费原稿回放另存带 SHA 的运行证据，不塞进依赖当前日期的普通单测。
4. 按改动影响安排检查。只改说明文字时，核对命令、链接、事实与格式，不启动论文重分析或全批重跑。实现改动的定向检查通过、版本稳定后，运行一次完整 `npm run verify`；分套件或分片通过不能代替完整汇总。
5. 交叉审查事实、来源、预算和发布边界，再核对 Markdown、链接与文档命令，使用具体中文提交并及时推送。

项目最终只保留 `main`。审阅可以在不写入正式运行数据的隔离环境进行。已有临时分支时，先确认有效修改已经合入 `main`，再清理分支，并核对远端提交。暂存时按文件区分本轮改动与工作区里已有的修改。

完整语法检查排除客户端固定的构建、SDK 缓存和验收副本目录（两端 `.build`、`.qa`，以及 Android 的 Gradle/CMake 输出）。这些目录中的历史项目副本不属于当前正式源码；客户端正式资源、构建脚本、测试，以及其他位置同名的 `build` 或 `.qa` 目录仍正常检查。排除路径由 `verify-project.js` 明确登记，不随任意 `.gitignore` 规则变化。

文档与论文讲解按[写作约定](writing-guide.md)组织；参数、协议名和强制条件以实现及权威文档为准。没有新证据或新改动时，不重复运行刚通过的相同子集。

新增 `scripts/` 下的模块时，同时更新 [脚本职责索引](../scripts/README.md)，并运行原有的 `tests/scripts-index.test.js`。新增 Python 模块还须运行 `tests/python/test_runtime_guard.py`：内部库也可能被直接执行，正常导入通过不能代替直接入口的沙箱拒绝检查。这些检查纳入本次定向验证，完整验收仍按上面的流程执行。

## 不可破坏的边界

- 默认日更始终使用 LLM/API；API 错误不能使其切换 Manual。
- 项目配置来自根 `.env`。外部子进程使用规定的最小环境，不能继承无关凭据。
- Muse 与 arXiv 必须使用项目代理；其他 LLM 默认 `agent:false`。
- 同篇分析及共享 JSON 更新必须持锁，并在锁内重读。
- 检查点指纹变化只使必要阶段失效，不能无条件清空全部成功结果。
- 日更分析、Reader 和发布只读取绑定的文本、PDF、来源元数据与清单。文件缺失或不符时，目标仍为北京时间当天才可重跑 `digest:prepare`；历史日期保留失败记录，按历史维护处理，不能用旧缓存补源。
- 历史 arXiv 每次来源获取都重新保存并核验官方四份文件；历史会议核验绑定的本地元数据/PDF SHA。两者都不能把旧博客、分析或 Reader 正文作为写作来源。
- generate、review、push 各自独立；review 只读最终字节。
- 发布资格证明、页面 SHA、Git 基线、远端 OID 和视觉任务须分别核验对应关系。
- 项目脚本不调用图像 API。

## Prompt 修改

`loadPrompt()` 读取 Markdown 的第一个围栏代码块。修改时逐项确认：

1. 占位符与调用方一致。
2. JSON 或章节结构与解析器一致。
3. 内部示例不会被误认成外层代码块。
4. 提示词 SHA 进入正确阶段指纹。
5. 重试反馈能定位问题并限制修改范围，不使整篇内容无故变化。
6. 读者正文没有模板句、证据 ID 或流程说明。

工作树只保留现用模板，路径统一位于 `prompts/current/`。阶段与文件的对应关系以 `scripts/lib/prompt-current-records.json` 为准，`scripts/lib/prompt-contracts.js` 提供读取接口。现用协议使用稳定名称和格式指纹；修改正文时还会核对完整文件及实际模板的 SHA-256，不按文件名推断兼容性。

模板覆盖主分析、正文审校、评分、核心摘要、读者文章、局部修复、结构修复及事实和术语纠正，详见[提示词索引](../prompts/README.md)。新分析使用现用模板；恢复已有付费候选时，先核验其原阶段、请求输入及来源，不因模板变化重新计数或换成新请求。

筛选模板为 `prompts/current/filter.md`，说明实际音频输入与评测、音乐生成、口语轮次控制和说话人分段错误的相关范围，并区分声音方法或系统的贡献与固定基准验证。通用理论、表示、算法或采样与音频线索交界的候选，先核验官方方法和实验材料。旧会议筛选仍核验原声明、原模板 SHA-256 和原正文，不能将现用正文代入历史请求。提示词格式也不能代替读者文章的内容核验。

旧提示词不保存在工作树。`scripts/lib/git-prompt-evidence-index.json` 登记原路径、Git 对象及整文件 SHA-256；受控读取器取回原字节，核对整文件和首个围栏代码块，同时保留原来源、检查点和付费记录。缺失或不符就停止，不能用现用正文补签。原请求允许的恢复保留已绑定的提示词身份；旧稿的只读重验不请求模型，也不增加请求额度。原本缺失的字段只按明确登记的历史规则解释，未知声明或指纹直接拒绝。

Git 证据索引不保存旧全文，也不授权新建旧任务。读取失败、Git blob 缺失或整文件/模板 SHA 不符须保留错误并停止，不因文件名或 SHA 形式合法而放行。测试使用严格读取器核验真实历史字节，不要求退休 Markdown 文件仍在工作树。

评分提示词还须保留八维顺序、范围、开源状态对应的六个固定分值、证据 ID 和代码计算的上限。Reader 提示词须抽检术语组合的解释、表格前后的说明和相邻图文，并保留未传入像素时不能猜图的限制。

## 词表与多级展示修改

三流程只从当前386项九维目录选择有证据的直接概念；总目录保留零计数节点，文章只显示选中项及祖先路径。词表原字节、分类证明和显示路径分别核验：保留旧SHA归档及原付费记录，严格纯追加只能只读重放，不因显示升级重新签名或追加模型次数。词表版本、站点成对资产及各发布边界见[标签规则](tag-display-policy.md#三条流程共用的目录与呈现)。

Python标签正常化只对长度不超过256的内置不可变字符串使用最多8192项的有界LRU缓存；不缓存词表对象、来源或分类资格，每次调用仍完整核验当前词表，变更与坏数据照常阻断。此优化减少重复字符串处理，不改变标签选择、原SHA或检查标准；原生进程崩溃仍按真实错误单独诊断。

修改 `tag_presentation.py` 时，须同时检查日更单篇/汇总、会议单篇/汇总和历史单篇/汇总的实际输出及传递依赖指纹；路径包含当前部署前缀，文章块不能出现兄弟概念、空分面或全目录。站点目录资产上线与论文页面重新生成是两个验收对象：已有批次要改变呈现，须生成完整目标页面集合，按实际内容SHA复用或重做独立审查，再推送和逐页核验。不能只提交共享代码或词表快照就声称旧文章已更新。

还须核对源Markdown和实际网页的分工：源文件保留有边界的共享分类块，单篇页头已有经核验分类时，网页正文仅按唯一完整成对边界去重，汇总保留。覆盖无边界旧稿、缺失/重复/倒序边界和真实Reader邻文，避免误删正文。站点模板修复须独立精确审查、中文提交推送，再以新博客基线执行正常整批生成/审查/推送，不扩大页面发布器允许写入的路径；最终检查应同时证明分类不重复且全部Reader内容仍在。

表数量不足诊断使用稳定 `code`、`requiredCount` 和 `actualCount`。修改相关提示或说明时，须同步检查生产、收集、修复、反馈和用于判断能否继续的输入指纹；新结构字段不能退回解析自然文案。详细字段与旧格式的有限兼容范围见 [数据格式](data-format.md) 和 [Reader 写作](reader-writing.md)。

组件消融不要求正文使用“消融”一词。对明确的同组件“无X时／有X后”实测对照，Node 分析与 Python 发布共同核验比较问题、同张结果表中的数值和本篇来源的连续陈述；假设、未来计划、否定或他人实验不能充当已完成证据。回归同时保存真实失败检查点及原封存全文，按 SHA 核验后保持原字节重放，不以构造正例代替真实故障。

### 原表显示与单位证明

偏好向量表的分组列单位须同时核对完整原DOM网格、唯一的两层列路径，以及封存PDF中完整表头和每一行的连续原字符。原HTML的重复数学显示仅在PDF逐行确认后可用于显示投影，原来源文件不改。均值差合并格须保留原跨度与同指标单位；正常读取和保存稿冷核使用同一规则，错列、缺行、错单位、伪造PDF引文和作用域内来源漂移仍拒绝。

封存 PDF 中的累计配置表和组件/参数消融表，只有完整表头、逐字表注、全部行身份及实际分隔线共同闭合时，才能使用对应的独立列单位证明。累计损失的数学字形还须核对原字体与下标位置，不能把普通字母猜成公式。正常排版在同一格的均值与不确定度两侧增加空格时，只允许合并这些空格；均值、误差项、符号与精度均保留。新增规则须验证真实完整表及错误数值、缺行、分带变化、伪造引文和保存后的来源冷核。

包含变化注的前端、预算、泄露时长与输入条件表，使用单独的完整原表识别规则，不放宽普通数值格。均值、不确定度、方向、阈值和变化量必须整格逐字重放；参考行与错误率变化单位另由同篇 PDF 的完整统计说明核验，不从展示均值重新计算。量级字母、秒单位和原下划线须保留，短线按对应数字字形定位，额外或重复的表线不能被忽略。
Python 发布冷核也须重放这条完整网格规则：先核当篇四份封存来源、完整结构化来源与实际 PDF 引文，再匹配每个显示单元格；不能只在 Node 分析端接受，或仅凭复制的证明对象推断单位。该发布实现同时纳入生成和审查指纹。
原 DOM 单元格的可见变量副本与明确 TeX 注解逐字符对应时，发布视图可仅显示该 TeX；上下标顺序只能采用注解明确给出的同组字符。带句点的图注控制记号只在同一图片及逐字对应的完整原图注中显示为行内代码，代码、普通正文和其他 HTML 不扩大处理。保存的 Reader、来源与图像记录保持原字节。


## Reader 专项修改的核对边界

完整表格格值的符号副本投影由 `lib/reader-source-display.js` 和 Python 发布器同步执行。`✓\checkmark`、`×\times` 仅在完整格且显式同值时合并，保留原 DOM、数字、精度、单位和来源 SHA；错配符号、运算续式及裸重复必须仍被拒绝。回归须包含完整真实矩阵与丢格、坐标、单位篡改，不能只测字符串替换。

Reader-only 完成判据必须重放真实父子反馈组合，不能把已通过的原签名按子包单独重算。只读完成作用域禁止写盘和模型请求；旧父恢复须在调用分析前核验主检查点，并在每次保存前拒绝 Reader 之外的上游变化（图片下载阶段、图片清单与图片叙述合同除外）。错误路径应完整还原内存及保存回调，回归同时覆盖原对象和不同的传入检查点。真实旧包、四来源、原稿和负例都要验证，详见[事实反馈恢复](reader-explicit-retry.md#已完成主文的独立-reader-事实反馈)。

## 修改数据格式与校验规则

主分析与博客发布分别执行 Node 和 Python 校验。修复来源绑定的列类型、表后边界或负面证据误报时，两端须用同一份真实保存稿与封存来源验证；先收集完整批次的实际阻断，再统一修复。正向的耗时、能耗“降幅”本身不代表负面结果，不能用这个词替代具名对照、指标方向及原文中的实测结论。专项检查通过只证明该项规则，不代替正常生成、审查和发布资格。

### 旧输入清洗是否损坏字符

模型请求保留数学字母和姓名中的合法 Unicode 字符，替换孤立的 UTF-16 代理字符。来源记录注明 `model-text-sanitization` 和实际结构指纹；重算已经付费的请求指纹时，仍使用当时的算法身份。旧结果在生产恢复、提升、暂存及日更发布前，须从已核验来源证明输入没有受旧清洗影响，或按原来源完整重分析。新版标记不能代替 TXT、PDF、runtime、manifest 与来源 SHA 核验。重分析前保留带 SHA 的旧正文和阶段快照，不改封存来源字节。

无法重新核对完整输入时，不得推定旧清洗没有影响输入：没有新版标记的旧 direct 会议暂存即使元数据是普通中文，也可能因缺少完整原文而拒绝复用；缺少可重新读取并核验的封存来源引用的明确 API Reader v2/v3 文件不得直接重新生成或续推。Manual、已发布页面只读和旧成功结构保持原规则。本次代码升级不自动调用模型或改写旧博客；有完整已核验来源且不含受影响输入的旧记录保留复用资格。

Reader 的数字来源核验保留完整数值，不能把 `130130`、无 TeX 依据的粘连小数或重复符号猜成半值。只有明确 TeX 结构且两侧数值、单位相同的显示副本允许清理。Node 恢复和 Python 发布会重核旧表格绑定；依赖旧半值别名或不对应原始单元格的旧记录将拒绝复用，须按原来源修复并重新审查，不自动改写旧正文。原文同段同时包含完整值与合法半值时，仅凭两数同时出现无法认定旧半值错误，仍须核对其对应实验与表格位置。反馈须保留原文的百分数、比率或无量纲口径，不能自行补百分号或删掉重复数字。

新增字段前说明它的用途和核验方式：

| 用途 | 要求 |
|---|---|
| 原始事实或来源 | 纳入相应输入或来源 SHA |
| 派生缓存 | 能从原始字节重建 |
| 恢复状态 | 保存版本和阶段指纹 |
| 发布凭证 | 对应精确文件及必要外部状态 |
| 可选诊断 | 不得单独改变业务完成结果 |

结构变化须同步 Node 校验器、Python 发布器、测试样例、迁移和历史兼容，以及 `validate:data`。SHA 只核验字节与对应关系，不能代替内容审查或证明部署成功。

## 批次调度与效率验证

新分析入口使用公共 `analysis-failure-rounds.js`：首轮选定全批，每轮每篇一次正常流水线，全部在途结果和保存完成后只续可重试失败集合。`batchMaxRounds` 与单阶段请求尝试、Reader付费追加分开；人工建议只报告，不改失败和发布资格。配置、范围及费用边界见 [三流程批次规则](three-workflows.md#全批轮次与失败集合)。

调度测试须证明第二轮不能抢在第一轮剩余论文或最终保存之前启动；完成项不再请求模型，非可重试/运行级失败不重跑，停止信号在轮次边界生效。保存异常不得被汇总成普通失败，也不得提前写 complete。跨轮继续同一来源和 Reader 候选身份，原失败、费用和预算耗尽状态不能被调度刷新。

日更首遍恢复用 ID 索引消除每篇重复读取整批旧结果，初始化按 ID 映射合并；内存只保留每篇最近尝试，所有逐次失败、检查点及费用仍持久保存。这是本地读写和查找优化，不是来源核验缓存。会议同批来源证明一次按 state SHA 合并，每篇 claim/result 仍即时保存；历史已由当前 renderer 暂存的隐式成员跳过，过期 renderer 只在原分析通过时重渲染。会议审查分块通过缓存还绑定整页、块索引和块内容 SHA，不能跨变更页面借用。

## 并发与原子性

JSON 保存使用原子写入。读改写时取得公共文件锁，在锁内重读最新正式分析记录，只合并本次论文或字段，再递增 `generation`。不能把锁外的整份旧数组写回去覆盖其他任务。

长任务定时更新运行或锁记录，并设置有效期限；只有程序确认持有者与期限符合失效条件时，才能回收。Node 分析队列遇到运行级错误会停止领取新论文。Python 页面审查通过 `run_bounded_llm_tasks()` 按指定并发数量安排任务，运行级故障后停止提交新任务，等待已开始的任务保存结果，再报告原故障；保存同时失败时也保留该异常。普通内容拒稿保存审计后继续剩余页面，最终汇总阻断；服务、存储、字节漂移或凭证损坏仍按各调用方的运行级故障规则处理，不能把任意异常转成内容失败。

Python `path_config.file_lock()` 保留原目录和持有人格式，回收前核对目录、持有人文件及字节，并通过单独的回收标记协调回收者。等待线程遇到同 inode、本人拥有的普通单链接持有人文件正在更新，或同目录正在创建/移除持有人记录时，会在原超时内重读；身份替换、未知文件和超大记录仍直接拒绝。创建失败与释放时也只清理本次仍持有的文件；未知文件和后来取得的锁保留。临界区正常结束时会报告续租失败；若临界区本身抛错，仍传播业务异常，不能据此认为已执行的写入已回滚。它与博客 Git 锁是不同协议，不能互换。

## 安全与日志

- 对外资源使用 HTTPS，回环地址测试除外。
- 外部资源重定向逐跳核验 DNS/IP。
- 日志每个非空物理行使用毫秒级北京时间戳。
- 日志和 `.env` 使用 `0600` 权限。
- 日志脱敏认证头、Cookie、token、secret、password、实际配置密钥和 URL userinfo。
- `data/`、`logs/`、`.env`、备份及缓存不得提交。

Python 日志清理会把目录读取、文件检查及删除失败写入 `problems`，同时输出脱敏告警；同一失败文件不会在本次清理中重复删除。不存在的日志目录仍视为合法空目录，清理诊断不会更改模型请求的结果。

## 运行存储诊断与清理

`npm run storage:status` 只读统计文件大小与数量，包括受保护的日更来源、历史来源/计划/私有页面、会议来源及异常响应保全目录。它们是可重新核验的输入与运行证据，`storage:prune` 不删除。状态命令遇到目录读取错误会显示路径和原因，并非零退出，已读到的统计仍会显示。

`npm run storage:prune` 默认只扫描引用并输出预计删除清单。status 和预览可在任务运行时使用，不要求停止写入者。真正删除须先人工核对清单，并停止全部抓取、筛选、分析、博客生成/审查/推送和视觉任务，再运行：

```bash
npm run storage:prune -- --apply
```

保留期默认 30 天，可用正整数 `PD_STORAGE_RETENTION_DAYS` 覆写，也可写入项目 `.env`。清理范围是 `logs`、`image-cache`、`api-reader-assets`、`visual-reference-inputs` 和三个已无程序读取的旧调试目录：`deep_analyzer_input_output`、`filter_input_output`、`iclr_filter_input_output` 下的**全部普通文件**，不限 `.log`；因此 `logs/` 中不得放置手册、脚本或证据文件。三类缓存删除前扫描 `data/current` 与 `data/archive` 的正式 JSON，核对绝对/相对路径和 URL SHA-256 引用。正式分析 JSON、发布/视觉清单、归档成品及博客文件不在白名单内。

JSON 损坏、符号链接、路径逃逸或计划后文件变化会在删除前整批阻断。本机锁持有者 PID 存活，或远端/非法持有者无法可靠判活时，同样拒绝删除；清理器不替调用者删锁。它会复扫引用与候选，但扫描和删除之间没有所有写入者共用的事务锁，仍可能发生竞态，因此 `--apply` 前停写是必要条件。预览可以报告这些阻断，不能把预览成功当成删除授权。

## 运行前体检、运行中状态与错误指引

开跑前运行 `npm run doctor -- --offline` 做只读体检：Node/Python、依赖、`.env` 权限与模型配置、HTTP CONNECT 代理、工作区角色、`data/current`/`data/runtime`/`logs` 占用、博客仓库未提交改动与目标日重叠、账号池冷却情况。默认不联网；加 `--network` 才用项目代理对 arXiv Atom/官方 OAI/RSS 各探测一次，并按 RSS `pubDate` 判断目标日公告是否已生成。任何 ❌ 项会给出可复制的下一条命令并返回非零退出码；命令不写文件、不发模型请求、不打印密钥。

运行中用 `npm run digest:status -- --date YYYY-MM-DD --watch`（默认 10 秒刷新，`--interval N` 可调，`--json --watch` 每行一个 JSON）查看阶段、数量、失败列表、最近日志、账号池可用数、本次费用和无进度提示；默认不带 `--watch` 时输出与原来一致。费用按日期聚合 `data/runtime/llm-usage`，不联网、不推算未记录的费用。

轻量监控遇到审查记录的 `postPublishVisuals: required` 时，仍按两类任务清单推导内部 `visual` 阶段，不使用生成清单的发布前标志省略其中一项；人类可见名称为“发布收尾”。该字段只接受已知的单篇或旧维护不适用模式，旧审查记录缺该字段时沿用原生成标志，未知值不表示完成。

这个视图不核验完整图片资产、当前发布豁免或部署网页，因此默认不生图的批次也可能停留在“发布收尾”。建议从 `./run-daily-digest.sh DATE --from visual` 继续，由正常日更入口重核发布并按持续设置登记不生图，不执行图片准备或生图。该提示不授予任何完成资格；最终仍查看普通 `digest:status` 的实际豁免核验，再核对部署和全部目标页面。

主要生产入口（fetch、deep、batch、reanalyze、Reader 刷新与博客三阶段）在打印原错误后会追加 `[下一步]` 指引（原因、建议步骤、可复制命令、文档位置），不吞原堆栈、不改变退出码。各阶段还可写人话摘要到 `logs/summaries/<YYYY-MM-DD>-summary.log`（Node `writeStageSummary` 与 Python `write_stage_summary` 同格式、自动脱敏、目录 0700/文件 0600）；摘要写入失败只告警，不影响业务。

## 抓取前探测与配置检查

- `npm run source:probe -- --date YYYY-MM-DD`：只读探测 arXiv Atom/官方 OAI/RSS 三入口，并判断 RSS 公告是否目标日；失败时给出等待/换入口/官方 OAI 的建议，不抓取、不写数据。
- `npm run llm:accounts`：只读查看账号池每个账号的状态、冷却与最早恢复；账号只显示本次运行的序号，不显示任何密钥或稳定指纹。
- `npm run config:check`：按 `scripts/lib/env-schema.js` 检查 `.env` 必填、类型、范围与未登记变量；不写文件、不回显密钥，支持 `--json`。大小写 HTTP 代理变量均逐项校验，`ALL_PROXY` 仍允许 curl 使用 SOCKS；整数须在 JavaScript 安全整数范围内。检查失败标明具体配置项，不代表每条运行路由都会选择该项，也不改变运行时的代理选择或整数解析规则。
- `npm run doctor` 与这三条命令都只读；抓取失败时 full-fetch 会追加 `[下一步]` 的限流/5xx/RSS 建议。doctor 比较主副配置的唯一密钥值集合，重复列出同一个值不会误报为部分重叠；集合相同只描述配置关系，不能证明端点属于同一服务或账号可用。

## 恢复决策与清单生成

### 先读失败记录，再选择正式入口

- `npm run recover -- --date YYYY-MM-DD`：只读采集已保存的分析失败、事实义务、页面审查问题及独立的批次审查问题，再按错误码汇总建议入口。日期须为真实日历日期。输出区分文件缺失、不可读、坏 JSON、形状错误、错批与无法确认日期的旧格式；存在坏资料时退出 2。文件缺失时仅提供 partial 预览，默认退出 0，`--strict` 退出 1，`--execute` 退出 2 且不派发。两份资料均可读时也只表示 `saved_records` 采集完成，`semanticCoverage: not_checked`、`scopeComplete: false`，不证明正式来源、完整失败集合或发布资格。`--execute --yes` 仍只调用既有入口并受原入口核验约束。

### 准备人工修正材料，不能据此采纳

- `npm run manifest:new -- --spec SPEC.json [--fact-feedback-file FILE ...]`：SPEC 写 `{paperId, replacements:[{path,value}]}`（1–8 个既有节点），可多次传 `--spec`，或使用数组 / `{papers:[...]}` 覆盖完整当前失败集合。若本次恢复使用事实反馈，须传入同一组反馈文件；命令按正式入口的反馈验证及失败谓词核对集合、重复项与人数限制，dry-run 和 write 均先核对。候选须安全可读、唯一，并对应当前论文、来源运行及来源 SHA，不按修改时间挑稿，也不吞读取错误。输出明确 `candidateIdentity: not_checked`、`paidOrigin: not_checked`；工具准备范围不含完整当前输入身份比较及原付费链重放；正式采纳仍核真实当前来源、原材料与 patch，并执行正常 Reader 及整篇资格检查。默认 dry-run，`--write` 才生成 `data/runtime/operator-corrections-<date>-<uuid>/`；材料准备成功不表示正式资格通过、不授模型请求权限，也不自动采纳。

### 错误码与文字建议的用途

- 错误码字典 `scripts/lib/error-codes.js` 与 `error-guidance` 的规则 id 对齐，供 `recover`、状态报告和文档共用。数字限流提示须为独立状态信号，不把论文编号、小数或相邻文字中的 429 当作状态；arXiv 文字信号按明确主机、独立词或已知代码识别，近似域名不作为官方来源提示。明确的 OAI/RSS 过期诊断保留优先级。文字匹配仅供辅助建议，不替代生产错误类型、来源验证或恢复权限。

## 表格与影响面预检

- `npm run table:check -- --draft FILE [--format json|markdown]`：离线检查表格粘连复写、列数与单位声明，不写数据、不替代正式发布校验。显式格式优先；未指定时 `.md`/`.markdown` 按 Markdown，其余按 JSON，坏 JSON 不回退。JSON 支持正文字符串、Reader 的 `sections[].body`、`markdown` 或 `article`；局部空段可保留，错误正文类型或整正文空白退出 2。围栏按打开的字符与长度关闭，代码样例不因短围栏或混用字符被当作正文表格；这不是完整 Markdown 解析器。
- `npm run impact -- <file-or-dir>`：静态列出改动影响的入口、测试与重验范围，避免改一处规则却漏跑相关流程。
- 审查误报记录使用 `scripts/lib/review-overrides.js` 的严格 schema（页面 SHA、发布提交、逐字证据、复核人），只把匹配的 error 注释为 warn，不放宽真实错误；是否采用由调用方显式决定。

## 发布后网页核验与收尾

- `npm run blog:push -- --date DATE --dry-run`：只列出审查凭证允许的精确文件清单，不 commit/push。
- `npm run verify:web -- --date DATE [--limit N] [--deploy OID] [--wait] [--allow-degraded]`：按生成清单批量请求汇总页与单篇，记录 HTTP 状态、最终 URL 和标题，原子写入 `data/current/web-verification-<date>.json`。`--deploy` 查询对应提交的 Pages workflow，默认仓库为 `nanless/audio-paper-digest-blog`，可用 `PAPER_DIGEST_BLOG_REPO_RUN` 覆盖；站点 URL 来自 `PAPER_DIGEST_BLOG_URL`。

  `--wait` 默认最多等待 120 秒，默认每 10000 毫秒轮询；可用 `--wait-seconds N` 与 `--poll-interval-ms N` 调整。无 gh、部署仍在进行或部署证据不可得时，默认不能完成验收。`--json` 在等待时输出 JSONL（部署快照行、summary、最终结果）。现用保存文件使用 `contract` 和 `schemaFingerprint` 声明格式，并记录 `createdAt`、`partial`、`deploy`、`generationManifestSha256` 和 `publicationOid`。存在 `blog-review-receipt-<date>.json` 时自动绑定其清单 SHA 与发布 OID，`--receipt` 可显式指定。

  页面检查仅要求 HTTP 200、最终 URL 去掉查询参数、片段和末尾斜杠后与期望地址一致、标题包含站点标记，且汇总标题含日期、单篇标题去掉站点标记后长度大于 4。它不核对准确论文标题、H1、canonical 或完整正文；这些须在最终全页核验中另查，不能将该命令通过解释为全部内容正确。

  核对完整标题时，用结果中的 `file` 找到发布提交里的对应页面文件，读取文件开头声明的 `title`，再按 Hugo 的页面标题规则与记录的网页 `<title>` 比对。汇总与单篇都要覆盖。页面内主标题、规范网址标签或正文需要核验时，从实际网页按各自规则检查。两次日更的标题补验见[复盘](2026-11-daily-maintenance-retrospective.md#两次发布留下了什么证据)。

  默认要求完整页面与部署证据：无 `--deploy`、`--limit` 抽样或部署未成功时标记 partial 并返回非零。`--allow-partial` 只放宽页面/抽样 partial 的退出判断；`--allow-degraded` 只放宽部署不可得或进行中的退出判断，不降低页面与凭证要求，也不把诊断记录升级为完整验收。

### 解释疑似误报，不改正式结论

- `npm run review:overrides -- --date DATE --file OVERRIDES.json [--receipt RECEIPT.json]`：只读核对误报解释，按页面 SHA 与逐字 claim 匹配，不修改失败文件或凭证，也不授予正式审查或发布资格。诊断报告 v2 的 `matched` 统计实际命中的解释条目，`matchedIssues` 与 `matches` 记录本次问题位置；`inputDeclaredOverridden` 单列原输入的旧标记，`sourceFailureSha256` 绑定原文件字节。严格退出码由 `currentMatchVerdict` 决定：仍有 error 或未完整解释的失败页退出 1，诊断无阻断退出 0，执行或参数错误退出 2。旧 `pendingBlockedFiles`、`overriddenFailedPages`、`wouldPass` 及 `legacyProjection` 保留旧投影，不能作为新退出依据。此变化会使只靠输入旧 `overridden` 标记的旧调用返回非零。`receiptCheck` 仅报告参考提交字段是否相等，`receiptContractVerified` 始终为 false；字段冲突退出 2，缺字段明确告警。失败文件显式日期冲突同样退出 2；旧文件缺日期时 `failureDateCheck` 明确未比对，`formalScopeVerified` 始终为 false。同一失败页中原有的 `overridden` 位置也须由本次匹配覆盖，不能用另一条新解释掩盖。`--json` 的正常诊断输出为单份 JSON，告警写入 stderr。

### 检查推送后的收尾步骤

- `npm run publish:finish -- --date DATE`：打印推送后收尾清单，包括正式状态、网页核验及当前发布的不生图登记。登记缺失时提示核对正式发布凭证后直接登记不生图；不提示图片准备，也不自行登记或调用图像 API。

`verify:web` 的完整部署结果还要求明确的 `jobVerified: true`。缺 runId、jobs 查询失败或超时、无法解析响应等均保留为未核验，不以 run 的成功结论替代 job 证据。此时结果仍为 `partial:true`；同时显式使用 `--allow-degraded --allow-partial` 只允许诊断命令退出成功，不会把证据升级为完整验收。实际 job 失败、取消或跳过继续返回失败。

## 锁视图与文档一致性

- `npm run locks`：只读观察 `data/runtime`、`data/current` 原有有界目录范围内的锁及博客仓库的共享锁。共享根由真实 Git common-dir 定位，支持 linked worktree；不创建锁根，不修权限。输出 `scanComplete`、`scopes` 与 `problems`，缺配置、读取失败或坏 owner 明确记为未完成，不能把空列表当作无运行任务。完整观测退出 0，部分观测退出 1，参数或观察入口错误退出 2；运行守卫拒绝仍退出 1，并在结构化问题及 stderr 保留明确的外部运行说明，不回显环境标记原值。这是对原扫描结果总返回 0 的收紧。共享锁始终 `alive:null`、`stale:false`，不凭 PID 或心跳授回收权。`--recover` 仅预览，`deleted:false`，不会删除或解锁；`--json --recover` 把候选放入 `recoveryPreview`，stdout 只输出一份 JSON。完成观测也不证明发布空闲、持锁或后续 CAS 已满足。
- `npm run docs:check`：检查根 `README.md`、`README.en.md`、`AGENTS.md`、`scripts/README.md`、`docs/` 与 `skills/` 下全部 Markdown 中的 `npm run <script>` 是否存在于 `package.json`；同一入口还核对文档里写的当前客户端版本（构建号）与 `apps/macos/Info.plist`、`apps/android/app/build.gradle.kts` 是否一致，以及 `docs/README.md` 与 `docs/README.en.md` 的工作台版本列表是否包含当前版本。未知命令或版本不符返回非零。全仓 Markdown 的相对链接和按最近 `package.json` 解析的 npm 命令由 `tests/documentation.test.js` 覆盖，根 `SKILL.md`、`manual/` 和原型文档也在其中；参数和配置项由 `npm run config:check` 按 `scripts/lib/env-schema.js` 核对。新增命令或升级客户端时，同步对应文档、版本段和版本列表。

## 存储保留建议

`npm run storage:report` 只读运行 `storage:status` 概览并打印三类建议：必须保留（封存来源/正式 JSON/发布与审查清单/费用账本）、可压缩（旧清单/旧通过缓存/归档成品）、可删（logs/缓存/旧调试目录）。真正删除仍须先 `npm run storage:prune` 预览，再停写后显式 `--apply`。

## 验证矩阵

用户明确要求从原文重写既有日批次或全部历史页面时，使用 [当前历史计划流程](history-rewrite.md)：冻结页面范围，核验会议本地元数据/PDF，按明确获取序号封存 arXiv 官方文本/PDF。备用 `history:arxiv-batch` 仅接受本次官方获取失败保存的命名交接；普通 `reanalyze`、Reader 刷新或清除 analysis 字段不能替代完整历史范围与来源证明。

`history:resume -- --plan ... --phase ...` 只恢复现行暂停标记，随后重新执行原阶段命令；`history:resume status|analyze --run-id ...` 只查询或分析已存在的旧运行，`locate --scheduler ...` 只定位其真实 run ID。不支持 prepare、sources、promote 或新建旧运行，不改日期、来源或预算。已有恢复材料和费用按原身份保留。

```bash
npm run verify
git diff --check
```

完整 `verify` 必须在沙箱外运行，先检查与博客部署一致的 Hugo **0.160.1**，再检查全仓 JS/Python/shell 语法、运行一次 `npm test`（含三流程与旧记录兼容 JS）、两处 Python 单测和只读 `validate:data`。任何步骤失败都非零退出。Hugo 资源管线样例必须真正构建，缺少 Hugo 不能算完整通过。遍历排除 `node_modules`、`.venv`、`data`、`logs`、`.git` 等依赖、运行数据和 Git 记录目录，不跟随符号链接；Python 字节码写入独立临时目录。

只有 CI 或无数据的干净检出仓库才显式使用 `npm run verify -- --allow-empty`。普通维护默认复验已有数据。`npm run verify -- --quick` 仅检查语法和数据，不运行单测或 Hugo，不能代替完整验收。定向调试可单独运行 `test:default`、`test:compat` 或选定测试；完整验证通过后无须重复这些子集。

### 什么时候运行远端 CI

普通 Git 推送不再自动触发 CI。按批次及时中文提交、推送；先完成必要定向检查和交叉审查，代码稳定后主动运行一次完整验收。PR 仍自动检查。GitHub 页面可在 Actions → CI → Run workflow 中选择分支；终端也可以运行：

```bash
gh workflow run ci.yml --ref main
```

主动运行后核对实际 `headSha`，确认它是本轮最终提交，再检查所有套件。不能拿旧提交的成功替代当前代码验收，也不在每个中间检查点重复开启完整 CI。实现再次变化或修复真实失败后，才运行新的验收。

### 完整覆盖与并行范围

CI 下载 [Hugo 官方固定版本](https://github.com/gohugoio/hugo/releases/tag/v0.160.1)，核对该 release 的官方 checksums 后安装。Node 20、22 分别运行四个 `verify --suite javascript --shard I/4 --allow-empty`；Python 两套测试及 `--suite static` 各在 Node 22 环境运行一次。共十个验证任务，加两个原名汇总检查，共十二个检查；不再为相同 Python 和静态任务重复准备第二套运行环境。

JavaScript 文件集从权威 `npm test` 命令推导，由 Node 原生分片且片内仍串行；全部 JavaScript、Python、语法、数据和真实 Hugo 要求保留。全部验证任务成功后，`test (20.x)`、`test (22.x)` 才报告完整通过；缺片、失败或取消都不能冒充通过。每片保存日志。同分支被后续验收替代的旧纯 CI 可取消，此规则不用于 Pages 发布。本地默认 `verify` 仍完整串行，本地入口仅检查已安装版本，不自动下载或升级。

### 邮件通知来自哪里

仓库工作流没有发送邮件的步骤。GitHub Actions 通知由账户的 [Actions 通知偏好](https://docs.github.com/en/subscriptions-and-notifications/how-tos/managing-github-actions-notifications)控制；手动验收或 PR 检查仍可能按该偏好发送邮件。取消普通 push 触发后，中间提交不再产生这类运行通知。账户级偏好会影响其他仓库，维护本项目时不自动修改它。

离线测试使用临时目录和合成/脱敏样例，用模拟调用替代模型、网络和发布，不修改生产正式分析数据来制造成功。Reader 测试应覆盖多错定位、数字/单位、图标记、坏 JSON、陈旧或越权补丁、损坏候选、恢复及无进展；发布测试应覆盖协议变化、文件字节变化、未调用 LLM 就阻断的错误和真实 Hugo 资源构建。记录输入指纹、通过或阻断结果及失败调用数。样例通过不代表真实文章质量或付费 token 改善；需要验证这些效果时，在既有任务持续授权内做来源绑定的隔离实验，保留输入和实际费用，按结果决定是否继续。付费请求不属于 `verify`，不为必要实验再次索取逐轮确认。

选择原表内容时，只支持能够安全逐字渲染的表。付费生成前，`TABLE_N_SELECTION` 列明可用性和原因；空表头、所有行均被来源标成表头，或未处理的 MathML/TeX 双写，会禁用该表，运行时仍会拒绝。不能猜表头角色或放宽数字等价条件；这些表可用 `source_quotes`，但连续原句、数字和单位仍须完整核验。

会议博客拒稿维护及出版原页视图应同时核对 CLI、adapter、来源/反馈身份、独立批进度、不可变采纳、发布 pending 门和真实 raw→view 消费；仅 JSON 自哈希或合成样例不能授真实来源/新 Reader/发布通过。普通迁移须在 grant/状态写入前拒 pending，显式同维护入口继续正常批次和汇总；必要新窗沿持续授权登记，原材料和费用不改，见[会议博客维护](conference-workflow.md#博客拒稿后的正常-reader-维护)。

页面审查通过记录永久按“相对路径 + 内容 SHA”复用。修改发布器仍须重新渲染，代码、模型、协议或 Hugo 变化须执行本批检查并生成新的审查凭证；只有实际页面内容 SHA 变化才重审该通过页；后续会议整批允许不同合法原协议的 passed，但必须核 canonical 路径/页 SHA 缓存的完整原 result、物理字节及自哈希，失败项仍绑定当前协议。部署与线上页面仍需人工核验，不能由测试或状态命令代替。

修改独立人工审查时，须同时核对 assembler、声明读取器和发布器 provenance 的清单分区：文章才做语义及逐图审查，引用资料、词表和受控论文图走现有机器来源核验；最终凭证仍为完整并集。回归须覆盖资产替换、未审引用页、伪缓存、站内图越界、失败不写通过缓存，以及旧纯页面声明。机器资产证明不能代替人工语义判断。

单图审查的相邻五部上下文允许共享一段过渡文字，但必须在实际模型输入中标明前图解释与本图自有部分，保留原段全部内容及真实冲突的阻断能力。回归使用实际原稿片段和当前图片来源，不能把前图特征在本图中缺失判成正文虚构；独立上下文不添加这类标识，也不改正文或原图身份。

日更封存计划、来源读取和两类 Reader 人工补丁入口先以非阻塞方式打开输入，再检查普通文件、链接及权限要求，避免命名管道让恢复进程一直等待。拒绝异常文件不等于来源已经修复；应保留现场并按对应恢复入口处理。Python 原子替换若在目录同步阶段发生真实 I/O 或权限错误，会返回原错误；改名可能已经完成，不能据错误返回假定旧字节仍在。只有文件系统明确不支持目录同步时才保留兼容。
