# Mac 与 Android 全资料同步设计与验收

当前一键同步处理网站论文的收藏时间、待读、笔记、批注和阅读进度。两端已经共用完整备份格式。完整备份能保存并恢复整个研究目录，恢复会切换当前工作区。本文规定把其余研究资料加入双向同步所需的合并和恢复规则。下文的完整资料合并属于后续实现及验收范围。

## 两端保存什么

| 资料 | 两端共用的依据 | 拉取与合并 |
|---|---|---|
| 收藏、待读、笔记和批注 | 论文身份、条目身份、编辑和删除记录 | 合并不同条目的更改。相同条目有互不知晓的不同更改时保留各版本，提供查看和解决入口 |
| 阅读进度 | 论文身份、阅读内容修订、PDF 原件身份、设备 | 同一原件的进度可以在另一端继续。保留设备各自的最近位置，不能拿旧导读的滚动位置替代新版位置 |
| 个人 PDF 和导入资料 | 文件内容 SHA、原论文关联、导入记录 | 内容相同只存一份原件，保留各条导入记录。名字相同而内容不同时保留两份原件 |
| 离线导读和网站资料 | 来源 URL、发布修订、原文和资源清单 SHA | 以完整来源包验证和保留。网站缓存可以重新下载，历史缓存不能被标成最新发布修订 |
| 研究会话、模型输入与响应、用量 | 事件或会话身份、来源身份、各原文件 SHA | 以原记录字节合并。相同事件 ID 对应不同字节时保留双方并暂停自动复用。另一台设备导入的记录仍按原设备凭证能力决定可否继续 |
| Zotero 归档记录 | 原论文、归档目标和服务回执身份 | 同步工作台历史与回执。当前设备实际授权后才可执行新的归档操作 |
| 其他研究文件 | 原版本、相对路径、原件 SHA | 先保留完整原件并允许取回。只有两端都理解该格式时才将其导入当前工作区 |
| 系统钥匙串、Android Keystore、应用密码、模型密钥、本机响应校验密钥和 Zotero 自身数据库 | 设备各自管理 | 继续从设备的本机设置获取。云端文件不能赋予新的请求或归档权限 |

已同步的对象按逻辑身份和原件指纹核对一致性。两端的实际磁盘路径、原生窗口布局和临时缓存各自管理。研究记录引用文件时，同时记录来源提交和文件 SHA。在收到另一台设备的绝对路径时，应用用这些身份找到已验证的本机副本。

## 上传如何保留每次提交

1. 从本机取得一致的资料快照，并记录该设备实际读过的云端提交。为这次上传生成独立的提交 ID，按条目记录原件 SHA、大小、引用和删除标记。把提交清单及所需材料先保存在本机待传区。
2. 上传到此次提交自己的目录。分块可沿用两端已经验证的完整备份传输。逐块回读核对实际字节。所有必需对象齐备后，创建完成清单，并核对回读的清单与本机原件。
3. 另一设备同时上传时会取得不同的提交 ID。两份完成清单都可发现，无需竞争写入一个云端总文件。中断后的重试沿用原 ID 和字节。若服务已保存完成清单而本机没收到回执，重试先回读同一清单；相同内容直接确认，发现不同内容则保留本机待传材料并报告错误。
4. 云端提交完成、本机安装完成和后续编辑待传分别记状态。上传期间产生的本机编辑进入后续提交。恢复旧备份不会改变应用实际观察过的云端历史，也不会把备份之后的远端修改当成已经处理。

## 拉取如何更新本机

先读完一个确定的云端目录范围，验证每份完成清单及其关联对象，再推进已读取进度。某页列表不完整、必要文件缺失、服务限流或内容摘要不符时，保留旧进度。目录按时间和容量划分，分页结果需要能够证明范围完整。读取历史时使用本机已核验的提交索引，避免每次从头下载旧文件。

合并前固定本机资料和工作区代次。读过对方某个版本后才产生的编辑可以更新该版本。双方都从同一旧稿出发的编辑保持并列。以笔记为例，Mac 把旧稿改成甲，Android 离线改成乙，哪台先上传都应同时保留甲和乙。用户选定或合写丙时，丙引用甲和乙两份来源，两份原稿仍可查阅。删除也带有来源。删除与尚未见到的编辑同时发生时，保留编辑与删除记录，由用户决定是否继续保留该项。

新资料在临时工作区通过本地结构和引用核验后，再切换本机视图。切换前再次核对本机工作区代次和编辑内容。遇到新编辑或完成了一次恢复，保留已下载原件并重新计算合并。切换由同一工作区的进程锁保护。切换前在磁盘保存事务记录，标明旧目录、暂存目录、目标版本和每次目录移动的状态。应用重启时先核对目录与事务记录，再恢复旧目录或完成已验证的提交。磁盘写入失败时，旧工作区、云端原件与本机待传材料应仍可取回。

## 如何接入已有资料

旧的完整备份仍按原 UUID 和清单读取。旧的逐设备同步文档按原字节摘要作为独立来源导入。每次导入同一字节时复用已有结果。旧客户端继续运行期间，新看到的不同文档先保存为另一份来源。旧协议中已经覆盖、且从未进入任何快照的字节无法由升级重建。

迁移后仍需能查看旧备份和恢复其原件。迁移完成凭证应绑定已读取的云端范围、每份原清单、实际下载的字节及本机接收状态。完成这些检查以前，应继续标记迁移待处理。

## 两端共同的验收场景

| 场景 | 通过条件 |
|---|---|
| Mac 与 Android 在离线时修改同一旧笔记，再分别恢复网络 | 两端最终看见相同的冲突版本集合。交换上传顺序，结果相同 |
| 两台设备分别新增 PDF、笔记、批注、研究记录和归档回执 | 两端逐项核对逻辑身份、原文件 SHA 和关联引用。保留实际来源与用量记录 |
| 一台设备删除条目，另一台从同一旧稿编辑 | 删除和编辑都可找回。用户解决后，两端显示同一结果和处理记录 |
| 上传完成但连接断开，下载中断，或完成前退出应用 | 重启从同一材料继续。完成记录不重复，已有原件可取回，本机进度不会跳过未核验资料 |
| 拉取时继续编辑，或同时确认另一个完整恢复 | 旧拉取无法覆盖新编辑或已恢复的工作区。等待合并的原件仍可重用 |
| 两个本机进程同时更新工作区，或进程在两次目录移动之间退出 | 同一工作区每次只允许一个进程提交。重启能从磁盘事务记录核对并恢复一个完整版本 |
| 两份文件同路径不同内容，同事件 ID 不同 SHA | 原件都保留。不会根据设备时间强选一个，也不会授权复用另一台设备的本机签名材料 |
| 云端分页缺项、429 或 503、服务拒绝条件请求、磁盘空间不足 | 明确显示暂停原因，保留本机材料和已成功的云端提交。恢复后重试通过 |
| 升级前同时存在旧完整备份、旧同步文档和未上传的本机编辑 | 两端分别原样保留旧来源。迁移重跑结果一致，跨端取回的文件 SHA 与原件相同 |

隔离服务器用于控制同时写入、限流、缺项和中断顺序。之后需要两台实际运行的应用对同一验收目录同步并核对原始字节，最后以两端正式包做覆盖升级。当前五类个人资料的回归结果和完整备份的既有记录见[两端同步规则](android-cloud-contract.md)和[安卓验证说明](android-validation.md)。
