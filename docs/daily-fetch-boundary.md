# 日更补抓的起止时间

补抓解决的是“上一次正式日更之后，哪些论文还没有发布”。先确定已发布基线和时间窗口，再完整抓取窗口中的候选，最后排除真正已发布的论文。论文已经进入本地库，不能代替已发布证明。

| 名称 | 含义 | 续跑时的要求 |
|---|---|---|
| `since` | 本次查询的起点，连续性模式可能向前重叠 | 从已保存边界及旧见证派生，不手填缩短范围 |
| `until` | 本次固定的 UTC 结束时刻 | 重启后保持不变 |
| `originalSince` | 启用旧获取见证前的精确起点 | 保留在连续性身份中，解释重叠从何而来 |
| 已发布基线 | 博客已核验远端 `origin/main` 中的日更及单篇页 | 本地未推送、只分析成功的记录不计入 |

重叠意味着重复取得部分旧候选，用于确认没有漏过边界；分页大小只控制一次返回多少条，不能决定整个窗口覆盖多少论文。下面分别说明普通边界、旧记录兼容和连续性核验。

## 先固定已发布基线和窗口

补抓只从博客已核验远端 origin/main 基线中的日更汇总及其独立页确定上一次批次，不读取未提交会议页面，也不把当前未发布的入选集当作已发布。每次固定 UTC 结束时间；续跑须以保存的结束时间重新核验同一批次和边界身份，不能因为当天重新启动就移动窗口。

旧批次没有完整抓取检查点或原始提交时间时，核验全部已发布 arXiv 编号、独立页和引用元数据的 SHA，以最早编号所属提交月份的月首作为保守下界。这个下界不是精确发布时间，也不证明旧批次抓取完整。2026-10-03 的16篇均为2610编号，因此从2026-10-01 UTC补抓；会重复抓取部分论文，但只排除真正已发布的论文；失败、仅入库或仅分析记录不能当作已发布。旧论文或其他来源缺少可验证编号时明确失败，不静默缩短窗口；首次运行须另行明确初始化起始时间，不自动默认七天。

每页100条是分页大小，不是整个分类的总量上限。较旧的批次可能需要更多页；不得用更新日期或遇到一个历史编号就提前结束。当前实现只支持可核验 arXiv 编号的旧日更边界，不声称已解决任意 HuggingFace 混合旧批次的初始化。新 v7 批次归档完整后，核验七类 arXiv 与 HuggingFace 来源计数、内容 SHA、覆盖窗口、候选与入选集合，并把深度分析文件及生成清单关联到远端已提交页面，再使用上一窗口的精确结束时间。上一批次归档中的 v7 证明，或 current 中已关联上次正式页面的 v7 证明损坏时明确拒绝，不退回月首掩盖错误。

HuggingFace 精选列表的入选日取自 `paper.submittedOnDailyAt`；顶层 `publishedAt` 不能替代它。抓取显式使用 `sort=publishedAt` 列表排序，并继续核对按真实入选日排列的页内及跨页顺序，不能遇到早日期后忽略后面较新的精选记录。新的覆盖记录还须带 `provider.dailySelectedAtField: paper.submittedOnDailyAt` 标志；缺少此标志的旧 `complete` 记录不能证明该范围已覆盖，也不能直接复用。

本次未完成的HuggingFace来源可修复后重新抓取，已核验的七类arXiv记录仍可按原固定 `until` 恢复；这基于来源语义与候选计算规则保持不变，不是给旧证明补签。全部来源完整前，不启动筛选模型或分析。

正常运行前应先同步远端引用；helper只读取缓存的 origin/main，并确认本地HEAD包含它。缺远端引用明确失败，本地未推送提交不算发布。缓存引用本身不证明网页部署，仍须独立保留最后远端验证与上线检查。

同日发布后数据尚在 current 时，只在批次日期、完整窗口和已提交页面生成清单全部关联通过时使用该窗口。current 中其他日期或未完成的新尝试不能充当上一发布证明；无法绑定时仍用保守月首重叠，不缩短范围。

### 旧归档目录的只读兼容

旧归档程序曾按最后刷新时间分目录，可能把明确属于某个 `batchDate` 的深度分析结果放到之后日期，导致该批次的四份来源文件分散。

只有预期批次归档目录确实缺少 `deep-analysis-result.json` 时，边界核验才会在本项目其他有效日期归档中只读查找普通分析文件；文件全字节 SHA 必须精确等于上一已审生成清单的 `inputSourceReference.sha256`，文件内 `batchDate` 也必须等于上一正式发布日期。

找到后继续完整核验来源、论文集合及已提交页面，证明仍记录原文件名与原 SHA，因此不会改变固定边界身份和结束时间。预期路径已有文件但字节损坏时直接失败，不用别处副本掩盖；不读取符号链接、不跨旧工作区，也不复制、合并或修改运行数据。新的归档按明确批次日期归档，避免再次出现这种布局。

## 明确要求抓到以前获取过的论文

执行者明确启用 `requirePreviouslyFetched: true` 时，边界仍先核验上一正式发布的五份文件证明，再从原抓取检查点为七类 arXiv 分别选取提交时间最新的已获取 ID，为 HuggingFace 精选选取真实 `hfSelectedAt` 最新的已获取 ID。同一时间的候选按规范化 ID 排序确定见证，避免续跑身份漂移。该模式没有完整的旧 v7 证明时直接失败，不能从页面编号、库内记录或月首猜测以前获取过哪些论文。

新增 `boundary.continuity` 使用 `daily-fetch-continuity-v1`，记录 `required: true`、原精确起点 `originalSince`、旧检查点整个文件的 `archiveCheckpointSha256`、各来源的期望见证及 `overlapCutoffDate`，共同纳入原有边界身份 SHA。实际 `since` 取原起点、七类见证提交时间所在分钟、旧精选入选日北京时间零点中的最早时刻；HuggingFace 以单独的重叠截止日补抓。`lastDigestDate` 继续表示原正式发布日期，不能为了扩展范围改写它。普通模式的原有边界和身份计算保持兼容。

旧获取 ID 只证明分页到达旧范围，不能替代正式已发布页面的去重基线。每页仍处理完整内容、继续核验整个时间窗，不在某个重复 ID 处立即终止。来源健康记录必须同时保存期望 ID、实际命中的规范 ID 及官方原始提交时间或精选入选时间；共享核验器检查二者属于同一时刻，没有实际观察记录时不能声明 `encounterVerified`。来源记录和正式候选集合仍须通过各自的数量、内容 SHA 与完整范围检查。

旧检查点中确实为空的来源标记 `not-applicable/no-previous-records`；HuggingFace 旧记录只有补充论文而没有精选入选记录时标记 `not-applicable/no-previous-daily-selection`。这些状态不声明遇到旧论文，也不能凭空填写见证 ID。冷核验旧检查点字节后重新派生见证，可拒绝手改期望 ID、时间或空来源状态，即使手改者重新计算了边界自身的 SHA。

单次 arXiv API 查询仍受服务数量限制：超过 30000 条时自动拆分成不重叠的分钟范围，并核对拆分前后总数；最小一分钟仍超过限制时明确失败，不静默截断。请求经共享主机调度，间隔至少 3 秒，已有更长等待仍保留。

当前目录中的合法 JSON 若属于另一日期或尚未关联上次已发布页面，可以保守重叠抓取，并通过不写入边界身份的诊断信息说明原因；已关联正式页面的 v7 来源证明损坏则停止，不能退回月首掩盖问题。读取或 JSON 解析失败也必须报出。

日更的整个抓取流程先取得独立运行锁，避免两个批次同时改写当前数据。默认使用 `LOCAL_DEAD_PROCESS_OPERATION_LOCK_RECOVERY`：锁记录、权限和文件身份均符合要求，且明确确认持有者属于本机、进程已退出时，可以在原过期时间之前恢复这把运行锁。仍活跃的进程、其他机器的持有者或不安全的锁不能走这条提前恢复；不能仅凭时间较久或一次启动超时手工删除锁。原有过期判断及逐篇论文锁规则不变。取得运行锁后仍须核对北京时间批次日期，随后才可归档和抓取。

## 请求等待

所有分类和分页共用同一个请求调度器。每次 arXiv API 请求仍保留至少 3 秒间隔；网络失败与 HTTP 429 的重试等待继续生效。分类切换不再另加一分钟等待，首次请求也不再先等半分钟。一个分类抓得久可能只是补抓天数和页数多，不能仅凭耗时认定限流并追加等待。
