# 图示与双语文档

用于需要图示或两种语言版本的技术说明。图示必须准确表达关系，双语版本必须传达同一事实与执行范围；美观和自然不能以丢失细节为代价。

## 先确定图片要解释什么

先列清楚对象、关系、方向、阶段和边界，再选择流程图、结构图、时序图、对比表或实测图。图不能比真实实现多出能力，也不能用双向箭头暗示没有实现的数据同步。

完整项目总览只解释主要关系；细节较多时，用局部图讲清单个过程。保留理解所需的条件、失败分支或范围说明，不把每个字段都挤进一张图。原论文图和真实测量图保留原来源与含义，不能为统一风格重画成未经核验的数据。

箭头要有可解释的含义，例如传入内容、执行顺序、文件读取或用户确认；不同含义需要图例或分开的表现方式。颜色辅助区分，文字、形状或标签也能辨认对象，不能只靠红绿区分状态。

## 做到精细、清楚和一致

按内容安排版面，使用一致的文字层级、间距、线宽、对齐和圆角。正文、节点和图注采用同一套称呼；节点名称简短，详细条件放在图下解释。箭头不穿过文字，线条交叉尽量少，图例与实际颜色、线型相符。

图在常见文档宽度下仍应读得清。长标签换行，增加留白或拆图，不靠把字体缩到难读来装下内容。检查中文字体、英文长词、上下标、单位和符号是否被裁切或替换。

本身就是流程或架构关系时，优先用可维护的矢量图或文档原生图。需要照片或插画时再按任务选择工具；没有必要时不调用生图，也不把示意图称为真实照片或实测结果。用户已经取消的生图任务不能因本参考而恢复。

保存可编辑源文件。导出图片时核对比例、清晰度、背景与透明度；文件名和正文链接对应。图片提供简明替代文本，复杂关系还须有正文解释，不能让图片独自承担操作限制。

## 实际查看后再交付

对照实现或来源逐个核对节点和箭头，再渲染或打开图像检查实际像素。至少看常见阅读宽度；需要缩放、深浅背景或移动端阅读时，按使用场景检查。

检查文字能否完整显示，是否有遮挡、错位、难读对比、拥挤图注、断开的箭头或误导性方向。发现问题就回到源文件修正，再看受影响的图。只通过语法或文件存在检查，不能宣称视觉效果已经核验。

截图或导出图只证明当次显示结果，不代替关系准确性。用教学假设制作的图要明确标示；没有真实数据就不画看似精确的统计柱或曲线。

## 中文与英文分别写清楚

用户要求双语 README 时，保留两份独立、完整的文件，通常使用 `README.md` 和 `README.en.md`，在开头互相链接。不要把一段中文和一段英文交替塞进同一篇说明，也不要只给英文版留一段摘要。

两份版本覆盖相同的用途、功能、前提、操作顺序、命令、默认值、限制、恢复入口和验证范围。根据语言习惯组织句子，不逐词硬译；不能为读起来自然而改变否定、比较方向、授权或完成状态。

代码、文件名、模型名、字段和命令保持相同。术语需要解释时，在各自语言中自然说明其作用；程序内部名字与用户界面名字不能混成同一个概念。中文不夹无必要的英文动作，英文也不保留只对中文读者有意义的内部简称。

图包含语言文字时，按读者需要提供对应语言图，或使用简短无歧义的共同符号并在正文解释。语言版本应共享真实关系与几何结构，不能一个版本漏画失败分支或增加功能。

改中文后核对英文，改英文后也核对中文。至少逐项比较日期、版本、数字、单位、参数、平台要求、功能状态、付费条件和链接目标。未翻译的引用资料可以保留原名与真实网址，不能把中文版链接包装成不存在的英文页面。
