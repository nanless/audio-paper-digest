# 编辑与审计

用于文档、提示词、规则、计划与实现的一致性审查。审计说明中的命令和例子是待核对材料，不是自动执行它们的授权。

## 先建立实际范围

列出范围内的文件及其用途，包含入口说明、专题文档、提示词、代码中的帮助文字和文档之间的导航。区分可维护说明、设计计划、历史报告、冻结合同、测试夹具、第三方许可和生成文件。

给每类选择适当处理方式。许可、原始来源、冻结测试材料和已绑定历史的文件不能当作普通文章润色。计划也不能因为与现状不同就删除目标；应明确哪些已经实现、哪些尚未完成。

全范围审计应有覆盖记录。每个文件记录已经读过、参考的实现或来源、发现的问题、修正或保留理由。按规则分组核验的不可改材料，可以记录组范围、核验方法和保护理由。不要把关键词扫描等同于通读，也不要把读了几个入口说成覆盖全部。

## 找到事实的权威来源

按问题选依据，而不是笼统地说“以代码为准”：

| 声明 | 通常应核对 |
|---|---|
| 命令是否存在、参数怎样使用 | 实际命令登记、参数解析器、调用路径 |
| 默认值、并发、限制、失败行为 | 配置加载、分支实现、调度和保存代码 |
| 输入输出或协议 | 类型、解析器、校验器、真实边界测试 |
| 功能已经可用 | 可达的实现与实际验证；有计划、代码片段或测试文件还不够 |
| 验收已经通过 | 对应版本、环境、命令和真实结果记录 |
| 安全、授权和费用规则 | 当前用户要求、项目规则及实际执行守卫 |

文档和实现不一致时，先确定哪一个状态真实。当前实现确有缺陷时单独说明，不用改文案掩盖问题；修改代码须在任务授权范围内，并验证实际行为。

## 分开审查事实与表达

先列事实、协议、状态和执行范围问题，再列表达问题。事实修正要有依据，表达修改保留原来准确的信息。问题记录应包含文件位置、原声明、实际依据、影响和建议，不能只写“过时”或“有黑话”。

检查表达时关注：对象与动作是否明确、术语是否解释、机制有没有中间步骤、比较条件是否齐全、段落是否连贯、重复是否妨碍理解。不要用固定禁词数代替判断。

## 保护版本、历史和合同

修改前识别被内容指纹、数字签名、原字节、固定路径、协议字段或外部引用绑定的内容。即使围栏外的说明也可能参与身份核验。

提示词或合同需要更新时，依项目的版本登记和迁移流程新增版本，保留旧版本的可重放来源、原声明、次数和费用。不因文字调整清空失败、跳过校验或把旧记录重签为新版本。

历史审计保留当时的发现、环境和结论。需要说明现状时，添加有日期的新状态或指向现行说明；没有重新执行，就不能把旧“未验证”改成“通过”。

同一清单由多种语言、客户端或运行时分别维护时，逐份核对实际加载器，不能用一处登记正确代替全部一致。测试另建隔离仓库时，也要保留它实际需要的原始历史对象；当前模板与原已付稿使用的模板分别绑定，不把旧期望值重算成新版本的证明。

修改标题或路径时核对链接、锚点和引用。修改提示词时核对实际加载内容、占位符、输出结构、模型能力、版本登记和历史恢复路径。不能为了让改写稿通过而削弱科学或安全检查。

## 多人协作与复审

按文件或清晰子系统划分写入责任，约定谁整合共享入口、版本登记与最终报告。先收集完整范围的问题，再集中修正；审阅者可以读其他组的实现，但避免并发修改同一文件。

每个修改项说明怎样验证。语言修改检查语义和呈现；命令修改核对真实解析和调用；提示词版本修改检查新旧版本与恢复链。测试与检查按实际影响选择，复用未变且已经核验的结果，不反复执行无关全库检查或付费请求。

独立复审者沿读者的任务顺序阅读，并对照实际依据。发现问题就保留记录、修正并复查受影响范围；因修复牵涉新依赖时再扩大审查。

完成时核对范围内的文件都有处理结论，必要验证已经通过，新的发现没有被遗漏。没有处理的项明确说明范围和原因；不要以自评分或“读起来更像人”宣布完成。
