# Manual 教程的写作与审查要求

[返回入口](../README.md) · [文档地图](README.md) · [运行手册](workflow.md) · [架构说明](architecture.md)

本版编辑要求用于采用 `manual-agents-sol-high-v2` 模型规则的任务，其文件 SHA 必须登记在作者输入包中。读取程序须按任务规则指定的版本核验路径及 SHA，不能只凭包内副本一致就接受。无版本后缀的旧规范保留原字节，旧记录按 `manual-agents-terra-high-v1` 原规则读取。旧 state v1、任务包 v3 和 receipt v1 只供核验，不继续领取、启动、提交或重试新任务；不得改写模型身份或凭证，也不能自动用于新任务。阅读旧文章与继续任务是不同操作，具体来源检查见末节。

## 教程需要让读者理解什么

目标读者第一次接触论文方向，但具备基础数学和机器学习知识。读完后，他应能说明论文解决的具体问题和适用范围，画出输入、表示、模块、训练目标和输出的数据流，并解释关键设计怎样起作用。实验部分应让他看懂评测条件、指标方向、强基线和关键数字，知道哪些结论不能外推；复现部分应帮助他判断还需要哪些数据、配置、资源及未披露信息。

本说明约束读者可见文章及相邻质量记录。事实依据仍来自当前论文全文、`ArtifactIndex` 来源索引、结果主张与来源绑定；能否发布还须通过发布器和页面检查。符合文章格式不等于事实已全部正确。

## 作者、修订作者与审查者

| 角色 | 应完成的工作 | 输入与职责限制 |
|---|---|---|
| `author` | 从当前论文证据写初稿，解释术语、方法、训练、数据和实验，建立正文来源记录 | 不读旧博客、历史分析或其他论文，不把摘要直接扩写成全文解读 |
| `technical_scoring` | 检查事实、评分、实验口径、开源状态和因果判断，提交校准与具体问题 | 按实际输入白名单读取来源索引及受控初稿文件；不改正文，不为文风抬分 |
| `pedagogy_readability` | 检查读者是否能沿问题、术语和解释理解论文，以及图表怎样参与论证 | 不仅给“更流畅”“更详细”等泛泛意见，不提供可粘贴的旧稿补丁 |
| `author_revision` | 依据原始证据和两份已验证问题记录重新写完整终稿，绑定来源并记录问题处理 | 不读取前稿局部润色，不改变技术审查确定的评分 |
| 单页审查者 | 只读最终不可变页面，检查正文、Markdown、Hugo 和图像可见效果 | 不边审边改已绑定 SHA 的页面 |

主助手与新任务的四个正文角色、独立修订审计者和单页审查者均使用 `gpt-6.1-sol/high`，任务记录如实填写实际模型和任务信息。新任务使用 state v2、任务包 v4 和 receipt v2，由输入包所属规则核对 `modelPolicy`、模型及推理等级；凭证自行声明的规则不能代替这一核对。新 records v4、spec v6 和 longform v2 保持原格式版本号，并将当前 `modelPolicy` 纳入记录及其 SHA；新 `paperSubagent` 使用 version 2。缺少模型规则字段的旧记录只按原规则读取，不自动补字段或改写旧 SHA。审查任务的实际输入不是任意全文或外部文件，须遵守生成包的白名单。每条问题记录（`findings`）应指出问题位置、受影响的读者任务、来源依据和能验证的修正要求；意见应让作者知道怎样重新查证，不提供从旧稿直接复制的替换段落。

## 当前页面怎样呈现这些内容

写作内容和最终页面布局有不同职责。当前 Manual 单篇发布器先显示中文题目，再显示英文题目与论文链接、论文的一句话判断、标签和评分；随后呈现点评、核心摘要、开源与复现资源，以及深度解读正文。可选补充信息放在后面，作者机构、排名、文档类型、论文链接及评分元数据放在正文后的折叠区，逐维评分证据也位于文末。

因此，不能把作者机构写成当前一定在正文前或标签之后。八个分项即使为 0 也必须完整显示。原始文章用论文特有的三级标题，发布时嵌套为四级；文章输入的章节计数与最终 HTML 层级分别核对。

一句话判断帮助读者理解论文的主要选择，不列组件清单；点评说明最有依据的贡献与主要缺口；摘要交代问题、方法、最强证据和主要限制。正文承担术语、机制、训练、数据、图表和实验的具体解释，评分理由只引用已经说明的证据，不在文末引入新事实。汇总页保留单篇的核心摘要与资源说明，并显示作者机构，不再次压缩到丢失必要条件。

正式分析数据使用十三个机器解析标题：`评分`、`机器摘要`、`标签`、`作者与机构`、`论文评价`、`核心摘要`、`方法概述和架构`、`核心创新点`、`实验结果`、`细节详述`、`评分理由`、`局限与问题`、`开源详情`。新生成的分析和页面统一使用“论文评价”。读取旧记录时，“毒舌点评”仍对应第五节；两个名称同时出现或任一名称重复都不能通过检查。兼容读取不改写旧正文，也不更新旧凭证。

这些标题供程序解析分析记录，不要求读者文章照抄。完整 Reader 正文缺失时，Manual 发布器仍拒绝从固定章节重新拼接文章。API 分析中的评价为 2–3 句话，Manual 的评价须满足现有两段及证据要求，改名不改变各自的质量标准。

## 开写前先读完整论文

先确定研究任务的输入、输出和评价对象，再沿数据流区分作者新增、继承和复用的部分。核对训练阶段、损失、参数更新与推理流程，检查数据划分、规模、采样或标注方式。把主结果、消融、负结果和效率实验与相应主张对应起来，记录原图、原表、公式、相关工作及代码、模型、数据、演示资源的发布状态。

这些检查形成结构化研究与编辑计划，不要求在正文说“中心矛盾”或“证据柱”。现有字段及范围仍须填写：

| 记录 | 需要说明的具体内容 |
|---|---|
| `governingTension` | `conflict`、`sideA`、`sideB`、`paperChoice`：任务需要兼顾哪些要求，困难在哪里，论文作了什么选择 |
| `mustExplain` | 7–12 项读者判断贡献或复现所必需的信息，绑定原文及正文位置 |
| `readerQuestions` | 4–7 个推进理解的问题及其正文回答，从任务和方法延伸到证据与限制 |
| `evidencePillars` | 2–4 组按论文主张组织的证据，记录比较、最强支持和边界，不按表号堆材料 |
| `compress`、`omit` | 哪些背景应压缩或省略，说明理由；低价值信息不换词反复出现 |

系统或方法论文必须解释任务边界、音频或数据路径、架构、训练、评测、复现和局限；实证类还须覆盖消融或负面证据。综述、理论研究按实际类型检查，不捏造不存在的实验。

## 正文顺序跟随理解需要

按当前写作提示词，教程正文为 6000–40000 个字符，通常使用 8–18 个论文特有的三级标题。标题表达具体读者问题或技术判断，不机械重复“方法概述”“实验结果”“细节详述”，也不以图号或表号组织叙述。长度服务于解释，不能单凭字符数判断质量。

先让读者知道任务和输入输出，再解释已有路线为何不足、本文改变了什么，以及完整系统怎样工作。理解机制后再谈训练、数据、评测和数字，最后说明复现条件与适用边界。论文类型不同，顺序可调整，但不能在任务尚不清楚时堆架构名词，或在比较条件尚未交代时宣布数字胜负。

段落应围绕明确的解释任务展开，让问题、机制、证据和限制之间有清楚联系。无需每段重复固定句首，也不必在段末重新总结本段。删去同义重述，让下一段补充读者仍缺的信息。结尾说明论文的能力、代价和可采取的复现或研究行动，不再抄摘要、罗列分数或机械重复开篇。

写作要求与结构化校验的范围需分别核对。当前 v6 记录检查正文至少 2400 字符，输入包的输出说明列出 2400–24000 的规范化字符范围，`reader-longform-v2` 要求 6–32 个内容块；它们不等于写作提示词的长度和章节要求，也不证明较短稿件已经满足教程质量。不能用提示词的长度上限绕过输入包或实际读取器的限制。

V2 编辑计划另有 4–8 个章节锚点。读取文章时，若同时传入完整正文映射与来源索引，正文可以增加章节，但须按原顺序保留计划中的锚点；程序随后核验完整标题与内容块。独立 `qualityPacket` 检查及 v3 教程计划另有 6000 字符、8–18 节的检查条件，不能泛称所有当前 v6 都执行它们。不能把锚点数当作最终章节数，或将某个入口通过推广为其他检查都已通过。

## 术语在首次使用处解释

专业名词首次出现时，用“中文含义（官方英文，缩写）”或自然句说明它是什么、输入和输出是什么、在本文负责什么，并解释需要区分的相邻概念。不要只换一个读者同样不懂的名词。

例如，写“结合 A 和 B”还不足以说明方法。须交代 A 提供哪类信息，B 改变什么计算，两者在输入、特征、损失还是推理阶段相接，以及这样安排的原因。后续固定使用一个明确简称，中文与英文技术词及其缩写间保留空格；公式变量和几个普通字母不能冒充已解释的教程术语。

## 方法先说明完整数据流

方法总览需要覆盖原始输入和预处理、中间表示及时间/频率/语义分辨率、模块输入输出和职责、串行及并行路径的汇合、训练与推理差异，以及最终输出和计算代价。读者应能据此画出系统，而不仅记住模块名。

解释模块时，具体说明它处理哪些张量、序列或标签，做什么变换，结果交给谁，为何需要这一分工，以及哪个实验支持该设计。没有直接实验时写明“未直接验证”，不能由整机改善推断每个模块不可替代。

继承主干、本文新增模块、训练系统与作者尚未验证的主张须区分。核心创新通常 3–5 项，每项交代旧方法的具体限制、本文改变的机制、支持证据和不能外推的范围；数量不能成为编造创新的理由。

## 训练需要解释优化行为

训练说明应覆盖这些问题：

| 内容 | 需要核查什么 |
|---|---|
| 阶段 | 预训练、对齐、微调或课程学习有几步，为什么按此顺序 |
| 参数更新 | 每阶段哪些模块冻结、更新或共享 |
| 目标函数 | 每项损失约束哪个行为，权重怎样设置 |
| 数据安排 | 不同任务、模态和长度的样本怎样进入相应分支 |
| 优化配置 | 优化器、学习率及其调度、批次大小、步数或轮数、正则化 |
| 资源 | 硬件、训练时长、显存和并行策略 |
| 稳定性 | 预热、梯度裁剪、采样平衡及失败恢复 |
| 推理 | 解码、搜索、采样温度、分块、上下文和实时要求 |

未披露的项目写“论文未说明”，不得按常见实现补造。列出参数后解释它们怎样改变优化或推理行为，不能只转抄配置表。论文中的精确参数名、变量和值保留原形。

## 数据与评测条件先于数字

关键数据集应说明名称、任务、语言或领域、来源，训练/验证/测试划分、样本数或时长，以及是否公开。解释标签或构造方式、预处理、过滤与混合，并检查数据泄漏风险。随后说明它能支持哪条主张、不能代表哪些场景。

内部数据没有规模、采样或标注说明时，实验解释与评分都须反映较弱的证据。不同数据集和设置的异构指标不能拼成一个“综合领先”。

## 图片需要实际可见的证据

每张入选图都参与具体解释。图前告诉读者看哪条路径、哪组曲线或哪类模块；原图与准确图注、替代文本及可访问原分辨率随后出现；图后先说明像素中真实可见的结构、方向、颜色或数值，再解释它支持什么判断。

没有允许输入中的实际像素，不能猜坐标轴、曲线、颜色或模块。图后文字也不能补造图上不存在的信息。优先选能建立完整系统认识的总览图、解释关键分工的机制图，以及支持核心结果或失败条件的结果图。

拒绝标志、网页界面碎片、许可图标、作者头像和不可读碎片。当前发布器使用完整原图；关键事实必须依赖尚未准备的裁图或局部放大时，不使用该图。每篇默认最多 4 张，重复解释同一问题的图应删去。来源索引中的每个图片条目仍须记录使用或合法省略，不能因只选几张图而遗漏处理记录。

## 表格保留条件和全部必要数字

表前提出明确的比较问题，说明保留哪些设置和指标；表后解释关键差异、成本及不能外推的范围。不要孤立放表，也不逐行复述数据。

结果表应包含方法、数据集或划分/设置识别、强基线或同主干对照，以及写明名称、单位和 `↑/↓` 的指标列。数字和必要条件必须能核对，“观察”“意义”“结论”不能冒充指标，异构设置应拆表。

来源索引已有原始矩阵时，Markdown 表由程序按原表单元格 ID 和固定规则生成，不能手抄改数、删不利行或改变合并单元格语义。正文说明选择该表的理由和数值比较；数值单元格计数从原矩阵计算，不能自报。

每个表格都须有对应处理记录。结果表不能从正文与完整数据附录同时省略，数值单元格覆盖须为 100%；放入正文或附录的表格需按对应来源与覆盖规则核验，允许省略的其他条目须有具体理由。

## 公式说明对象、变量和作用

只保留理解方法或实验所需的公式。行内用 `\(...\)`，块级用 `\[...\]`，禁止裸 `$...$` 或 `$$...$$`。原式须有论文来源，不能为增强技术感编造公式。

解释它在计算什么，变量、维度和求和或期望范围怎样定义，再用自然语言说明优化方向或约束，以及它怎样改变模型行为、对应哪项实验。公式不能代替机制说明。每个来源公式都须记录使用或合法省略。

## 实验围绕论文主张展开

用 2–4 组证据组织实验说明，而不是按论文表号翻译。先交代比较问题、数据集、协议和指标方向，再给方法与强基线的准确数字，解释支持了哪项判断，指出未胜出项、缺失对照、不可比条件和适用限制。这些信息应组成连贯论证，不要求每节按相同五个句首写作。

系统或模型论文需检查目标域是否改善、公开基准是否支持主张、同主干比较的收益与退化、组件是否有直接消融，以及效率、实时或资源主张是否有实测。未做的评测标为 `notEvaluated`；局部第一不能概括为全面领先，整机结果不能证明每个组件都有因果贡献。

结构化结果主张绑定数据集/设置、划分/条件、方法、基线、指标、值、单位和方向，并同时对应来源与读者正文。实证文章须有可核对数字；当前正式结果要求系统/方法论文至少 4 条主张，其他实证论文至少 3 条，覆盖至少 2 个表格或实验组。读者叙述写成自然句，不能把记录格式的字段串搬入正文。

## 开源与复现如实区分状态

评估论文的开放资源时，以论文直接交付的代码、模型、数据或演示为依据。第三方依赖、普通引用和未来承诺不能写成“已开源”。资源区区分已发布且可访问、部分发布、承诺未来发布、只有演示、只有正文引用却没有直达资源，以及未发布。只有可访问的演示时，须明确这一状态，不能据此声称代码已开源。

每个链接使用 HTTPS，交代许可证、版本、能下载什么及复现还缺什么。资源事实和开源评分一致；没有披露的材料、配置、硬件或步骤写明缺口，不把缺证据当作技术错误。

## 限制与评论有明确依据

作者说明、负结果、未胜出设置和实际测过的范围，可支撑论文已知的适用边界。缺失消融、内部数据、统计不确定性、复现、效率、安全或外推问题，可以进一步讨论，但编辑推断须标明依据与推断身份，不能冒充作者结论。

使用具体动词和论文特有信息，让句子说明原因、结果或比较关系。删去泛泛的“提出新框架”、跨论文通用的亮点/短板模板、连续同义重述、为回避判断而重复的模糊限定，以及固定“证据边界在于”“下图用于核对”句首。适当的谨慎应对应实际不确定性，而不是使整篇没有清楚判断。

写作应自然、有节奏，不堆比喻或标题党。提示词、Manual、证据块、记录格式、审计 ID 等流程信息留在质量记录中，不进入读者正文；正文用正常术语和具体解释表达来源支持的事实。

## 评分与可读性分别复核

八维评分使用正式维度和上限：创新性 2、技术严谨性 1.5、实验充分性 1.5、清晰度 1、影响力 1.5、开源 1.5、可复现性 0.5、工程/实践价值 1.5，总分封顶 10。开源使用固定分值 `0/0.2/0.5/1/1.2/1.5`，不能自行创建尺度。每维理由给论文特有证据及扣分边界，脱离维度名称仍能说明判断。

清晰度只评价组织、符号、图表和表达；可复现性评价数据、配置、超参数、硬件和步骤。无直接消融的多组件系统不能获得满额实验充分性，内部评测规模不明时降低置信度，没有延迟、吞吐或资源测量时不能给满工程价值。一个缺陷按单一主要维度归因，不能在多维反复扣同一项。

可读性审查核对段内逻辑、段间承接、章节职责、事实是否在读者需要的位置解释、术语与视角、句子节奏和去模板表达；这些是质量记录维度，不是正文小标题。每条问题定位到文本和读者任务；全满分时追加反证检查，不能默认没有问题。当前四角色中的可读性结果另按七项可读性输出的格式和分数要求核验：每项为 0–2 的整数，总分至少 12/14，且每项都不能为 0，才可通过；这与其他质量量表分别核对。

## 修改本文件会影响哪些检查

解释澄清、内容要求或程序检查条件的修改都会改变本文件 SHA。新增程序必须执行的条件应同步实现并测试，不能仅在说明里写“必须”而让校验器继续接受。

Node 的实际任务文件检查在 `requireFiles=true` 时，对 `author` 和 `author_revision` 比较包内编辑要求及提示词与该任务规则指定版本的文件 SHA。注册、已保存状态恢复和 records 汇总使用这一检查；纯包结构校验不读文件，两个审查角色也不直接执行同一项当前文档比较。父任务、实际文件和结果的其他要求仍分别成立。

旧 Python v5 写作来源和既有封存预览仍按原协议核验固定路径及原文件 SHA，其中 `inputs.editorialContract` 对应提示词，`inputs.referenceContract` 对应编辑要求；新模型任务须核验新规则指定的规范版本和 SHA。不能仅凭旧清单一致就把旧模型记录用于新任务，也不能修改旧规范或凭证来让检查通过。

新任务从新规则指定的规范字节生成输入包；需要升级的在途任务从最早变化节点重新执行，再汇总后续结果。旧证据保留，不修改旧 JSON 或给旧记录重新计算凭证。静态旧 Markdown 和已部署文章不会因本文件修改自动不可读；是否能重跑任务、复验预览或重新发布，须按具体入口检查，见[历史兼容边界](architecture.md#历史兼容边界)。
