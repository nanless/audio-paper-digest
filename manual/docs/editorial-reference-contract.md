# Manual 教程编辑契约

[返回入口](../README.md) · [文档地图](README.md) · [运行手册](workflow.md) · [架构契约](architecture.md)

> 本文件既是人类可读的编辑说明，也是 production author packet 的 SHA 绑定输入。任何字节变化都会改变新 packet 的契约身份，使绑定旧 SHA 的在途节点及其下游失效。历史工件仍按自身绑定版本只读复验。

## 受众、目标与进入条件

目标读者是第一次接触该论文方向、但具备基础数学和机器学习背景的研究生。写作成功的标准不是“信息很多”，而是读者读完能够：

1. 用自己的话说出论文解决的具体问题和适用边界；
2. 画出输入、表示、模块、训练目标和输出的数据流；
3. 解释至少一个关键机制为什么有效，而不只是记住组件名；
4. 读懂主要实验表，知道指标方向、强基线、关键数字和不能外推的结论；
5. 判断复现需要哪些数据、配置、资源和仍未披露的信息。

本契约只约束读者可见教程和相邻质量记录。事实真实性仍由当前论文全文、ArtifactIndex、result claims 和来源绑定决定；发布可用性仍由 publisher/review gate 决定。

## 作者与 reviewer 的边界

| 角色 | 应做 | 不应做 |
|---|---|---|
| author | 从当前论文证据冷启动，建立教学主线，解释术语、方法、训练、数据和实验 | 阅读旧博客或历史 analysis 后扩写；同时处理第二篇论文 |
| technical reviewer | 核对事实、评分、实验口径、开源状态和因果边界 | 为了“好看”抬高分数；把整机结果归因给未消融组件 |
| pedagogy reviewer | 检查读者问题是否递进、术语是否就地解释、图表是否参与论证 | 只给“更流畅”“再详细一点”等不可执行意见 |
| revision author | 根据原始证据和结构化 findings 冷启动完整替换稿 | 在 previous draft 上移动、补段或局部润色 |
| page reviewer | 只读最终不可变页面，检查 Markdown 与 Hugo 可见效果 | 边审边改已绑定 SHA 的页面 |

所有 reviewer findings 应指出：问题位置、违反的读者任务、来源证据和可验证的修正要求；不要提供从旧稿直接粘贴的替换段落。

## 页面信息层级

发布页正文前按固定职责呈现：

1. 中文题目；
2. 英文题目和论文链接；
3. 标签；
4. 总分与八维分项；
5. 作者和机构；
6. 一句话概括；
7. 毒舌点评；
8. 核心摘要；
9. 开源与复现资源；
10. 深度解读正文。

正文之后放逐维评分依据。八个分项即使为 0 也必须显示。

这些区域不能互相代写：

- 一句话概括只给中心判断，不列方法清单；
- 毒舌点评分别指出最强证据和最大缺口，不重写摘要；
- 核心摘要回答问题、方法主线、最强证据和主要边界，不展开推导；
- 深度解读承担术语、机制、训练、数据、图表和实验解释；
- 文末评分只引用正文已经讲清楚的证据，不引入新事实。

汇总页的核心摘要和开源资源应直接保留单篇页内容，不再二次压缩；每篇同样显示作者和机构。

## 开写前：先建立论文地图

不要从摘要直接扩写。先逐项清点：

- 研究任务的输入、输出和评价对象；
- 论文真正新增的组件，与继承/复用组件的边界；
- 完整信号或数据流；
- 训练阶段、目标函数、冻结/解冻策略与推理流程；
- 数据集、划分、规模、采样或标注规则；
- 全部主要结果表、消融、负结果和效率结果；
- 架构图、机制图、结果图、公式与相关工作；
- 开源代码、模型、数据、Demo、许可证和未发布项。

然后形成一个读者蓝图：

- **中心矛盾**：任务的两端各需要什么，为什么相互拉扯；
- **7–12 个必须解释项**：读者判断贡献或复现不可缺少的知识；
- **4–7 个递进问题**：从“为什么需要”推进到“哪里不成立”；
- **2–4 根证据柱**：按论文主张组织，而不是按 Table 1/2/3 排列；
- **压缩项与省略项**：低价值背景只出现一次，模板信息不进入正文。

系统/方法论文的必须解释项至少覆盖 task boundary、audio path、architecture、training、evaluation、reproduction 和 limitations；有实验时还必须覆盖 ablation 或 negative evidence。

## 正文的因果顺序

正文通常用 8–18 个论文特有三级标题。标题应该表达读者问题或技术判断，不得机械使用“方法概述”“实验结果”“细节详述”，也不得包含 Figure/Table 编号。

推荐的教学依赖是：

```text
任务与反例
  → 基础术语和输入/输出
  → 既有路线及其具体失败原因
  → 本文的中心判断
  → 完整数据流/系统总览
  → 关键模块与机制
  → 训练目标、阶段和取舍
  → 数据集与评测协议
  → 主结果、消融、负结果与效率
  → 复现条件、限制和行动建议
  → 回扣中心矛盾
```

论文类型不同可以调整顺序，但不能在读者尚不理解任务时直接堆架构名词，也不能在没有说明评测口径时先宣布数字胜负。

每个自然段只承担一个任务：提出问题、解释机制、给证据或限定边界。段末应推进下一步，而不是换词重复本段。

## 术语必须在使用位置解释

第一次出现专业名词时，用“中文含义（官方英文，缩写）”或等价自然句说明，并立刻回答它在本文中的角色。

一个合格定义至少包含：

- 它是什么对象；
- 输入和输出是什么；
- 在当前系统中负责什么；
- 它与相邻概念为什么不能互换。

不能只写“使用 A 与 B 结合”。必须解释 A 提供什么信息、B 改变什么计算，以及“结合”发生在输入、特征、损失还是推理阶段。

同一术语后续固定使用一种简称。中文与 ASCII 技术词之间保留空格；不要用公式变量、两三个字母的普通短串冒充教程术语。

## 方法：先给全貌，再拆机制

方法总览至少讲清：

1. 原始输入和预处理；
2. 中间表示及其时间/频率/语义分辨率；
3. 主要模块的输入、输出和职责；
4. 串行路径、并行分支及其汇合点；
5. 训练时与推理时的数据流差异；
6. 最终输出和计算代价。

拆解模块时使用同一组问题：

- 这个模块接收什么张量、序列或标签？
- 它执行什么变换？
- 输出交给谁？
- 为什么不能由前后模块承担？
- 哪个实验直接支持这项设计？如果没有，明确写“未直接验证”。

不得把继承主干、本文新增模块、训练系统和作者尚未验证的主张混成一条“创新点”。核心创新通常 3–5 项，每项都要包含旧方法的具体限制、本文改变的机制、支持证据和不能外推的范围。

## 训练细节：解释优化对象，而不只列超参数

训练章节至少检查：

| 维度 | 需要回答的问题 |
|---|---|
| 阶段 | 预训练、对齐、微调或课程学习有几步？顺序为何如此？ |
| 参数更新 | 每个阶段哪些模块冻结、解冻或共享？ |
| 目标函数 | 每一项损失约束哪个行为？权重如何设置？ |
| 数据路由 | 不同任务/模态/长度样本如何进入对应分支？ |
| 优化配置 | optimizer、学习率、schedule、batch、步数/epoch、正则化是否报告？ |
| 资源 | 硬件、训练时长、显存或并行策略是否报告？ |
| 稳定性 | warm-up、梯度裁剪、采样平衡或失败恢复是否报告？ |
| 推理 | 解码、搜索、temperature、chunk/context、实时约束如何设置？ |

没有披露的项目明确写“论文未说明”，不得按常见实现补造。列出超参数后还要解释它改变的优化或推理行为；否则表格只是配置转录。

## 数据集细节：先说明数据在证明什么

每个关键数据集至少交代：

- 名称、任务、语言/领域和来源；
- 训练/验证/测试划分；
- 样本数、时长或规模，以及论文是否公开；
- 标签或构造方式；
- 预处理、过滤、混合和数据泄漏风险；
- 它支持哪条主张，不能代表哪些场景。

内部数据若没有规模、采样或标注说明，必须在实验解释和评分中同步降低证据强度。不能把多个数据集的异构指标拼成一个“综合领先”。

## 图：必须成为论证节点

图片不是装饰。每张入选图都应形成：

```text
前文提出具体阅读任务
  → 图片（准确 caption/alt，可访问原分辨率）
  → 后文指出可见事实并回扣结论或边界
```

图前必须告诉读者看什么，例如追踪某条输入路径、比较两条曲线或定位共享/私有模块。图后先说像素中真实可见的结构、方向、颜色或数值，再解释这些事实支持什么；不能用图后文字补造图中没有的信息。

优先选择：

1. 建立完整心智模型的总览图；
2. 解释关键分工的机制图；
3. 支撑核心证据或失败边界的结果图。

Logo、网页 chrome、许可图标、作者头像和不可读碎片应拒绝。当前发布器使用完整原图；若关键事实必须依赖未物化裁图或 panel 放大，宁可拒绝该图。每篇默认最多 4 张，重复回答同一问题的图应删除。

## 表：让数据回答明确问题

每张表前先写它要回答的比较问题、保留哪些设置和指标；表后解释最关键差异、代价和不能外推的范围。不能孤立放表，也不能逐行复述。

结果表至少应有：

- 方法列；
- 数据集、split 或设置识别列；
- 强基线或同主干对照；
- 写明名称、单位和 `↑/↓` 的指标列；
- 可核对数字和必要条件。

“观察”“意义”“结论”不能冒充指标列。异构设置应拆表，不要为了列数整齐拼接。

ArtifactIndex 已有源矩阵时，Markdown 表必须由 cell ID 确定性渲染；禁止手抄改数、删掉不利行或改变合并单元格语义。正文需要覆盖表格数值 cell，并说明为什么选择这张表。

## 公式：原式、变量、直觉和作用缺一不可

只保留理解方法或实验必要的公式。行内公式使用 `\(...\)`，块级公式使用 `\[...\]`；禁止裸 `$...$` / `$$...$$`。

每个重要公式依次解释：

1. 原式在计算什么；
2. 变量、维度和求和/期望范围；
3. 用自然语言描述优化方向或约束；
4. 它如何改变模型行为，以及对应哪项实验。

公式不能替代机制说明。论文没有必要公式时不要为“显得技术”而编造。

## 实验：按主张组织证据

不要按论文表号翻译。围绕 2–4 根证据柱组织，例如：目标任务、公开泛化、消融/负结果、效率/部署。

每个实验小节遵循：

```text
比较问题
  → 数据集/协议/指标方向
  → 方法与强基线的精确数字
  → 这组证据支持什么
  → 未胜出项、缺失对照或不可比条件
  → 不能外推到哪里
```

系统/模型论文至少检查：

- 目标域任务是否真正改善；
- 公开基准是否支持核心主张；
- 同主干对照是否有收益和退化；
- 多组件系统是否有直接消融；
- 效率、实时性或资源主张是否有真实测量。

不存在的评测明确标记 `notEvaluated`。局部第一不能概括为全面 SOTA；整机结果不能证明每个组件都有因果贡献。

结构化 result claim 必须把 dataset/setting、split/condition、method、baseline、metric、value、unit 和 direction 同时绑定到来源与读者正文。实证论文至少有一条可核对数字；读者叙述必须是自然句，不能把 schema 字段串当正文。

## 开源与复现

只把本文直接交付的代码、模型、数据或 Demo 计入开源。第三方依赖、论文中的普通引用和未来承诺不能写成“已开源”。

资源区应区分：

- 已发布且可访问；
- 部分发布；
- 承诺未来发布；
- 只有 Demo；
- 只有正文引用、没有直达资源；
- 未发布。

每个链接使用 HTTPS，并说明许可证、版本、可下载内容和复现仍缺什么。资源事实与开源评分必须一致。

## 限制、批评和写作语气

限制分两层：

- **论文证据直接支持的边界**：作者说明、负结果、未胜出设置或已测适用范围；
- **进一步审视**：缺失消融、内部数据、统计不确定性、复现、效率、安全或外推风险。

编辑推断必须标成推断，不能伪装成作者结论。

文字应有节奏、有判断、有因果连接，但“有文采”不等于比喻堆叠或标题党。优先使用具体动词和论文特有名词，避免：

- “现有方法存在不足，本文提出新框架”；
- “亮点一是”“短板是”等跨论文模板；
- 连续多个段落同义重启；
- 为避免承担判断而反复使用“可能、或许、一定程度”；
- “证据边界在于”“下图用于核对”等机械固定句首；
- prompt、manual、evidence block、schema、审计 ID 等流程元话语泄漏到读者正文。

结尾回到开篇中心矛盾，说明论文选择换来了什么能力、付出了什么代价。不要再次罗列分数或改写摘要。

## 评分与可读性复核

八维评分必须使用正式维度、上限和固定开源锚点。每维理由都要包含论文特有证据和扣分边界，能脱离维度名称独立成立。

特别注意：

- 清晰度只评价组织、符号、图表和表达；
- 可复现性只评价数据、配置、超参数、硬件和步骤；
- 无直接消融的多组件系统不能获得满额实验充分性；
- 只有内部评测且规模不明时必须降置信度；
- 没有延迟、吞吐或资源测量时不能把工程价值写满；
- 可读性全满分时必须追加反证审查，而不是默认“没有问题”。

Readability review 至少检查：段内逻辑、段间承接、章节职责、事实局部性、术语与视角、句子节奏、去模板与文学性。每个 finding 必须能定位到正文位置和读者任务。

## 发布前验收清单

### 内容

- [ ] 开篇定义任务、输入输出和中心矛盾，而不是先给组件名。
- [ ] 方法总览能画出完整数据流；新增与继承组件明确区分。
- [ ] 训练、数据集、评测协议和复现缺口都有专门解释。
- [ ] 每个关键术语首次出现时定义，并说明与相邻概念的关系。
- [ ] 主结果、消融/负结果和效率证据按主张组织。
- [ ] 精确数字、作者机构、资源状态和限制都有当前论文证据。

### 图表公式

- [ ] 每张图都有论文特有 lead 和 explanation，且图中事实肉眼可见。
- [ ] 每张表前有比较问题，表后有结论与边界；指标列、方向、单位和条件完整。
- [ ] ArtifactIndex 表格 cell、图片、公式都被使用或合法省略。
- [ ] 公式使用 `\(...\)` / `\[...\]`，变量和优化直觉均已解释。

### 页面与渲染

- [ ] 标题层级在 Markdown 和 Hugo HTML 中均大于正文，且没有图表编号式标题。
- [ ] 标签之后显示作者和机构；八维分项完整。
- [ ] 表格在桌面和移动端可读，没有错列或被截断的关键列。
- [ ] 图片 URL、caption、alt、邻文和可点击原分辨率一致。
- [ ] 没有裸 `$`、未闭合强调、内部 schema 名称或流程元话语。
- [ ] 单篇页与汇总页的核心摘要、开源资源、作者机构保持一致。

任何页面修改都会改变 page SHA，必须重新审查变化页并重新组装批次 receipt。Review 通过不代表可以跳过 push 的 Git 与远端 OID 验证。

## 契约变更规则

修改本文件前先判断是：

1. 纯解释澄清；
2. author/reviewer 的新语义要求；
3. 应由确定性 validator 实现的硬门禁。

三类修改都会改变本文件 SHA。若新增硬门禁，应同步更新实现和测试；不能只在文档里声明“必须”却让 validator 静默接受。新批次从新 SHA 物化 packet；在途批次从最早受影响 role 重做；历史工件继续按旧契约只读复演。
